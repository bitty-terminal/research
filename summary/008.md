# 008 — Semantic Terminal Folding, Hints, and Composer

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-07
- One-liner: Commands become objects; keyboard can address everything.
- Background / Problem:
  - AI coding interfaces have popularized output folding; Bitty lacks a space-saving equivalent.
  - Long commands and multi-command pages are hard to operate without a mouse.
  - Single-line Enter-to-run misfires easily; long multi-line commands edit poorly.
- Key conclusions / Decisions:
  - Direction fixed as semantic terminal: character stream upgraded to addressable, operable, foldable UI without touching underlying terminal truth.
  - Output folding builds on existing shell-integration command ranges, adding stable command ranges and a command-block abstraction.
  - Hint mode generalizes keyboard jumping: targets separated from actions, supporting folding, jumping, multi-Panel, and workspace.
  - Hints should become a generic plugin API, not a one-off jump feature.
  - Input side builds a command composer: multi-line editing, history, external editing, paste-to-submit.
  - Composer submit keys are configurable; defaults are Enter for newline, Ctrl+Enter to execute, Esc to close, Alt+E for external editing.
  - No global Enter hijacking; handle shell, interpreter, editor, and fuzzy finder scenarios separately.
  - Prefer structured submit over per-key simulation.
  - Split into three capabilities: command blocks, Hints, composer.
  - Landing order: semantic anchors, folding MVP, Hints, composer, external editing, cross-Panel generic API.
- Destination: bitty-terminal-docs, bitty-plugins-docs (terminal interaction versus first-party plugin capabilities split across both)
- Open items:
  - Overlay real-world issues still need fixing.
  - Composer default keybindings await dogfooding decision.
