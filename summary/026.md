# 026 — Built-in Contracts and Layered Prompt Configuration

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-15 00:05
- One-liner: Built-ins teach semantics, users set preferences, runtime owns capabilities.
- Background / Problem:
  - Built-in runtime semantics mixed with user preferences into giant prompts that are hard to maintain and easy to override.
  - If tool interfaces rely fully on natural-language description, every plugin addition forces core prompt edits.
  - Project configuration is mostly single documents, lacking structured manifests with capability boundaries.
- Key conclusions / Decisions:
  - Built-in core prompts teach only runtime semantics and invariants, staying short, stable, and versioned, never directly overridable.
  - Prompts teach semantic rules only; interfaces come from injected tool schemas so new tools need no core prompt change.
  - Prompts assemble from five layers: built-in contracts, global user instructions, project instructions, skill and agent personas, and current-turn runtime deltas.
  - Structure project configuration as manifests covering instructions, agents, skills, tools, external services, hooks, and context switches.
  - Different agents may use different personas, combining core, user, project, and persona into final behavior.
  - Capabilities come from registry and permissions; prompts cannot grant authorization, and over-privileged calls are rejected by runtime.
  - Fetch details on demand with a runtime self-description interface; panel and similar features are consulted only when used.
  - Bring panel and lifecycle semantics into the formal runtime model to stop each plugin reinterpreting them.
  - Keep assembly structured internally, converting to model-specific message shapes at the edge, with stable layers first for caching.
