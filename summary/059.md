# 059 — Wheel Context Runtime: Tiered Evidence, Knowledge DAG, and Information Refinement

- Status: Captured — conclusions not yet captured in any `*-docs` repo; destinations proposed below (owner-pending)
- Date: 2026-09-19 (archive receipt; the original discussion contains no explicit date)
- One-liner: Elevate Wheel context from transcript compression to a Context Runtime: decouple immutable Evidence Store (Git ODB/CAS) from the Knowledge DAG; treat temperature (Hot/Warm/Cold) as working set state orthogonal to semantic type; replace linear chat logs with recoverable Context Refinement and provenance; and coordinate multi-agent teams via shared knowledge refs and cache-aware provider lowering.
- Background / Problem:
  - The owner asks how Bitty AI / Wheel should manage large context: structured Git-like representations (why/what/where/how, Context Compiler) work well for state, but how should massive raw text—namely file reads (code, documentation) and internal thinking—be managed without creating runaway prompt growth or cache-miss cost explosions?
  - In existing coding agents, file reads permanently bloat the linear conversation history (`read_file` appends thousands of tokens forever), and compaction simply summarizes or truncates transcripts, degrading reasoning quality and destroying prefix cache.
  - The owner asks how Agent Teams should transfer context without massive token duplication, and whether this paradigm is better characterized as "Information Refinement" rather than mere "Context Compression".
- Key conclusions / Decisions:
  - **Foundational Architectural Principle**:
    - _Prompt is a build artifact, not the source of truth._
    - _Transcript is an execution trace, not the memory._
    - _Evidence is stored, events are persisted, knowledge is refined, state is committed, context is compiled._
    - Core invariant: _Lossless storage, lossy materialization._ Active context can be concise and lossy, but the underlying system retains full reversible provenance.
  - **Context Refinement vs Context Compression**:
    - Reject the paradigm of constantly summarizing bloated conversation transcripts.
    - Establish distinct lifecycle operations:
      - **Refinement**: Transforming raw Evidence/Events into dense, structured Knowledge (Findings, Facts, Decisions, Rationales).
      - **Materialization**: Lowering References and Knowledge into active prompt tokens.
      - **Promotion / Demotion**: Moving items between Hot, Warm, and Cold working sets.
      - **Eviction**: Removing items from the active working set without deleting them from storage.
      - **Compaction**: Rewriting transcripts (retained only as a fallback for legacy transcripts).
      - **GC**: Reclaiming unreachable or expired evidence blobs.
  - **Temperature (Hot/Warm/Cold) as Working State, Not Content Type**:
    - Semantic type (Evidence vs Knowledge) is strictly orthogonal to working temperature:
      - _Hot_: Actively needed for current reasoning (verbatim code slice or exact finding).
      - _Warm_: Recently active or likely needed soon (summary, outline, or indexed reference).
      - _Cold_: Inactive but recoverable via provenance ref (not in active prompt).
      - _Archived_: Historical audit evidence.
    - `Pinned` is an orthogonal boolean (`pinned=true|false`), allowing critical raw code slices to remain Hot and Pinned, while stale decisions become Cold.
  - **Evidence System (OS Page Cache / Virtual Memory Analogue)**:
    - File reads do not enter conversation history. They generate an `EvidenceView` (path, revision, blob hash, symbol/line selector, content hash, freshness).
    - Once the agent derives a Finding or Fact (e.g. "dedup must precede budget in compiler.rs"), the 145 lines of raw code demote from Hot to Warm/Cold. The active prompt retains only the compact Finding and an `EvidenceRef` (`compiler.rs@blob:abc#L182-L327`), slashing prompt tokens while preserving complete traceability.
    - Git Object Database (ODB) is natively leveraged as the Content-Addressed Store (CAS) for tracked files; Wheel CAS only stores untracked files, stdout, LSP/MCP outputs, web fetches, and generated artifacts.
  - **Event -> Knowledge Bridge: Structured Rationale**:
    - Replace thousand-token internal monologue dumps with structured `Action` metadata: `Why`, `What`, `Where`, `How`, `Expected`, `Observed`, `Implication`, `Next`.
    - Separate **Raw Reasoning** (ephemeral, noisy, provider-local, uncommitted) from **Reasoning Artifacts** (Hypotheses, Decisions, Rationales, Constraints, Findings).
  - **Provider Continuation Layer & Thinking State**:
    - Provider-native opaque thinking blocks (Claude thinking blocks, OpenAI continuation handles, session IDs, cache breakpoints) belong to a separate `Provider Continuation Layer`.
    - They are non-canonical and non-portable: switching from Claude to GPT retains the canonical Context DAG without breaking agent continuity, while Claude-to-Claude reuses native continuation state for cache hit optimization.
  - **Agent Team Knowledge Sharing: Shared Base + Private Branches**:
    - Agents share **knowledge refs, not transcripts** (`Agents share knowledge, not transcripts`).
    - Team context forms a tree: Common Ancestor `C0 -> C1` (mission, task DAG, architecture decisions, shared interfaces).
    - Individual agents branch off (`A1`, `B1`); Agent A's working set (raw reads, scratch observations) stays private. Only when Agent A reaches a verified decision or finding does it publish a `Context Commit` back to the Team Context DAG.
    - Inter-agent messaging passes lightweight references (`TaskRef`, `BaseContextRef`, `KnowledgeRefs`, `EvidenceRefs`), allowing the recipient's Context Compiler to choose what to materialize.
  - **Multi-Objective Context Compiler & Cache Planner**:
    - Context compilation balances: `utility = (relevance + criticality + recency + dependency + authority + evidence) - (token_cost + staleness + redundancy + cache_disruption)`.
    - Representations range from Exact -> Slice -> Semantic Extract -> Structured Knowledge -> Digest -> Ref Only -> Omit.
    - **Cache Planner**: Arranges prompts into a stable shared prefix (system prompt, tools, capability definitions, team context commit) and a dynamic suffix (agent role, task, working set, hot evidence, recent events).
    - **Refinement Threshold**: Refinement is scheduled economically (only when `expected_saved_tokens > cache_break_cost + refinement_cost`), preventing micro-refinements from constantly invalidating the prefix cache.
  - **The 6 Core Components of Wheel Context Runtime**:
    1. `Evidence Store`: Content-addressed store (Git ODB + Wheel CAS) preserving raw facts and provenance.
    2. `Context DAG`: Graph of structured knowledge (Tasks, Decisions, Findings, Rationales) linked to Evidence.
    3. `Working Set Manager`: Manages Hot/Warm/Cold, Pinned, and eviction policies.
    4. `Refinement Engine`: Distills raw evidence/events into high-density knowledge.
    5. `Context Compiler`: Resolves working context IR based on role, task, and token budget.
    6. `Cache Planner / Provider Lowering`: Maps Context IR to provider-specific cache layouts and manages provider continuation state.
