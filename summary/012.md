# 012 — Batch Tool Calls and LSP Reuse Strategy

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-13 02:44
- One-liner: Tool call count is not model round-trip count, so favor batching and semantic tools while reusing existing LSP implementations through interfaces.
- Background / Problem:
  - Reading and writing many files one tool call at a time raises concerns about model API cost and cache invalidation.
  - The applicable boundaries for parallel calls, batch patches, subagents, and similar techniques need to be clarified.
  - Ownership of LSP and lint support needs a decision, including whether they can assist checking and code understanding.
- Key conclusions / Decisions:
  - A single model request can return multiple tool calls, run them concurrently, and consume the results in one later request; measurements showed about twenty percent of tool messages were parallel batches, saving over seven thousand round trips.
  - Serialize when there are data dependencies, model protocol limits, or interactive tools; at least one more request is still needed to consume batched results.
  - Rule of thumb: place independent dependency-free calls side by side in one round, serialize dependent ones, prefer code-execution-style batching for mechanical multi-file loops, and call directly or delegate to a subagent when judgment-heavy exploration is needed.
  - Batch patches change many files at once; delegation isolates parent context but does not remove total call volume; batching saves round trips but results still cost tokens in context, while code-execution batching can return only a summary.
  - Bitty only implements stable language interfaces and capability abstractions while users install their own language servers and linters; covered capabilities are diagnostics, formatting, go-to-definition, find-references, and code actions.
  - bitty-ai should center on a small set of high-information-density semantic tools rather than exposing dozens of low-level file and shell tools.
