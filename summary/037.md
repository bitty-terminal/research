# 037 — Storage Layering and Session Sharding

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-15 23:14
- One-liner: Separates config, data, state, and cache with per-session storage to avoid a single bloated database.
- Background / Problem:
  - A single global database grows toward tens of gigabytes with use, making migration and backup painful.
  - The config directory mixes in logs, history, and caches, which resists dotfile management.
  - Export semantics for sessions, panes, and memories are not yet separated.
- Key conclusions / Decisions:
  - Strictly separate config, data, state, cache, and runtime layers: config stays portable while cache stays rebuildable.
  - Retire the single giant database in favor of a small catalog library plus per-session libraries, a content-addressed object store, and a separate memory store.
  - Large payloads store hash references with compression and dedup; contexts store assembly recipes instead of duplicating full text.
  - Memories split into session, project, and global tiers, with rebuildable indexes kept in cache.
  - Pane history lives segmented under the state directory; the AI side keeps only references.
  - The export UI may be pluginized, but snapshot serialization must be a stable core capability with versioned export formats.
  - Sessions follow active, closed, and archived lifecycles with matching storage stats, cleanup, and self-check capabilities.
