# 045 — Agent Authority and Hard-Safety Boundary

- Status: Partial — bitty-upstream mechanisms captured (draft capture in bitty-docs, PR bitty-docs#323 open — not merged; six implementation tasks queued in `bitty` as CTX-0519..CTX-0524); the Lua-harness/bitty-ai-owned semantics are not captured (owner-pending in bitty-ai-docs; `origin/045.md` stays unrenamed by us)
- Date: 2026-09-17 00:46
- One-liner: Lua decides "how", never "whether it is allowed": keep the agent's impassable boundaries in Core — capability intersection, resource limits, panel write-lease, secret isolation, and privilege/path authorization — while the Lua harness composes workflows on top.
- Background / Problem:
  - A capable agent harness can be assembled mostly in Lua, but the security boundary cannot be guaranteed by Lua: prompt-only rules and Lua self-discipline fail in predictable ways (an unbounded subagent fan-out; `for i = 1, 1000 do spawn("cargo build") end`; several agents plus a human writing to one PTY; `cat .env` after being told not to; provider tokens reaching context, logs, Lua logs, or panel history; an agent running `sudo` because it looked reasonable; a plugin declaring `filesystem = "all"`, `root = true`, `max_agents = 100`).
  - Bitty needed a concrete split: what belongs to Lua (workflow, strategy, scheduling, UX), what belongs to the AI layer (agent/task/delegation/budget/capability semantics), what belongs to the host (non-bypassable execution, PTY, filesystem, panel, secret, privilege boundaries), and how user/project policy narrows without ever widening.
  - The record framed this as four layers plus one sentence — "Lua can decide how to do something, but it cannot decide whether it is allowed to" — and then named thirteen failure modes with the mechanism that must prevent each.
- Key conclusions / Decisions:
  - Fix the layering: `bitty` owns the host security ceiling (execution, PTY, filesystem, panel, secrets) as a non-bypassable boundary; `bitty-ai` owns the AI-semantics hard constraints (agent, task, delegation, budget, capability); the Lua harness owns workflow/strategy/scheduling/UX and may compose freely but never widen authority; user/project policy only narrows.
  - Classify every rule as Hard Safety, Policy, or Strategy: hard ceilings (max agent count, max subagent depth), RAM/CPU limits, disk free-space guard, panel writer exclusivity, `.env` authorization, secret handles, and root escalation are host/AI enforcement, never convention; strategy choices (agent fan-out, retry, parallel review, scheduling order) stay Lua.
  - Four-layer policy stack (Host Security Ceiling / User Policy / Project Policy / Lua Harness Policy) with intersection semantics: the effective value is the most restrictive; host 16, user 6, project 4, Lua requests 8 yields 4, and path grants narrow the same way.
  - `EffectiveCapability = Host Ceiling ∩ User Policy ∩ Project Policy ∩ Parent Delegation ∩ Task Grant ∩ Agent Request`: a Lua declaration is always a request; `filesystem = "all"`, `root = true`, or `max_agents = 100` never self-grant; `Capability(child) ⊆ Capability(parent)`; a worker cannot re-expand authority a commander ceded.
  - Resource enforcement for jobs is Core mechanism: the chain Lua request → bitty-ai resource/budget policy → bitty execution supervisor → OS must end in enforcement (Linux cgroup v2, `RLIMIT`, process groups, GPU observation/budget, filesystem quota or free-space guard; Windows Job Objects; macOS equivalents) and typed failures (`ResourceLimitExceeded`, `ExecutionBudgetExhausted`, `ConcurrencyLimitReached`) — never a crashed machine.
  - Panels get a Core lease: several read leases and one interactive writer identified by `(principal, generation)`; a non-holder's write is denied with the lease reason, and handoff fences the old generation and assigns a new one. Discipline is expressed by Lua; mutual exclusion is guaranteed by Core.
  - Secret isolation uses opaque handles (`secret://github/default`): the host credential store resolves the value and injects it into the child process environment only; agent context, execution logs, Lua logs, and panel history never receive the value. Use ≠ read.
  - Privilege is denied by default: a `PrivilegeRequest {reason, command, target}` passes host policy to explicit user approval and then allows exactly one scoped privileged execution — no permanent sudo session and the agent never knows the sudo password.
  - Filesystem authorization must not rely on filenames: default-deny sensitive locations (`.env`, `.env.*`, `~/.ssh/**`, `~/.gnupg/**`, `~/.aws/credentials`, token and browser credential stores) plus `FilesystemScope` + `SensitivePathPolicy` + content-based secret detection/redaction, with user consent instead of silent access, and no Lua bypass.
  - The Lua API should be controlled requests (`agent.spawn`, `execution.run`, `panel.acquire`, `fs.read`), each entering one authorization path, rather than raw capabilities (`os.execute`, `io.open`); a pathological harness loop then receives `BudgetExceeded` repeatedly instead of taking the machine down.
  - Mechanism in Rust, organization model in Lua: Core knows Agent, Task, Grant, Budget, Delegation, Mailbox, Execution, and Lease — not Commander/Planner/Reviewer; team shapes (flat swarm, manager-worker, planner-executor-reviewer, debate, MapReduce, pair programming) are Lua concepts that update no Core.
  - The upstream deliverable is a primitive set (agent/task/delegation/capability/budget/execution/panel-lease/context/provider/mailbox primitives), not a fixed "Bitty Agent Harness"; the official `bitty-ai` Lua harness is one harness and community harnesses compose the same primitives, so no harness (infinite swarm, malicious or buggy plugin, runaway agent, wrong delegation) can cross the capability, budget, resource, secret, filesystem, privilege, execution, or lease boundaries.
  - User-layer rules split into what the system can technically prevent (deny, confirmation, redaction, ceilings) and user hygiene the system cannot control (a user pasting a password into chat), where the system only warns, redacts, avoids persisting, and avoids logging — security never depends on "the user should understand security".
