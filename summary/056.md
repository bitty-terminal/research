# 056 — Wheel Context Storage and Reasoning Management

- Status: Captured — conclusions not yet captured in any `*-docs` repo; destinations proposed below (owner-pending)
- Date: 2026-09-18 (archive receipt; the original discussion contains no explicit date)
- One-liner: Separate the stored history from the compiled model context — persist events, commit structured knowledge (rationale, decisions, evidence) instead of raw chain-of-thought, and let a context compiler build a small stable-prefix prompt, treating cache hit rate as one optimization rather than the goal.
- Background / Problem:
  - The owner asks how Wheel should store the AI side's context in a Git-like, structured way, and specifically whether the AI's own thinking and the user conversation also need to be persisted — long reasoning from one LLM is unwieldy, and a context fork/migration becomes expensive if everything is copied.
  - A second thread asks whether a tool call can carry a `reason`/why field recorded each time, whether a high cache hit rate equals doing the task well (e.g. dropping all prior thinking each call but keeping why a tool was called), how why/what/where/how storage should work, and whether cache-miss billing is really small.
- Key conclusions / Decisions:
  - Central distinction: **Wheel's stored history must not equal the next prompt sent to the LLM.** User conversation, tool calls, file operations, and agent decisions can be persisted long-term, but only a selected and compiled working set enters the model context window.
  - Three layers, mapped to Git: History / Object Store (`.git/objects`), Semantic State (`tree + commit`), Working Context (`index + worktree`). The object store holds messages, traces (tool call/result/output/file observation), reasoning records, artifacts, and context commits.
  - An agent's state is not `messages: Message[]` but a `ContextCommit { tree, parents, agent, model, timestamp, summary }` whose tree carries conversation, task state, reasoning state, knowledge, artifacts, environment, and agent graph.
  - Conversation is stored in full, but should not be a forced linear array: conversation itself may be a **DAG** (one user turn branching to multiple agents), which matches the intended agent-team graph rather than main-agent-plus-flat-subagents.
  - AI thinking must not be stored as raw chain-of-thought token text. Define a Wheel-controlled **Reasoning Record**: goal, observations, assumptions, hypotheses, decisions, rejected alternatives, uncertainties, next actions, and evidence — the portable, provider/model/session/machine/branch-independent object.
  - Two kinds of thinking: **Scratch Reasoning** (very short-lived, ephemeral, by default not committed) and **Reasoning Record** (long-term, committed). A stable conclusion becomes a record; in-progress musing is discarded.
  - Git commit semantics fit: commits are logically full snapshots of cognition but physically incremental (persistent data structure / structural sharing), so a fork only adds refs to shared objects and long thinking no longer makes forks heavy.
  - Context is generated by a **Context Compiler**: Object Store → Context Graph → Context Compiler → Prompt → LLM. Storage capacity and context-window size must be fully decoupled (a multi-GB Wheel repo yields a tens-of-kB prompt), exactly as a Git repo's size is unrelated to `git status` output.
  - Git mapping adopted as a design frame: Object DB→context object store, Blob→message/output/artifact, Tree→context tree, Commit→context commit, HEAD→agent current context, Branch→context branch, Tag→milestone, Index→prompt staging area, Worktree→agent live runtime, Reflog→context history, Stash→suspended context, Merge→context merge, Cherry-pick→import reasoning/task/result, Rebase→rebuild on new context, GC→context compaction, Clone→context migration.
  - **Context Index** is the staging area: it declares which objects enter the next inference (`wheel context status` shows staged goal/task/reasoning/files versus excluded messages/traces).
  - **Merge is semantic, not textual**: merging two agents concatenates no chat logs; it produces a merge commit with parents, records conflicting conclusions, the chosen resolution, the reason, and preserved evidence.
  - Introduce **Episode** as a working unit: trigger → events (action/observation/reasoning/decision) → optional outcome and reasoning record. Users see message-level turns; Wheel stores episode-level structure, which makes agent debugging tractable.
  - Provider-native reasoning state (reasoning IDs, encrypted state, continuation/cache handles) is stored as an optional opaque `ProviderState` object; Core never depends on it. Portable semantic context (ReasoningRecord/Decision/Observation/Task/Message) keeps `GPT → Claude` continuations possible while `GPT → GPT` may reuse native state.
  - **Cache hit rate is not task quality.** Optimization is a multi-objective function — task success, context relevance, latency, token cost, cache reuse, information preservation — never `maximize(cache_hit_rate)`. Actively shrinking unrelated context (raising cache miss, lowering token count and noise) can be the correct behavior; the guiding objective is `minimize(required_context) while preserving(required_information)`, then `maximize(cache_reuse)` as a second layer.
  - Name the durable form **rationale** (or intent), not `reasoning`, to avoid implying full chain-of-thought. Lifecycle: ephemeral LLM internal reasoning → decision boundary → structured Rationale (Why / What / Where / How / Expected / Observed / So-what / Next) → Context Object Store.
  - Make why/what/where/how a **tool-call standard protocol**: `Action { intent, call }` where `Intent { why, what, where, how, expected }` and `Outcome { observed, evidence, changed, implication, next }`. This is far richer than `{ tool, args }` and gives a machine-readable engineering log; the tool `reason` field plays the role of a Git commit message ("what changed and why").
  - A ~300-token structured rationale replaces ~15k tokens of raw thinking; the next model re-reasons from structured state instead of inheriting stale assumptions, reducing **reasoning inertia** and often improving quality.
  - Prompt-caching economics (2026): input is billed per token split into uncached (1×), cache read (commonly 0.1×), and cache write (Anthropic ~1.25× at 5-min TTL, ~2× at 1-hour; OpenAI usually no write surcharge; Gemini implicit ~10% plus explicit per-hour storage). Caching is **prefix-exact**, not semantic — stable material must lead and mutable material must trail, or everything after the first differing token is billed uncached. Cache only discounts input processing; output and context-window/TPM occupancy are unaffected.
  - Resulting prompt shape: `Stable Prefix` (core prompt, tool schemas, project rules, stable knowledge) + `Structured State` (goal, task, decisions, rationale, key observations) + `Dynamic Tail` (recent messages, latest tool results, current request) — getting cache friendliness, a cleaner and smaller context, and fresh re-reasoning at once.
  - Wheel telemetry should report context efficiency (input tokens, cached tokens, cache hit %, selected/excluded objects, compressed %, relevance estimate) rather than cache hit alone.
  - Guiding philosophy captured as: **Persist events, commit knowledge, compile context** — "Wheel does not need to remember every sentence an agent thought, only why it acted, what it did, what it found, and what cognition that changed," making Wheel an LLM-native versioned execution/cognition runtime rather than a chat session manager.

Terminal-side surfaces (panel history versus compiled context, fork of execution snapshots, event log) remain with the terminal documentation owner.
