# 035 — Decouple Image Protocols from the Appearance System

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-15 14:19
- One-liner: Image protocols are only image producers while appearance and compositing form an independent layered system.
- Background / Problem:
  - With the primary/secondary image-protocol route decided, its relation to transparency, blur, background, theme, and color-picking plugins needs clarification.
  - Window transparency, image transparency, and UI transparency are easily confused as one concept.
  - Whether to parse protocols in-house or bring in existing ecosystem dependencies needs a decision.
- Key conclusions / Decisions:
  - Understand rendering as layers: desktop, window background, terminal background, terminal graphics, text, and UI overlay.
  - Distinguish window-background transparency, image alpha transparency, and UI transparency instead of multiplying one alpha across the whole window.
  - Blur stays a platform window-backend capability and does not enter the graphics-protocol module.
  - Background images and terminal graphics protocols keep separate semantics but share image infrastructure such as decode and texture caches.
  - Mainstream graphics protocols with layered semantics fit the compositing model better; legacy protocols are parsed and then normalized.
  - The color-picking plugin faces only the theme system and recomputes palettes driven by background-change events.
  - Build a small in-house graphics-protocol module for production, borrowing only from existing implementations and specs; third-party libraries serve only as test senders.
  - Cursor color and opacity belong to the theme/appearance system.
