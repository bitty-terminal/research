# 050 — Portable Capabilities in .agents, Harness Behavior in .wheel

- Status: Captured — `bitty-ai`-owned conclusions distilled as a draft discussion synthesis in `bitty-ai-docs` (`specifications/research/research-distillation-050-051-bitty-ai.md`, accepted through PR bitty-ai#120, merged); captures in other corpora (Wheel configuration owners) not verified — treat remaining sub-conclusions as owner-pending
- Date: 2026-09-18 (archive receipt; the original discussion contains no explicit date)
- One-liner: Keep `.agents/` as the portable cross-harness capability layer describing what a project offers, and `.wheel/` as the Wheel-native harness control plane describing how Wheel should behave; the two coexist without overlap.
- Background / Problem:
  - Bitty (terminal/runtime platform) and Wheel (agent harness) scopes have diverged, so project-level agent behavior must stop masquerading as Bitty configuration.
  - `.agents/` content should stay migratable across harnesses, while `.wheel/` unlocks deeper harness-level behavior only when Wheel is in use.
- Key conclusions / Decisions:
  - `.agents/` is the interoperable discovery surface (skills, MCP, agent definitions: what capabilities exist); Wheel reads and supports it but never injects Wheel-specific machinery into it.
  - `.wheel/init.lua` is the single fixed contract; the remaining layout stays free-form Lua modules (the sketched commands, tools, agents, context, policies, hooks, and profiles groupings are organizational examples, not required directories).
  - Capability filtering heads the feature list: enable/disable allowlists over discovered skills and MCP servers feed a discovery-to-policy-to-resolver-to-compiler chain, directly addressing skill/MCP hell.
  - Context policy lets projects set budgets, pin or exclude paths, and tune retrieval through high-level policy APIs; users describe policy, never compiler algorithms, protecting cache stability, safety, and debuggability.
  - Structured rules and constraints (deny, require-confirmation, verify-on-change) sink into policy, permission, and verification runtimes so deterministic enforcement replaces long system-prompt rule lists and shrinks the core prompt.
  - Custom commands, provenance-tracked custom tools (native, Lua, MCP, and script tools unified as capabilities but internally distinguished by origin), and structured agent definitions (model, tools, skills, permissions per profile, driving compiler pruning) round out project extensibility.
  - Verification gates (per-change checks, targeted versus full tests, before-complete requirements) make task completion evidence-gated rather than model-asserted; hooks (task, tool, compile, spawn events) are tiered into safe, advanced, and unsafe levels so ordinary project config cannot break harness invariants.
  - `.wheel/` stores only committable configuration; runtime state, sessions, caches, and checkpoints live in platform state, data, and cache locations or other non-repository paths, never beside the config.
  - Executable project Lua demands trust-on-first-use from day one: never auto-execute project config on entering a repository; record path plus config hash, re-prompt on change, and offer capability inspection before trusting.
  - Sandbox `.wheel/` Lua behind Wheel-mediated APIs with declared deny-by-default permissions (project-scoped filesystem, controlled process, no ambient network), keeping project configuration auditable.
  - Load pipeline: project discovery from `.agents/` plus Lua config from `.wheel/` feed a capability resolver whose output enters the Context Compiler and Agent Runtime; `.wheel/` references, filters, constrains, and composes `.agents/` capabilities rather than duplicating skill or MCP stores.
