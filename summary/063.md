# 063 摘要：bitty-network 独立网络扩展（trimmed mirror of origin/063.md.completed）

thesis：`bitty-network` 是官方可选 Rust Core Extension / Runtime Service，不是基础 Core 强制部分。
默认纯终端 Bitty 保持 zero-network dependency；天气/GitHub/邮箱/Wheel Provider/远程控制复用同一套网络基础设施。
最硬 boundary：`bitty-core ≠ bitty-network ≠ bitty-ai`，即 L0 Core → L1 Rust Core Extensions → L2 Lua Plugins 三层模型。

## 1. bitty-ai 不拥有网络层
各插件自带 reqwest+rustls/tokio+quinn 会重复解决 TLS/proxy/DNS/cert store/timeout/连接池/HTTP2-3/WebSocket/auth/retry/rate-limit/streaming/cancellation。
Cargo 能去重同版本 crate，但去重不了多版本、多 runtime（tokio/async-std/smol）——而那还不是重点。

## 2. 真正价值：统一 networking runtime + policy（> 依赖去重）
最大坑是每插件自建 Tokio Runtime → threads/timers/DNS/连接池/TLS session 全重复。
bitty-network 提供共享 async runtime + HTTP 连接池 + DNS 缓存 + TLS session 缓存 + proxy 设置。

## 3. 拆两个 crate
- `bitty-network-api`：极轻（Request/Response/Error/Stream/WebSocket API/capability 定义/service trait），不依赖真实 HTTP/TLS 实现。插件只依赖它，经 IPC/service lookup 到实现；不知道 reqwest/hyper/rustls/quinn 是否存在。
- `bitty-network`：真实现（async runtime/HTTP client/TLS/DNS/proxy/WebSocket/连接池/streaming/policy）。

## 4. Lua 插件
`local net = bitty.network; net.get{url=...}` → Lua API → -api → Rust 实现。Lua 不管 socket/TLS/runtime/cert/proxy。

## 5. 统一权限模型（最大额外价值之一）
manifest `[permissions.network] hosts=[...]` → Network API → Capability Check → 实现。插件禁 `socket()/connect(anywhere)`。
Bitty 知道谁在联网、连哪里、为什么；未来可做 Network Inspector（插件×host 流量表）。各插件自带 reqwest 则无法统一实现。

## 6. Proxy/TLS 各配一次
`[network] proxy` 全员继承（Wheel/GitHub/Weather/Mail/Remote），统一处理 HTTP_PROXY/HTTPS_PROXY/NO_PROXY/system proxy/PAC。
TLS 统一 provider（system cert/custom CA/client cert/policy），backend 可换（rustls/native/platform）而上层 API 不变。

## 7. Wheel 变干净
Wheel 只留 Agent/Context/Tasks/Tools/Provider 抽象/UI；network/HTTP/TLS/WebSocket 不属于 Wheel。
OpenAI Provider Plugin → LLM Provider API → bitty-network → api.openai.com；无 Wheel 时 GitHub/Weather/Remote 照用同一网络层。

## 8. Remote 区分：不是 reqwest wrapper
Remote 要 TCP/QUIC/WebSocket/WebRTC/local discovery/NAT 穿透/multiplexing/文件传输。
`bitty-network = runtime + transport(TCP/UDP/QUIC) + protocol(HTTP/WS) + TLS + DNS + policy`；
HTTP 插件走 HTTP 层、Remote 走 transport 层、Wheel 走 HTTP/WS 层。

## 9. feature 分层（默认全关）
client/server/http/websocket/quic/proxy/oauth。天气只要 client+http；Wheel 要 client+http+websocket；Remote 要 server+quic。
默认 `bitty` 完全不启用，不为天气插件把 Remote Server 编进去。

## 10. 运行时可选 ≠ 编译时可选（三方案）
A. 编译时 feature（最简单，需不同 build）；B. 动态库（Rust 无稳定 ABI，插件兼容麻烦）；
C. 独立 `bitty-networkd`（Bitty 经 IPC 连接；没装则 `bitty.network unavailable`，最干净）。
折中推荐：轻 Network API + Service Bridge，MVP 先 embedded backend，日后按需 external networkd，API 不变。

## 落地
- crate 关系：bitty-core 下挂 bitty-network-api（轻接口），bitty-network（可选扩展）提供 HTTP/WS/Transport，消费者 Wheel/GitHub/Remote/Weather/Mail。
- 同类 L1 扩展可复用模式：bitty-media / bitty-browser / bitty-devtools / bitty-remote（比 Lua Plugin 更底层、不污染最小 Core 的 Rust Extension）。
