# 019 — Git Submodules and Multi-Repository Documentation Layout

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-14 01:03
- One-liner: Compose multiple repositories with submodules, isolate ownership per repository, and keep an integrated development experience in the workspace.
- Background / Problem:
  - Terminal, plugin, and AI work proceed in parallel, and a single repository couples branches, pipelines, and context too tightly through sharing.
  - Code repositories should still conveniently show their matching documentation with reproducible version binding.
  - Workspace, submodule, subtree, and monorepo approaches need clear applicability boundaries.
- Key conclusions / Decisions:
  - Submodules reference a fixed commit of another repository rather than a branch, giving reproducibility by construction; language workspaces and Git organization live on two different levels and do not replace each other.
  - Clones must recursively initialize submodules; updates advance inside the submodule first, then record the pointer change back in the parent repository.
  - Split repositories only when an independent lifecycle plus exact version referencing is needed; closely linked code and documentation should not be split merely for the sake of splitting.
  - Recommend three standalone documentation repositories, each mounted as a documentation submodule directory inside its matching code repository.
  - Keep one unified documentation repository as an aggregator, likewise referencing the three documentation repositories through submodules, forming a directed-acyclic reuse shape without recursive nesting.
  - This structure gains domain isolation, independent commits and releases, an integrated directory during development, and exact binding between code versions and documentation commits.
  - A multi-agent workspace can register parent and submodule paths as separate repositories and automatically recognize cross-project boundaries.
