# 061 — Bitty Remote: Unified Remote Infrastructure and the Remote Client

- Status: Captured — conclusions not yet captured in any `*-docs` repo; destinations proposed below (owner-pending)
- Date: 2026-09-21 (archive receipt; the original discussion contains no explicit date)
- One-liner: Position the Bitty Remote Client as the remote frontend of Bitty's Workspace/Panel/Agent architecture — React Native + Expo over a shared Rust remote core, a four-layer Panel Remote Protocol with semantic-first cell and UI-tree diffing (pixel streaming only as fallback), and a unified Remote Infrastructure (device identity, capability grants, rendezvous/relay transport) serving panels, files, agents, and notifications with an optional, never mandatory, Bitty Cloud.
- Background / Problem:
  - The owner asks how a mobile/iPad Bitty client should be built and what backend infrastructure it needs: which stack (React Native + Expo + Rust core versus Flutter versus Tauri Mobile) and how to treat references such as RustDesk, File Browser, and ntfy.
  - The hard problem is not the app framework but the protocol: "how does a Panel travel over the network to another device?" — panels are far more than shell stdout, so raw stream forwarding or pixel streaming alone are wrong primitives.
  - The owner requires the network-dependent part to be Rust Core, not Lua Core: plugins should consume remote capabilities, never build transport, identity, or traversal themselves.
- Key conclusions / Decisions:
  - **Remote frontend, not another terminal.** PTY, shell, agents, and plugins stay on the host Bitty; the device presents panel state and sends input and control. The iPad form (workspace sidebar, panel area, custom key bar, hardware keyboard/trackpad) may be the most valuable configuration; no LLM runs on the device.
  - **Stack: React Native + Expo app shell, Rust shared core.** Panel rendering starts with React Native Skia (GPU canvas, immediate-mode `Picture` drawing) and can later move to a native view over the shared Rust/wgpu renderer; a `bitty-remote-core` Rust library owns protocol, codec, crypto, state sync, and reconnect. Flutter is rejected (no reason to add a second ecosystem); Tauri Mobile suits companion tooling, but WebView is not the first choice for high-interactivity panel surfaces (terminal grid, IME, selection, high-frequency diffs).
  - **Panel Remote Protocol, four layers.** Control (open/close/focus/move; workspace and panel lists, attach/detach/focus/resize, subscribe/unsubscribe — sharing concepts with the accepted local IPC), Input (key/text/mouse/touch), Panel State (grid/UI tree/cursor), and Transport (WebSocket now, QUIC later).
  - **Semantic-first rendering; no screenshot-by-default.** Terminal panels sync as a first-connection `PanelSnapshot` (cells, cursor, scrollback position, title, cwd) followed by sequenced `PanelDiff` operations (update cells, move cursor, scroll, set title); reconnect resumes from the last sequence or requests a fresh snapshot. Plugin panels travel as declarative UI-tree diffs that the client rebuilds locally. Rendering modes: cell/grid diff, UI-tree diff, asset plus metadata; frame/video pixel streaming is only the fallback for renderers that cannot be structured. New constraint on the UI framework: Bitty UI should be renderable and serializable/remoteable.
  - **Transport: WebSocket MVP, iroh/QUIC target, swappable behind a trait.** The MVP uses WebSocket + TLS (universal support, easy debugging); the formal target is `iroh` 1.x (public-key-identified P2P QUIC bundling device identity, NAT traversal, and relay fallback) with QUIC multi-stream multiplexing so file transfers never add panel latency. Do not hand-build a RustDesk-style rendezvous/relay pair; borrow the topology (direct P2P preferred, rendezvous discovery, relay fallback) but not the screen-streaming abstraction. Transport stays panel-agnostic.
  - **Unified Remote Infrastructure, not a panel-only backend.** Panel is the first consumer; device identity, connection, permissions, transport, relay, and an event system are shared by services multiplexed over one authenticated session: panel, filesystem, agent, workspace, notification, clipboard, and plugin, addressed RPC-style (service + method + parameters).
  - **Capability-first device security.** A device receives explicit capability sets (panel read/input/create/kill, workspace read, scoped filesystem read/write, agent read/command, clipboard, notification subscribe) granted on first connection and revocable at any time; sensitive locations (keys, credential, and secret stores) are denied from day one. This is remote-control infrastructure for a computer, so the security boundary is designed first.
  - **File service.** A native capability-scoped file service (stat / read_dir / offset-based read / offset-based write) under the same grant model. File Browser is a product/API reference only, not a dependency: it was archived upstream on 2026-09-01 with unresolved security issues, and Bitty's implementation is simple enough to own.
  - **Notification service, two layers.** Online devices receive events directly over the remote session; offline devices need the platform push gateways (APNs / FCM), the same two-layer split ntfy documents. The Bitty event bus feeds the notification service, which serves both the remote app and plugins.
  - **Bitty Cloud is optional.** Discovery, relay, and push gateway are optional infrastructure; official service, self-hosting, LAN-only, and VPN-only must all work, and Core must never depend on a Bitty Cloud. LAN operation needs no server (mDNS/local discovery, QR pairing); rendezvous and relay enter only for NAT-ed internet paths.
  - **Plugin participation boundary.** Network implementation remains in Rust Core; selected capabilities are exposed to Lua (for example `bitty.notify.send` and `bitty.remote.publish`), and plugins remain unaware of QUIC, relay, push, and traversal — the same mechanism/policy split as the rest of Bitty.
  - **Experiments, transport first.** `remote-transport` (iroh/QUIC/NAT/relay), then `remote-panel` (snapshot + diff + input + reconnect over WebSocket + Expo + Skia), then `remote-files` (list/read/write/chunk), and later `remote-notify`. The panel experiment is also the acceptance test of the Panel abstraction: a panel that can be rebuilt, controlled, and migrated on a different device becomes a first-class compute and interaction entity.
