# 053 — Public Plugin Contracts and Layered Lua Frameworks

- Status: Captured — archive summary prepared; canonical documentation capture has not been independently verified. The [original record](../origin/053.md.completed) is byte-identical; only the `.completed` suffix changed (owner directive 2026-09-18).
- Date: Unspecified — the original discussion contains no explicit date.
- One-liner: Keep private Lua imports inside a plugin, compose plugins through declared versioned public contracts, and grow optional frameworks above a narrow Lua SDK rather than another monolithic core.
- Background / Problem:
  - The discussion asks how Lua plugins in separate repositories should call each other, whether they need wrappers, and whether reusable UI and other framework plugins can sit between Rust mechanisms and user applications.
  - Importing another plugin's source by relative path or modifying the module search path couples consumers to repository layout and implementation details, undermining versioning, replacement, lazy loading, permission mediation, and potential process separation.
- Key conclusions / Decisions:
  - **Private modules versus public contracts:** ordinary `require()` is appropriate for private modules inside one plugin. Cross-plugin consumers should use declared public services or mediated proxies, not reach into another repository's source. Repositories are publication boundaries; versioned service contracts are architectural boundaries. Later framework-import sketches do not establish an exception for private cross-plugin imports.
  - **Typed and schema-backed SDK contracts:** explicit request, response, and event shapes, versioning, and Lua tooling/type hints should make contracts checkable rather than relying on undocumented tables. A service interface can have multiple conforming implementations; consumers should not depend on the provider's repository layout or implementation language.
  - **Distinct dependency kinds:** a package dependency requires installation of a particular plugin; a service requirement needs a compatible provider of an interface. Keep these declarations distinct so an official, user-supplied, or other authorized provider can be substituted without rewriting consumers. A declared service requirement is not itself a permission grant.
  - **Location transparency is a proposal, not fake synchrony:** a common service-facing abstraction could mediate same-runtime and cross-process calls. Local shortcuts must not bypass enforcement or pretend remote calls are ordinary synchronous calls that can block the UI/event loop. The record proposes async-first calls and standardized streaming; any accepted contract must also explicitly define cancellation and lifecycle behavior. Its await, promise, coroutine, callback, and stream-iteration spellings are alternatives in discussion, not accepted SDK methods or evidence of runtime support.
  - **Four layers:** Rust enforcement and mechanisms → narrow public Lua SDK → replaceable, optional framework plugins → application/user plugins. Rust is suited to performance-sensitive, platform-specific, correctness-critical mechanisms such as rendering, font shaping, input/IME, scheduling, and resource lifecycles. Lua composes widgets, layouts, themes, dashboards, workflows, and user-facing policy within enforced authority boundaries.
  - **Small core and SDK:** retain only justified, stable public abstractions in the SDK; do not grow a heavy second “Lua Core.” Ordinary plugins must not bind to raw Rust internal APIs. Frameworks can evolve separately while public contracts insulate consumers from changes to host internals; this is a design aim, not an unconditional compatibility guarantee.
  - **Optional competing frameworks:** UI components and higher-level composition can live in independently versioned plugins rather than a mandatory official UI framework. Reactive, immediate-mode, terminal, canvas, and dashboard-oriented approaches are illustrative alternatives, not approved packages, APIs, or an implementation roadmap.
  - **Wheel and AI illustrations remain owner-pending:** model/provider abstraction, normalized streaming across providers, tool schemas and registries, context/memory, workflows, and multi-agent orchestration illustrate reusable framework layers. User-defined tools would be discovered through public registration rather than source location. These examples belong to the relevant Wheel and AI owners outside this dispatch; they do not establish Wheel ownership of model infrastructure, accepted tool/provider interfaces, or a new agent lifecycle.
  - **Authority and lifecycle take precedence:** accepted security requirements and lifecycle schemas override the record's speculative service methods, coroutine/stream interfaces, custom event vocabulary, and lists of SDK facilities. Process execution, agent spawning, IPC, networking, and credentials are illustrative mechanism needs, never ambient access or authorization. Framework wrappers cannot bypass host enforcement. Provider stream normalization must reconcile with the owning canonical event schema rather than install the sample event names as a competing protocol.
