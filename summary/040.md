# 040 — Plugin Taxonomy, Extension Points, and the Plugin Graph

- Status: Captured in part (plugin direction recorded in `bitty-plugins-docs`; original kept unrenamed for the terminal direction)
- Date: 2026-09-16 12:35
- One-liner: Plugins form a graph of dependency, service, and extension relations; every plugin may be an application, and every application may expose its own extension platform.
- Background / Problem:
  - A single "plugin" label covered very different things: pure capabilities, background services, UI widgets, full applications, and panel providers.
  - Whether extension platforms could nest (a plugin hosting its own Lua VM) risked a runtime tree that multiplies isolation and capability surfaces.
  - Dependency declarations risked becoming an escalation channel: a plugin could demand capabilities through what it depends on rather than through its own manifest.
  - There was no accepted way to express extension points and contributions in a manifest, nor a versioning model for extension-platform APIs.
- Key conclusions / Decisions:
  - Taxonomy: Plugin, Service, Widget, Application, and Panel Provider; a _platform plugin_ is a plugin that hosts its own extension platform (for example Bitter, Bitty AI, Statusline, Docker).
  - Runtime stays flat while semantics layer: explicitly no nested Lua VMs; relations are dependency, service, extension-point, and contribution, and the plugin graph is a relation graph, not a process tree.
  - Extension points are first-class: each platform plugin publishes an inventory (Bitter: `bitter.language/highlighter/formatter/completion/code_action/status_item/sidebar`; Bitty AI: `bitty-ai.model/tool/context/memory/compactor/agent/command/ui`; Statusline: `statusline.segment`; Docker: `docker.action/renderer/inspector`).
  - Candidate manifest shapes (`[contributes] extensions = [...]` and `[[extensions]] point = ..., id = ...`) remain unaccepted proposals; the accepted dependency declaration stays `[dependencies]`.
  - Dependency must not become capability escalation; capabilities stay explicit and deny-by-default per isolation and resource rules.
  - Extension-platform APIs are versioned (for example `bitter.editor@1`, `bitty-ai.tools@1`, `bitty-ai.context@2`).
  - Recorded principles: "Every plugin may be an application, and every application may expose its own extension platform" and "Bitty extends plugins; plugins extend ecosystems"; Bitty must not become a kernel.
- Destination: bitty-plugins-docs (`specifications/plugin-ecosystem-model.md`), bitty-ai-docs
- Open items: Contribution manifest shapes are unaccepted; the extension-platform API versioning contract is not yet accepted.
