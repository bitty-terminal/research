# 054 — Bitty Plugin Package Management with Lux for Lua Dependencies

- Status: Open — conclusions not yet captured in any `*-docs` repo; destinations proposed below (owner-pending)
- Date: 2026-09-18 (archive receipt; the original discussion contains no explicit date)
- One-liner: Bitty owns its plugin package manager (lifecycle, permissions, services, compatibility) while Lux serves only the Lua dependency layer at development and packaging time, producing self-contained installable plugin artifacts.
- Background / Problem:
  - Plugin-management UX should unify under one entry point, but equating the Bitty plugin system with the Lux Lua package manager conflates two different package kinds with different lifecycles and dependency graphs.
  - Bitty plugins carry lifecycle, permissions, services, panels, UI, and compatibility concerns; plain Lua packages carry only sources, resolution, semver, and lockfiles.
- Key conclusions / Decisions:
  - Keep two graphs behind one CLI: the Bitty plugin graph (managed by Bitty) and the Lua package graph (resolved with Lux tooling); users see unified install/update/remove/list commands without knowing which resolver runs underneath.
  - Use Lux as reference and build-time backend (manifest, lockfile with integrity, git/local/workspace dependencies, vendoring, LuaRocks compatibility, semver resolution) but do not equate the systems or take a hard runtime ABI dependency on its pre-1.0 embedding API.
  - Own the runtime module loader: the host implements a resolver chain (plugin-local, plugin dependencies, framework packages, stdlib, vendored libraries) over the sandboxed Lua runtime, banning native extensions and C loading rather than emulating a full traditional Lua runtime.
  - Ship self-contained plugin artifacts (manifest, Lua sources, vendored pure-Lua dependencies, assets) with dependencies pre-resolved, favoring reproducibility, startup speed, security, offline install, sandboxing, and version consistency over on-device resolution.
  - Confine Lux to development and packaging (declare, resolve, vendor, pack) so end-user installs need no Lux toolchain — a build-time versus runtime split.
  - Admit only a defined sandbox-compatible Lua dependency subset (pure Lua, no native code, no arbitrary process execution or dynamic native loading); reject native dependencies at the manager level and route native needs (e.g. storage) through host Rust services.
  - Define a Bitty-owned plugin manifest (identity, entrypoint, host/harness compatibility, provided and required services, plugin dependencies, permissions) separately from the Lua dependency manifest; no mega-manifest across abstraction levels.
  - Unify the CLI (add, update, sync, doctor, list, enable/disable, info, permissions) over internal resolve, verify, unpack, register, and loader-configure steps; keep two lock levels (user-side plugin lock plus build-side Lua lock baked into the artifact).
  - Never let project composition files auto-install or execute plugins on entering a repository: declarations prompt for explicit user trust first — a supply-chain boundary analogous to the `.wheel/` trust rule.
  - Final three layers: Bitty-implemented Plugin Manager, host-controlled Lua Resolver (Lux at build time), and Service Registry for plugin wiring over the Lua runtime — keeping host network dependencies out of install/resolve paths and positioning the plugin registry and index as the distribution point.
- Destination: proposed owner-pending — plugin-manager ownership, manifest and permission model, and resolver/loader boundaries to the core/plugin documentation owners; Lua subset and build-time Lux flow to the SDK and packaging owners; registry and index role to the plugin-ecosystem owners.
