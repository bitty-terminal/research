# 060 — Phodopus: Piccolo Successor Runtime Strategy and Architecture

- Status: Captured — conclusions not yet captured in any `*-docs` repo; destinations proposed below (owner-pending)
- Date: 2026-09-20 (archive receipt; the original discussion contains no explicit date)
- One-liner: Fork Piccolo as an independent sandbox-first Lua successor runtime (`Phodopus`): decouple generic VM, modular stdlib (`require`, patterns, utf8), memory quotas, and runtime-agnostic async bridges from Bitty's Host ABI, absorbing mature upstream PRs across a 6-phase roadmap.
- Background / Problem:
  - An in-depth evaluation of Piccolo reveals that while its core stackless VM, memory safety, microsecond cold start (~35 µs), and Fuel mechanism are sound, it is an incomplete micro-engine rather than a production-ready runtime.
  - Crucial features required by Bitty's plugin and UI ecosystems are completely unimplemented upstream: module loading (`require`, `package.*`), string formatting (`string.format`), pattern matching (`find`, `match`, `gsub`), Unicode support (`utf8.*`), error stack traces (`debug.traceback`), real Tokio async I/O, and hard memory allocation quotas.
  - While Piccolo upstream has ~29 open PRs addressing many of these gaps (e.g. PR #128 for `string.format`, #129 for pattern matching, #110 for `utf8`, #121 for backtraces), governance and merge throughput have stalled.
  - The owner asks whether Bitty should maintain in-tree vendor patches or fork Piccolo into an independent, hamster-themed successor project to create a comprehensive sandbox-first Lua runtime.
- Key conclusions / Decisions:
  - **Independent Successor Fork over In-Tree Vendor Patches**:
    - Avoid maintaining a fragmented in-tree "monster patch" inside Bitty.
    - Establish an independent, reusable open-source runtime with its own identity, preserving MIT/CC0 attribution and upstream commit history.
  - **Naming: `Phodopus` (Hamster Genus)**:
    - Named `Phodopus` (the dwarf hamster genus), harmonizing with Bitty's hamster theme (`Bitty` -> `Bittie` mascot -> `Wheel` agent harness -> `Phodopus` runtime) while standing independently alongside Rust infrastructure crates like `Tokio`, `Wgpu`, `Winit`, and `Serde`.
  - **Strict Boundary: Generic Lua Runtime vs Bitty Host ABI**:
    - Do not bake Bitty-specific APIs or Tokio dependencies directly into the VM core.
    - Modular crate architecture for `Phodopus`:
      - `phodopus-core`: Pure VM, bytecode compiler, `gc-arena`, coroutines, Fuel, executor.
      - `phodopus-stdlib`: Standard libraries (`string`, `table`, `utf8`, `math`).
      - `phodopus-module`: `require`, searcher chains, VFS resolver, `package.loaded`.
      - `phodopus-debug`: Stack trace formatting, source locations, debugger hooks.
      - `phodopus-sandbox`: Hard memory quotas, Fuel budgets, cancellation, resource accounting.
      - `phodopus-async`: Generic runtime-agnostic suspend/resume operation bridge.
    - Bitty-specific Host ABI (`bitty-lua`: `bitty.ui`, `bitty.panel`, `bitty.fs`, `bitty.command`) sits strictly on top as a consumer.
  - **Runtime-Agnostic Async Bridge (No Hardcoded Tokio in Core)**:
    - Piccolo's `async_callback.rs` uses a NOOP waker and panics if an external future is `.await`ed.
    - `Phodopus` decouples async execution: VM yields a typed `HostOp::Pending(handle)` to the host trampoline. The host adapter (Tokio or async-std) drives the future and resumes the Lua coroutine (`thread.resume`) upon completion.
  - **Sandboxed Module Resolver (`require`)**:
    - `require("mod")` executes through a pluggable searcher chain: preloaded modules -> embedded modules -> VFS searcher -> host resolver.
    - Bitty binds `PluginVfsSearcher` and `LuxPackageSearcher` under its capability model, preventing arbitrary host filesystem traversal.
  - **Native Lua Patterns & Unicode Separation**:
    - Reject mapping `string.match` directly to the Rust `regex` crate; review and adapt upstream PR #129 to preserve authentic Lua pattern semantics.
    - Separate standard Lua `utf8.*` (code points) from terminal typography (`bitty.text.width`, graphemes, East Asian Width via `unicode-width` and `unicode-segmentation`).
  - **First-Class Sandboxing with Hard Memory Quotas**:
    - Elevate `Phodopus` beyond basic Lua: integrate runtime limits into the builder API (`Runtime::builder().memory_limit(16 * MIB).fuel_limit(100_000)`).
  - **Six-Phase Fork Roadmap**:
    - Phase 0: Fork Piccolo, preserve git history and MIT/CC0 attribution, establish upstream tracking remote.
    - Phase 1: Review and absorb mature upstream PRs (#128 `string.format`, #129 patterns, #110 `utf8`, #121 `traceback`, #130/135 diagnostics).
    - Phase 2: Build `package` / `require` module resolution and standard library gaps.
    - Phase 3: Implement hard memory quotas, Fuel policy, and capability sandboxing.
    - Phase 4: Generic async bridge with optional Tokio host adapter.
    - Phase 5: Integrate into Bitty Core via `bitty-lua` Host ABI.
- Destination: proposed owner-pending — Phodopus runtime integration plan, module resolution (`require`) specification, and Lux dependency binding to the plugin ecosystem documentation owner (`bitty-plugins-docs`); `bitty-lua` Host ABI layer, Tokio async trampoline bridge, and terminal text layout vs `utf8` distinction to the terminal platform documentation owner (`bitty-terminal-docs`); toolchain and runtime dependency governance adopting `Phodopus` as an independent sibling project under MIT/CC0 to cross-cutting governance (`bitty-docs`).
