# 030 — Runtime Dependency Boundary Planning

- Status: Open (not yet recorded in *-docs, follow-up needed)
- Date: 2026-09-15 01:00
- One-liner: Keep kernel minimal, third parties only in adapters.
- Background / Problem:
  - Pure-standard-library runtime is correct; do not pull async and network stacks early for convenience.
  - Models, external protocols, code intelligence, and persistence genuinely need third-party power, which pollutes the kernel without planning.
  - Some new dependencies need a higher toolchain than the current baseline, so upgrade strategy comes first.
- Key conclusions / Decisions:
  - Keep the runtime network-free and near standard-library only long term; async, request, and transport code lives only in providers and adapters.
  - Model providers use mature async and request stacks, starting as one package with many modules and splitting later by release rhythm.
  - External protocols prefer official SDKs without hand-rolled handshakes or transports; baseline gaps are solved with standalone adapters or whole upgrades.
  - Tool parameters derive schemas from types with validate-then-convert, authorizing before dispatch.
  - File scanning, syntax parsing, language services, fingerprinting, and diffing each reuse existing ecosystem crates, focusing custom work on sharing and authorization semantics.
  - Avoid persistence for now; when local single-process storage is truly needed, prefer lightweight embedded options.
  - Explicitly distinguish protocol identity from runtime instance identity in naming to avoid same-name export confusion.
  - Evolve packaging along dependency boundaries, stabilizing interfaces first and splitting only when real external dependencies appear, avoiding premature fragmentation.
