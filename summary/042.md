# 042 — Cross-Platform Dependencies and Release Compatibility

- Status: Captured (draft capture in bitty-docs, PR bitty-docs#315 open — not merged)
- Date: 2026-09-16 17:50
- One-liner: Separate source, build, and runtime dependencies; keep Core network-free behind a dependency firewall; own release compatibility because winit/wgpu cannot.
- Background / Problem:
  - With `bitty-ai` joining, HTTP/TLS/async/JSON stacks could sink into the terminal core through shared crates, and the team asked whether repeated `reqwest`/`tokio` dependencies should be deduplicated by a shared wrapper crate.
  - The workspace already owns external dependencies cleanly (19 crates, `bitty-core`/`bitty-ipc` dependency-free), but no written policy governs version unification, feature locality, or dependency islands.
  - The release pipeline builds cross-platform binaries, yet distribution compatibility (glibc/musl, ARM64 matrix, package runtime dependencies, GPU/driver baselines) is not yet systematically managed; winit and wgpu solve API portability, not ABI or distribution compatibility.
- Key conclusions / Decisions:
  - Distinguish source/download reuse, build-artifact reuse, and the final binary: Cargo's resolver already shares one crate version across the graph, so wrapper crates created only to avoid duplicate dependencies are unnecessary; duplicated transitive versions in `Cargo.lock` (for example `bitflags`, `windows-sys`) come from winit/wgpu/crossfont/arboard/image/portable-pty and must not be force-unified to zero.
  - A shared crate such as a future `bitty-net` is justified only when shared network policy is needed (proxy, TLS policy, timeout, retry, auth, offline mode, telemetry), never for dependency deduplication.
  - Dependency policy: a Core dependency budget; feature locality (AI dependencies stay in `bitty-ai`, Lua in the plugin host, network only in crates that genuinely need it); and `[workspace.dependencies]` for unified versions and feature policy.
  - Treat "Core never gains a network dependency because of AI, cloud, or registry" as an architecture invariant that refines the accepted DIR-016/DIR-017 no-initiate boundary.
  - Establish a `bitty-ai` dependency island: network, TLS, async runtime, JSON, SSE, MCP, and provider dependencies must not flow down through `bitty-runtime` into terminal crates.
  - Propose a five-layer dependency firewall: L0 `bitty-core`/`bitty-vt`/`bitty-ipc`/`bitty-package` (no GUI/GPU/network/AI); L1 `bitty-term-state`/`bitty-ui`/`bitty-config` (domain dependencies only); L2 `bitty-platform`/`bitty-render`/`bitty-pty`/`bitty-lua` (own one external subsystem each); L3 `bitty-runtime`/`bitty-plugin-host`/`bitty-rich` (composition); L4 `bitty-ai`/`bitty-app` (capabilities and composition root).
  - Five immediate actions: add `[workspace.dependencies]` (starting with winit and pollster); verify whether `bitty-app -> bitty-perf` is a real production edge; remove the `bitty-term-state` <-> `bitty-ui` dev-dependency cycle long term; create the `bitty-ai` dependency island; add CI dependency governance (`cargo tree --duplicates` informational only, `cargo-deny` for licenses/advisories/bans).
  - Static versus dynamic linking: Bitty's own crates are statically linked; the system boundary still uses dynamic libraries. `winit` absorbs window/input API differences and `wgpu` GPU backends, but Bitty itself must manage minimum OS versions, minimum glibc, musl support, GPU/driver baselines, font packaging, package runtime dependencies, signing, and real-machine testing.
  - Release pipeline defects observed: the Linux `aarch64-unknown-linux-gnu` target has dormant cross logic but no matrix entry; the Alpine `.apk` is packaged from the glibc binary and needs a separate musl/Alpine build; `nfpm.yaml` declares no runtime dependencies (fontconfig/freetype), unlike the Arch `PKGBUILD`. These match DIR-020 items 1, 2, and 4.
  - Define three-layer compatibility with a responsibility split: architecture (x86_64/aarch64) and OS/ABI (Linux GNU/musl, Windows MSVC, macOS Darwin) belong to release CI; window backend (Wayland/X11/Win32/AppKit) belongs to winit; GPU backend (Vulkan/DX12/Metal/GL fallback) belongs to wgpu.
  - Keep the "platform difference funnel": 90%+ of Bitty code must not know the OS, and `#[cfg(...)]` stays confined to `bitty-platform`, `bitty-pty`, `bitty-package`, and a few native integration points; abstract common semantics rather than flattening differences, as `bitty-pty` already does for Unix PTY versus ConPTY.
  - IME and fonts follow a four-stage path: wrapper (winit IME, crossfont) -> compatibility layer -> conformance suite -> extract a standalone crate only after real use; fix upstream first (for example a winit Wayland text-input bug) instead of forking; Core knows only semantic types (`Preedit`, `Commit`, `CursorRect`, `FontFace`, `GlyphRun`, `CellMetrics`, `RasterizedGlyph`, `Capabilities`). Do not build two large cross-platform crates simultaneously.
- Destination: bitty-docs (`docs/development/platform-compatibility.md` draft capture and DIR-024 register row, bitty-docs#315), refining DIR-020 release distribution in bitty-terminal-docs; `bitty` release-matrix execution stays with the DIR-020 tasks
