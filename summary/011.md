# 011 — Native Agent Runtime and Lua Safety Boundary

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-13 02:11
- One-liner: Borrow ideas from CarryCtx while growing native Bitty task and agent services, keeping Lua to policy and Rust to capability enforcement.
- Background / Problem:
  - CarryCtx and ctxctl validated useful abstractions for tasks, dependencies, and context, but an in-process agent shelling out to a CLI takes a detour.
  - Open questions remain on whether a project config directory should exist, whether agents only do coding, and where the IPC and Lua capability boundaries lie.
- Key conclusions / Decisions:
  - Do not depend permanently on an external CLI; split into native services such as Task, Agent, Workspace, Context, and Evidence, expose them to agents as Tools, and share the lower-level Rust services between CLI and Tools.
  - Place project declarations in `.bitty/` (agents, workflows, prompts, policies, tools, skills); keep runtime state in separate repo-local and user-level directories, tolerating `.agents/` without creating a dual source of truth.
  - Keep Role, Model, Capability, Tool, and context policy orthogonal, with per-task model routing; define an Agent as the combination of identity, role, policy, capability, routing, memory, workspace, tools, and lifecycle.
  - Structure growth into four levels — observation, memory, recipe, skill — plus policy proposals; proposals require policy-engine approval and agents must never self-escalate capabilities.
  - Lua owns configuration, panels, agent definitions, workflows, event hooks, prompts, and UI behavior; the trusted Rust core owns terminal, rendering, composition, IPC transport, auth, quotas, sandboxing, and persistence.
  - Secure Lua disables io, os, debug, loadlib, and similar by default, reaching files, processes, and network only through capability-checked controlled APIs; hot paths and per-unit callbacks stay out of Lua and receive only aggregated semantic events.
  - Upstream should provide correct semantic primitives first rather than finishing every plugin; panels can be seen as visual projections of IPC endpoints, and IPC will become the main line for agent collaboration.
  - Write three RFCs first — capability model, Lua host API, and IPC principal model — before expanding agents and plugins.
