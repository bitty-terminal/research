# 002 — Panel App Container and IPC Infrastructure

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-08-30
- One-liner: Panels as first-class app containers, IPC as the unified extension protocol.
- Background / Problem:
  - A terminal with only split PTY cannot host browser, file management, mail, chat, IDE, and similar capabilities.
  - Plugins, external programs, agents, and multiple instances lack a unified controllable communication channel.
  - The long-term shape needs alignment with Neovim-style composability and Hyprland-style composable layout.
- Key conclusions / Decisions:
  - Panel is defined as a first-class UI container: terminal, files, Git, browsing, and AI chat are all Panel implementations.
  - Panels share a unified lifecycle; Panels can communicate and compose into new applications.
  - Long-term shape is fixed as a programmable terminal workspace, not a terminal with more features.
  - API stability priority order: Panel, Workspace, Layout, Command, keybinding, Event, Capability, Service, Widget, Plugin.
  - The ecosystem ceiling is decided by Panel, Event, Command, and Capability together.
  - IPC serves Automation, Plugin, Agent, CLI, and integration under one shared protocol.
  - Any program can control Bitty via IPC; shell scripts can drive workspaces and notifications directly.
  - Plugins support process isolation and multiple languages, without forcing one process or one language.
  - Adopt a request plus event dual model, layered with Capability checks.
  - Browser Panels need extra caution on security and cost.
- Destination: bitty-terminal-docs, bitty-plugins-docs (Panel, workspace, IPC, and capability model split across both)
- Open items: None
