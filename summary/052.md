# 052 — Wheel Plugin Decomposition: Kernel, Plugins, Distribution

- Status: Partial — `bitty-ai`-owned conclusions distilled as a draft discussion synthesis in `bitty-ai-docs` (`specifications/research/research-distillation-052-bitty-ai.md`, accepted through PR bitty-ai#122, merged); captures in other corpora (Wheel architecture, plugin-ecosystem owners) not verified — treat remaining sub-conclusions as owner-pending
- Date: 2026-09-18 (archive receipt; the original discussion contains no explicit date)
- One-liner: Keep Wheel a minimal harness kernel (runtime, context primitives, tool protocol, service API, events, capability enforcement, minimal panel/model interfaces) and compose everything else — UI, model management, tools, memory, strategies, observability — as Lua plugins, with bitty-ai as the official distribution.
- Background / Problem:
  - The owner proposed splitting UI, model management, dashboards, and user-extensible tools out of Wheel so the core stays small, fast-moving surfaces evolve independently, and Wheel can run headless across panels.
  - Bitty's distinctive Lua-to-Lua extension dimension (plugins built from plugins, not only Rust-to-Lua IPC) makes a composable decomposition natural.
- Key conclusions / Decisions:
  - Boundary rule: Wheel Core provides mechanism, plugins provide policy — core knows what Context, Agent, and Panel are but never decides when to compact, how many subagents to spawn, or what chat UI looks like.
  - In/out split: agent lifecycle and tool-call loop, context representation primitives, tool definition and invocation protocol, plugin registration with service discovery, event bus, capability and permission checks, a minimal panel bridge, and a model abstraction stay in; providers and auth, UI variants, dashboards, tool packs, memory, context and multi-agent strategies, observability, persistence, MCP/skill adapters, policy packs, and notifications move out.
  - UI becomes replaceable plugins over a small event/agent/session/context/tool/panel API, decoupled from the agent's own panel so a headless agent can be driven from a separate dashboard panel.
  - Model management becomes an LLM runtime/gateway plugin behind a unified generate/stream/tool-call interface hiding keys, OAuth, subscriptions, and endpoints, so model-ecosystem churn never forces harness upgrades.
  - Tools become provider plugins declaring provided tool namespaces over a minimal native base (process, filesystem, panel, IPC), Unix-style, so the default Wheel needs few built-in tools.
  - Two Lua-to-Lua layers: same-process Service Registry/Event Bus/Capability calls versus cross-process or cross-panel IPC, ideally behind one location-transparent call API that routes local versus remote delivery.
  - Declared plugin dependencies (required and optional services) form a package-like dependency graph; `.wheel/` plus global configuration act as the composition layer selecting and constraining plugins while `.agents/` keeps cross-harness interop.
  - bitty-ai becomes an official plugin distribution (preset compositions from minimal to full) rather than one large plugin; closing formula: Bitty is the runtime, Wheel the agent kernel, bitty-ai the distribution, plugins capabilities, `.wheel/` composition, `.agents/` interop, IPC and service bus the glue.
