# 046 — Wheel Scoped to Coding Agent Harness

- Status: Captured — conclusions not yet captured in any `*-docs` repo; destinations proposed below (owner-pending)
- Date: 2026-09-17 20:10
- One-liner: Wheel is Bitty's official Agent Harness plugin scoped to software engineering only — Coding domain fixed, roles vary inside it; Personal/Office/always-on agents are separate future plugins, never Wheel scope.
- Background / Problem:
  - The owner asked whether Wheel should present multiple agent kinds (opencode/Claude Code/Codex/Copilot-style coding agents versus Hermes-style global self-evolving agents) and proposed doing only the Coding Agent for now, because Hermes/OpenClaw/office agents differ in purpose, composition strategy (e.g. Hermes self-summarization for system management, config edits, news, cloud services, Q&A), and storage layers.
  - The record agreed and hardened the boundary: Wheel fixes Domain = Coding while keeping Role open (Primary/Commander/Coding/Review/Debug/Research) over one unified `Agent { role, model, tools, permissions, context, budget, workspace }` primitive — roles are configuration, never a class explosion.
  - Hermes is moving toward persistent memory, self-created skills, cron, messaging gateways, and remote execution (autonomous agent, not a coding copilot); OpenClaw is a personal assistant with persistent state/memory and a gateway. A Personal Agent centers on User (memory, calendar, email, browser, cloud, cron, notifications, OAuth, vault, multi-device sync), runs as a months-long daemon, and needs lifelong user-centric memory — versus Wheel's project-centric memory (architecture, why a function is implemented this way, test history, task/branch state). An Office Agent centers on documents/spreadsheets/slides/email/calendar/approvals with stronger external side effects (`send Email`, `share Document`) and a different permission model (`read Gmail` vs `read(src/)`).
- Key conclusions / Decisions:
  - Scope: `Wheel = Bitty 官方的、面向 Software Engineering 的 Agent Harness`. It may support multi-agent, multi-role, multi-model, multi-workspace/panel — but its task domain is always software development. Non-goals (proposed verbatim for the Wheel README/RFC): not a personal AI assistant, not a general-purpose autonomous agent, not a messaging gateway, not an email/calendar assistant, not home automation, not a lifelong user-memory system, not a cron/automation daemon, not a general cloud-management agent. `Wheel is focused on software engineering workflows.`
  - Future shape: `bitty-terminal` holds Wheel (Coding) plus separate future personal/office agent plugins; all share Bitty Agent Primitives (AgentId/SessionId/JobId/TaskId, AgentRuntime/Context, Tool/ToolRegistry, Permission/Capability, ResourceBudget, AgentEvent/Handle/Lifecycle, Provider, ContextStore/Artifact, Job/JobResult) plus Bitty-native Panel/Workspace/PTY/Process/IPC/Worktree/LSP.
  - Anti-premature-abstraction: do NOT design a Universal Agent API for an imagined Personal Agent (`trait Agent { memory, cron, email, code, browser, ... }`); generalize only from two real implementations (Wheel needs X → implement X; second agent needs X → extract X).
  - Staged Wheel MVP: stage 1 = single Primary Coding Agent (read/search/edit/shell/git/LSP) in a Bitty Panel with Panel/Worktree/Process/LSP/Task awareness; stage 2 = Primary + Subagents (resource budget, permissions, typed result, progress note, task/worktree binding); stage 3 = Commander (plan/assign/monitor/review/merge) — the true Agent Harness.
- Destination: proposed owner-pending captures — (1) Wheel scope + Non-goals block into the `wheel` repo (`README.md`/`AGENTS.md`, wheel-owner task); (2) `Agent = Identity + Role + ...` composition rule plus Hermes/OpenClaw classification (autonomous/background family) already partially in bitty-ai-docs (`ai-architecture.md:216-220`, `:881-906`, `:911-941`) — reconcile the fixed-Coding-domain statement against the "Non-coding agents are the same composition" candidate and the CTX-0047 unmerged-candidates comparison, not re-decided here; (3) user-centric/lifelong-memory and daemon-lifecycle requirements belong to a future personal-agent plugin repo, not recorded anywhere yet.
