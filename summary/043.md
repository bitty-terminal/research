# 043 — Platform Testing Infrastructure and Benchmarks

- Status: Captured (draft capture in bitty-docs, PR bitty-docs#315 open — not merged)
- Date: 2026-09-16 17:52
- One-liner: Test Bitty in three tiers — native, QEMU/libvirt VMs, and physical hardware — and keep the VM layer reproducible with base images plus overlays.
- Background / Problem:
  - Bitty depends on OS-specific behavior (Unix PTY versus ConPTY, Wayland/X11, fontconfig/FreeType, Mesa/Vulkan, IME stacks, shells), so `cargo test` alone cannot validate real Windows/Linux environments.
  - Cross-platform testing needed a concrete, automatable Linux-hosted plan: which VM technology, which guest matrix, how to run tests inside guests, and how to avoid reinstalling an operating system per run.
  - GPU, IME, and driver behavior cannot be fully reproduced in a VM, so the plan had to define what VMs can and cannot prove and where physical hardware is required.
- Key conclusions / Decisions:
  - Adopt a three-tier test architecture: Native tests (unit: parser, grid, ECS, config; PTY, layout), VM tests (OS integration: ConPTY/PTY, Wayland/X11, distributions), and Physical tests (GPU, IME, macOS, real hardware).
  - Fix the Linux host stack as QEMU (virtual hardware) + KVM (same-architecture acceleration) + libvirt (VM lifecycle, API, snapshot, network), with qcow2 overlays and SSH/WinRM for in-guest execution.
  - VM matrix staged by cost: pull requests run Linux x86_64 and Windows 11 x86_64 KVM; merge/main adds Ubuntu, Fedora, and Alpine; nightly adds Linux and Windows ARM64 under QEMU TCG (not recommended per commit); a native ARM64 host can replace TCG later.
  - Never install a guest from ISO per run: maintain prepared base images (VirtIO drivers, SSH, Git, PowerShell, VC runtime, test agent) and create a disposable qcow2 overlay per test, deleting it afterwards.
  - Use libvirt as the automation control layer rather than hand-rolled QEMU scripts, and build a Bitty-owned test controller (`cargo xtask vm list/start/test`, for example `crates/bitty-test-runner`) that automates overlay creation, domain definition, boot, readiness wait, artifact upload, test execution, log/screenshot collection, shutdown, and overlay removal.
  - Split guest access by responsibility: libvirt plus the QEMU guest agent for VM management (state, filesystem freeze, shutdown, IP information); SSH for test execution (Windows OpenSSH Server is sufficient, so WinRM is unnecessary), behind one `Guest` trait (`exec`, `upload`, `download`) for Linux and Windows guests.
  - VM GPU coverage is useful but bounded: virtio-gpu with virgl/Venus can validate window creation, wgpu initialization, fonts, shaders, resize, and render-loop stability, but vendor-driver defects (NVIDIA proprietary, Intel Mesa, AMD RADV, Windows D3D12, macOS Metal) require physical runners. Run physical runners on a nightly cadence, not per PR.
  - Model IME and compositor variation as VM images (Arch + Hyprland + fcitx5, Ubuntu + GNOME + IBus, KDE Plasma + fcitx5, X11 + i3) because IME defects depend on compositor, display server, and IME implementation.
  - Design an E2E test protocol instead of fragile UI automation: `bitty --test-mode` exposes a test IPC surface (spawn terminal, send keys, create/split/resize panel, query screen/cursor/render state, screenshot, exit), reusing Bitty's existing IPC and Panel architecture.
  - Test pyramid order: unit tests most, then integration, then QEMU VMs, then physical hardware least; long term, a `bitty-test-runner` fronts `cargo test`, libvirt/QEMU, and native runners, with nightly ARM64 TCG plus physical AMD/Intel/NVIDIA and macOS Metal runs.
  - Benchmarks use a fixed benchmark VM for repeatable CPU/RAM/startup/parser/throughput measurements; cold start and warm start are measured separately; RAM uses PSS with fixed VM XML, pinned vCPUs, and multiple iterations (median/p95/stddev); parser/terminal throughput and real-world replay workloads fit VMs, while GPU, input latency, and power belong to physical benchmark runners. A `bitty-bench` subproject (images, workloads, runner, vm, results) with machine-readable JSON output is the candidate shape.
