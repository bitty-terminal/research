# 062 — foot Speed Analysis and Bitty Damage/Invalidation Direction

- Status: Capture in flight — destination proposed below (tdocs candidate doc, owner-pending merge); rename to `062.md.completed` once the canonical page lands.
- Date: 2026-09-23 (archive receipt; the original discussion contains no explicit date)
- One-liner: Dissect why foot is fast without a GPU terminal renderer (cell/row dirty tracking, viewport-not-memcpy scrolling, PTY coalescing, row-parallel workers, shared glyph cache) and upgrade it into a Bitty-general Damage/Invalidation System (three-level damage, browser-style UI invalidation, Persistent Panel Texture under wgpu, tile damage, ring-buffer GPU scroll) under the principle that state change does not imply redraw.
- Background / Problem:
  - The owner asks why foot is so fast (recalling a render-only-changed-parts mechanism) and whether Bitty can borrow it.
  - foot is Wayland-native and CPU-first: software rendering into Wayland shared-memory buffers, doing less work rather than accelerating the same work on the GPU (unlike the Alacritty/Kitty/Ghostty GPU-first line).
  - Bitty is broader than a terminal grid (Terminal + Native UI + Graphics + Wheel/Agent surfaces) and renders through wgpu swapchains, so foot's techniques cannot be copied literally.
- Key conclusions / Decisions:
  - **foot's speed is less work, not faster work.** Cell/row two-level dirty flags (`row->dirty`, `cell->attrs.clean`, verified in the foot clone `vt.c`); damage defaults to updated rows, never the full window; scrolling moves the viewport instead of memcopying the grid (virtual-memory mapping trick, `max-shm-pool-size-mb`); a small delayed-rendering window coalesces consecutive PTY writes into one render (also kills flicker from intermediate frames); render workers parallelize rows capped by visible-row count; server mode shares fonts and glyph cache across windows.
  - **Bitty generalization: a Damage/Invalidation System.** Terminal Grid yields dirty cells/rows (down to `DamageSpan { row, start, end }` column ranges); Native UI yields dirty nodes; graphics yields dirty rects — all feeding one Damage Tracker (region/tile set) into a Frame Scheduler and then the renderer.
  - **Browser-style invalidation for Native UI.** Only the changed UI-tree node dirties its parent sub-rect (e.g. one agent's status change rebuilds only the sidebar subrect), close to React reconciliation / retained-mode scene graphs, not traditional terminal rendering.
  - **wgpu adaptation: Persistent Panel Texture.** wgpu 30 has no cross-platform `present(damage_rects)`, so dirty rendering must not be tied to Wayland damage: each panel keeps a persistent texture, only dirty regions update, unchanged panels reuse textures, and a cheap composition pass presents to the swapchain. Terminal render cost is thus decoupled from window present cost.
  - **Tile-based damage and ring-buffer GPU scroll.** Panels subdivide into tiles with only dirty tiles re-rendered (uniform across Terminal/Native UI/Image/Dashboard); scrolling keeps a physical ring buffer with a moving viewport offset so only genuinely new rows render — critical for high-rate output (`yes`, `cargo build`, log tails).
  - **Core principle.** State change does not imply frame redraw; frame redraw does not imply panel redraw; panel redraw does not imply full-region redraw.
