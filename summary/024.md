# 024 — Repo-Wide Reconciliation and Core Slimming

- Status: Captured (conclusions recorded in bitty-docs)
- Date: 2026-09-14 23:00
- One-liner: Stop design inflation; reconcile first, then extract and harden.
- Background / Problem:
  - Architecture has taken shape, but docs-first ordering and experimental implementation left state drift and duplicated facts.
  - The terminal runtime carries too many optional experiences, conflicting with the minimal-core plus plugin-extension philosophy.
  - Architecture docs mix in project snapshots, still promise future repo splits after completion, leaving spec and implementation contradicting each other.
- Key conclusions / Decisions:
  - Shift focus from design to reconciliation, extraction, hardening, and verification; no more top-level concept expansion.
  - Freeze new official experiences in the terminal runtime; smart panels move to the agent runtime first.
  - Converge the agent base package into generic protocols with a restricted message vocabulary; model and compression runtime capabilities belong to the agent side.
  - Keep the generic protocol package clean; host capabilities like terminal snapshots and tool dispatch move to a separate bridge layer.
  - Specs live in docs repos, implementation and evidence in code repos; authoritative contracts are not stored in implementation comments.
  - Architecture docs keep only long-term contracts and ownership; snapshot counts and commit messages sink to status files and release evidence.
  - Split accepted versus draft boundaries to avoid single docs contradicting themselves on status.
  - Allow published but pre-release factual user docs without waiting for internal verification for install and daily use.
  - Project status files are the single source of state facts; other pages give only summaries or generated checks.
  - Clarify three doc mount semantics: docs trunk is latest, code mounts match implementation, governance mounts match review snapshots.
  - First do repo-wide fact reconciliation, then add drift gates, then batch-migrate optional experiences outward and freeze the bridge layer.
- Destination: bitty-docs primary — verified in the documentation workflow (user-doc maturity tiers, DIR-015), the project state snapshot and routing rules, and the Phase A reconciliation; involving bitty-terminal-docs, bitty-plugins-docs, bitty-ai-docs
- Open items: Out-migration of optional experiences beyond the recorded directions and the remaining bridge tasks stay with owning tasks (for example DIR-018); no research-level item remains open.
