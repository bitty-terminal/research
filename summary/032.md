# 032 — Pluggable Model Access and Subscription Management

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-15 13:31
- One-liner: Model abstraction stays in core while all vendor and subscription integrations move into plugins.
- Background / Problem:
  - Whether a dedicated model-management plugin is needed to support multiple vendors and subscription shapes.
  - Concern that the core would grow heavy and network dependencies would pollute the terminal binary.
  - Interface-style supply is easily confused with subscription- or CLI-style supply.
- Key conclusions / Decisions:
  - Core keeps only the provider contract, model description, capability vocabulary, registry, selection routing, fallback, and usage semantics.
  - Vendor integration, authentication, subscription adaptation, and model discovery are all owned by plugins, with the management UI separated from adapters.
  - Subscription-style supply is expressed through transport abstractions such as CLI wrappers, without unofficial token workarounds.
  - Semantic aliases are introduced: agents declare only capability needs while routing policy selects the actual model.
  - Credentials use opaque handles from the host keystore, invisible in plaintext to both the management UI and agents.
  - The AI core ships with zero vendor dependencies; model and provider plugins are installed on demand.
