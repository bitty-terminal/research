# 001 — Core/Plugin Boundary and Five-Layer Model

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-08-30
- One-liner: Mechanisms belong in Core, policy and UX in Plugins, bounded by a five-layer model.
- Background / Problem:
  - A hard Core versus Plugin split is insufficient; Tabs, Split, background and similar need part-by-part ownership.
  - Wider pluginization risks eroding terminal truth, security, and runtime invariants.
  - The API boundary shared by official and third-party plugins is not yet fully fixed.
- Key conclusions / Decisions:
  - Guiding rule: Core owns resources, state, invariants, and mechanisms; Plugins own behavior, policy, and UX.
  - Tabs: container and lifecycle in Core; tabline, ordering, naming, and keyboard UX in Plugins.
  - Split: layout tree, split primitives, focus and resize in Core; layout policy and keybindings in Plugins.
  - Background: color, transparency, blur, and image rendering in Core; wallpaper selection and animated wallpapers in Plugins.
  - Scrollback: storage, quotas, and persistence in Core; search, history browsing, and export in Plugins.
  - Never-pluginize red lines: PTY/VT/state/grid/cursor, Unicode and rendering, keyboard/mouse/IME, protocol parsing, security primitives, window display, layout and focus primitives, plugin host and quota registry.
  - Decision test: if it stays a correct terminal with the feature disabled, it belongs in Core; system and truth concerns imply Core primitives; "how the user wants it" implies Plugin.
  - Five layers established: experience plugins, plugin API, application primitives, terminal Core, platform layer.
  - Goal is not the most plugins, but maximally composable UX and policy over strong low-level primitives.
  - Reuse first: mature capabilities like rg and git integrate via Host Service or external tools; Lua only orchestrates.
  - First batch of official plugins is richer than the status quo: tabs, search, shell integration, panels, statusline, sessions, projects, and more.
  - Lua must not spawn processes directly; external tools declare required and optional dependencies via manifest.
  - Statusline follows a modular provider model; lock screen distinguishes experience lock from true system lock and never stores passwords.
- Destination: bitty-terminal-docs, bitty-plugins-docs (Core primitives versus plugin API boundary is core content of both)
- Open items:
  - First-batch official plugin list still needs convergence.
  - Whether AI-related plugins enter the first batch is undecided, leaning to defer.
