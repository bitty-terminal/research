# 057 — Workspace-Native Application UI Runtime and Panel Architecture

- Status: Captured — conclusions not yet captured in any `*-docs` repo; destinations proposed below (owner-pending)
- Date: 2026-09-19 (archive receipt; updated with extended component architecture discussion)
- One-liner: Elevate Bitty to a Workspace-native Application UI Runtime: decouple Workspace, View, Panel, and Activity; adopt a 5-level composable UI hierarchy (minimal Rust primitives, Lua assembly, standard components, and third-party frameworks) over wgpu without HTML baggage; and enforce Core-owned animations, GPU effect budgets, and transactional window chrome.
- Background / Problem:
  - The owner asks how Bitty's UI/UX framework should be designed, combining Bitty's unique Panel and Workspace mechanisms with reference to tiling window managers (Hyprland, Niri, Sway) and modern terminal emulators (Kitty, Ghostty, WezTerm).
  - Panels in Bitty host rich plugin applications (e.g. btop system monitor, Docker dashboard, statusline) as full native-like application surfaces ("Plugin as a Service" / Plugin Application Runtime), rather than web-based UIs (WebView) or heavy cross-platform frameworks (Flutter).
  - Empirical benchmark data confirms that Piccolo (pure-Rust stackless Lua VM) achieves sub-millisecond multi-VM initialization (~9.9 µs per VM) and ~12 KB heap overhead per instance with outstanding string manipulation performance, making per-plugin isolated VMs viable.
  - The discussion expands into concrete component engineering: whether Bitty UI should be composed like web/React components (Sidebar, Card, Button, List) without cloning HTML's bloated element set; how to divide responsibilities between Rust mechanisms and Lua appearance (e.g. VirtualList, TextInput); how theming and accessibility (A11y) should be governed; and how to reconcile existing documentation debt (such as outdated `panel-vision.md` and scattered RFCs).
- Key conclusions / Decisions:
  - **Bitty as a Workspace-Native Application UI Runtime**: Bitty is not merely a terminal emulator with UI widgets; it is a programmable workspace and terminal-centered application shell.
  - **Spatial and Identity Hierarchy (`Workspace` -> `View` -> `Panel` -> `Activity`)**:
    - `Workspace`: Manages spatial layers (`WorkspaceScene` containing `tiled_layer`, `floating_layer`, `pinned_layer`, `popover_layer`, `overlay_layer`, and `scratchpad`).
    - `View`: Compositor presentation attachment point (`LayoutTree<ViewId>` or Z-stack); an internal compositor primitive hidden from end-users and plugin Lua APIs.
    - `Panel(PanelId)`: Application and session identity (`PanelId != ViewId != TerminalId`). Moving a panel across workspaces updates only its presentation attachment, leaving its PTY, `TerminalId`, `PanelId`, and Lua VM intact.
    - `Activity`: Unit of navigation and content within a Panel, managed by an `ActivityStack` that supports push/pop navigation (e.g. Overview -> Container Detail -> Logs).
  - **Definition of "Bitty-Native UI"**: Distinct from Ghostty's OS-native toolkit widgets (AppKit/GTK4) and cross-platform web engines (WebView/Flutter). Bitty renders a retained declarative UI tree directly via `wgpu`, while reserving OS-native APIs strictly for Window chrome, IME, clipboard, drag-and-drop, accessibility, file pickers, notifications, and system menus.
  - **Retained Declarative UI Model (No Immediate Mode Draw Loops in Lua)**: Lua emits a declarative `UiTree` only on state changes, semantic actions, timers, or service events; Rust reconciles tree diffs, computes layout, performs hit-testing, updates accessibility, and generates paint lists. Lua never runs a per-frame `draw(frame)` loop.
  - **Web/React-Style Composition with Minimal Primitives (No HTML Element Bloat)**:
    - HTML has 100+ elements because it carries document semantics, SEO, forms, and backward compatibility. Bitty sheds this baggage and adopts "minimal primitives + massive composition".
    - `Button` is not a required Rust class; it is composed in Lua: `Button = Box + Text + Focus + Pointer interaction + Keyboard activation + Style + A11y role`.
    - `Card` is pure composition: `Box + Background + Border + Padding + Header + Content`.
    - `Sidebar` is a layout pattern (`Column + VirtualList + ActionButtons`), not a specialized runtime element.
  - **The 5-Level Architecture of Bitty UI**:
    - `Level 0 — Rust Mechanisms`: Layout engines, text shaping, image decode, scroll physics, TextInput/IME, focus engine, hit-testing, animation interpolation, accessibility tree, GPU pipelines.
    - `Level 1 — Lua Primitives`: `Box`, `Text`, `Image`, `ScrollView`, `VirtualList`, `TextInput`, `Canvas`, `Terminal`, `Overlay`.
    - `Level 2 — Standard Components (bitty-ui-core)`: `Button`, `Card`, `List`, `Sidebar`, `Tabs`, `Toolbar`, `Dialog`, `Tooltip`, `Menu`, `Table`, `Tree`, `CommandPalette`.
    - `Level 3 — Domain Components`: `WorkspaceSidebar`, `GitBranchList`, `DockerContainerCard`, `AgentStatusCard`, `FileTree`, `ChatMessage`, `ModelSelector`.
    - `Level 4 — Applications`: Docker Plugin, Wheel AI UI, Git Plugin, btop-like Monitor, File Manager, Full Editor.
  - **Complex Widgets: Rust Mechanism + Lua Appearance**:
    - High-complexity elements (`VirtualList`, `TextInput`, `Editor`, `ScrollView`, `Canvas`, `Terminal`, `Table/Tree virtualization`) cannot be left entirely to Lua because they involve cursor navigation, grapheme clusters, IME composition, and large-dataset viewports.
    - Rust handles virtualization (e.g. instantiating only the visible 30 rows in viewport) and scroll physics; Lua defines per-item row appearance and action dispatch.
  - **Pluggable Theming & Third-Party UI Frameworks**:
    - Spacing, radius, and color tokens are defined in Lua theme tables. Standard components consume tokens; users and plugins can swap entire styling libraries without touching Rust Core.
    - Third-party design frameworks (`bitty-material`, `bitty-minimal`, `bitty-retro`, `bitty-tui-like`, `bitty-pixel`, or Neovim/macOS-styled frameworks) exist as pure Lua Level-2 libraries running inside the plugin VM.
  - **Accessibility (A11y) Semantics**: Visual styling is completely free, but interactive semantics require discipline. Standard Lua components automatically bind appropriate `role` metadata, keyboard shortcuts (Enter/Space), focus management, disabled states, and accessible names.
  - **Bounded Canvas Display Lists**: Visualizations (e.g. btop CPU graphs) do not run drawing loops in Lua; Lua submits bounded display lists/scene commands at low frequency (e.g. 1 Hz), while the Rust compositor renders smooth transitions at display refresh rates (e.g. 144 Hz).
  - **Layout Sizing Constraints & Niri-Style Columns**: Panels declare sizing constraints (`min_size`, `preferred_size`, `max_size`, `aspect_ratio`) rather than forcing hard dimensions. Niri-style dynamic column widths allow natural side-by-side coexistence of terminals (e.g. 900px), file trees (280px), and AI chats (480px) without forced binary-split squashing.
  - **Unified Style Cascade & Typed Panel Rules (Hyprland-inspired)**:
    - Establish `ResolvedStyle` precedence: Safety Policy -> User PanelRule -> WorkspaceRule -> User Theme -> Plugin Preference -> Plugin Content Theme -> Framework Default.
    - Distinct authority scopes: Window/Shell Chrome (Core + User), Panel Chrome (Core/User final; Plugin requests), Panel Content (Plugin controlled within Host budget).
    - Typed Panel Rules with explicit priority, specificity, source precedence, and conflict diagnostics, avoiding order-dependent ambiguity.
  - **Core-Owned Motion Hierarchy**: Lua defines target state changes; Rust interpolates. Motion trees inherit settings (`motion.default` -> `motion.panel` -> `motion.panel.open/move/close`), with mandatory support for `reduced_motion` and zero-wakeup frame-on-demand rendering.
  - **Three-Tier Resource Budget (Beyond Piccolo Fuel)**: While Piccolo's `Fuel` caps Lua bytecode execution, GPU effects (blur, opacity, shadows, textures, animations) demand host-level control. Implement a three-tier budget: `Lua Fuel` + `Host API Admission Budget` + `UI/GPU Resource Budget` (node count, texture memory, blur surface area, draw calls).
  - **Window Chrome & Workspace Rail**: Elevate status concepts into `WindowChromeRuntime` (WorkspaceRail, StatusBar, OverlayRoot, NotificationArea, CommandSurface). The vertical Workspace Rail acts as a permanent dock and the primary drop target for panel dragging and workspace creation (`+` drop target).
  - **Mod+LMB Drag-and-Drop Gesture Transaction**: Mod+LMB lifts a panel, displays interactive drop targets (splits, floats, rail items, or new workspace creation), and commits or rolls back (via Esc) atomically.
  - **Command Ontological Equivalence**: Every mouse gesture maps 1:1 to keyboard shortcuts, Command Palette entries, CLI invocations, IPC messages, and Agent actions via a single unified Command Registry.
  - **Orthogonal Panel States & Decoupled Plugin Lifecycle**: Decompose panel state into independent axes (Lifecycle, Presentation, Visibility, Focus, Attention, Interaction, Activity). Closing a panel does not unload its parent plugin; background plugins request attention badges rather than stealing user focus.
  - **Declarative Rehydration over VM Serialization**: Workspace persistence records layout, IDs, presentation modes, sizes, and activity routes. On startup, VMs are freshly instantiated and state is rehydrated declaratively, avoiding brittle disk serialization of raw Piccolo heap stacks.
  - **Documentation Debt Reconciliation & 5-RFC Convergence**:
    - Retire or archive outdated `product/panel-vision.md` in favor of Vision v2.
    - Reconcile `RFC-OQ-3` using the accepted `Panel != View` separation.
    - Consolidate future UI specifications into five core RFCs:
      1. `UI Runtime RFC` (UiTree, layout, widget primitives, input/hit-test, accessibility, diffing, UI budget)
      2. `Workspace Scene RFC` (tiled, floating, pinned, fullscreen, scratchpad, popover, overlay)
      3. `Panel & Activity RFC` (Panel/View relations, ActivityStack, PanelProvider, lifecycle, persistence state)
      4. `Panel Rules & Styling RFC` (rules, size constraints, appearance, themes, precedence)
      5. `Window Chrome RFC` (WorkspaceRail, StatusBar, plugin chrome slots, notifications, global overlays).
