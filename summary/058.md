# 058 — Beacon Spatial and Semantic Targeting Framework

- Status: Captured — conclusions not yet captured in any `*-docs` repo; destinations proposed below (owner-pending)
- Date: 2026-09-19 (archive receipt; the original discussion contains no explicit date)
- One-liner: Elevate Beacon from a terminal jump plugin to Bitty's workspace-wide Spatial and Semantic Targeting Engine: decouple target discovery (`TargetRef`), spatial label allocation, and GPU annotation layers from execution, routing `Action(Target)` through the unified Command Registry.
- Background / Problem:
  - The owner asks how the `beacon` plugin (inspired by `flash.nvim`) should be designed in light of the newly established Bitty UI Runtime, Panel/Activity model, and Workspace Scene architecture from Record 057.
  - Historically in `semantic-terminal-rfc.md`, Beacon was scoped narrowly as Phase 7 (P7) of Semantic Terminal for jumping between terminal lines and CommandBlocks.
  - With Bitty evolving into a Workspace-Native Application Shell featuring rich UI controls (Buttons, Lists, Cards) and domain plugins (Docker, Git, Wheel AI), restricting Beacon to terminal buffers is an architectural mismatch.
  - The discussion resolves how Beacon should address heterogeneous controls, panels, workspaces, and terminal blocks; how to avoid ad-hoc Lua callbacks by binding directly to the Command Registry; how to prevent label explosion via scoping; how to allocate labels spatially; and how to split generic Rust core mechanisms from the official Lua plugin.
- Key conclusions / Decisions:
  - **Beacon's Architectural Identity — Spatial + Semantic Targeting Engine**:
    - Beacon is not a simple jump plugin; it is Bitty's keyboard-driven semantic addressing layer for the entire workspace.
    - Fundamental duality: Mouse locates objects via screen coordinates through `Hit Test -> TargetRef`; Keyboard locates objects via Beacon labels through `Target Registry -> TargetRef`. Both dispatch uniformly via `Action(TargetRef) -> Command Registry`.
  - **Core Interaction Model: `Action × Target` (Vim-Style Operator-Pending Mode)**:
    - Beacon resolves _what to target_, not _how to execute_. It does not implement actions like `panel:close()` internally; instead, selecting a target dispatches a typed Command ID (`panel.close`, `panel.focus`, `command-block.fold`, `docker.restart`) to the global Command Registry.
    - Dual interaction paradigms:
      - **Action-first** (high frequency): Operator precedes target (e.g. `Leader f` -> Focus targets [A/S/D], `Leader z` -> Fold targets [D/F/G], `Leader m` -> Move panel to workspace [1/2/3]).
      - **Target-first** (exploratory): Target precedes operator (e.g. `Leader Space` -> Select target -> context action menu).
  - **`TargetRef` as Generation-Based Semantic Handle**:
    - Targets are represented as lightweight semantic references (`PanelRef(PanelId, Gen)`, `WorkspaceRef`, `CommandBlockRef`, `UiNodeRef`, `LinkRef`), never raw UI tree or memory pointers.
    - Targets are ephemeral snapshots collected upon entering Beacon mode. If the underlying entity disappears or re-renders, generation validation fails with `StaleTarget` and cancels or recollects cleanly.
    - Compositor internal `ViewId` is excluded from user-facing targets; users target Panels, Controls, Workspaces, and Domain Objects.
  - **Automatic UI Discovery + Explicit Domain Providers**:
    - UI Runtime components automatically participate in Beacon by exposing semantic properties (`focusable`, `clickable`, `actionable`, `semantic_id`, `bounds`, `command`); `ui.button` is automatically indexed, whereas static containers (`ui.card`) are ignored by default.
    - Three-tier Target Provider architecture:
      1. `Core Providers`: Panels, Workspaces, CommandBlocks, UI focusable controls, Links, RichBlocks.
      2. `Plugin Providers`: Domain entities (Git branches/commits, Docker containers/images, Wheel agents/tasks/tool-calls).
      3. `Derived Providers`: Composite and contextually filtered target sets.
    - Plugin providers collect targets through cold-path snapshots on session entry—never running per-frame poll loops.
  - **Target Scoping to Prevent Label Explosion**:
    - Constrain candidate targets by explicit scopes: `CurrentControlGroup`, `CurrentPanel`, `CurrentWorkspace`, `Window`, `WorkspaceRail`, and `SemanticDomain`.
  - **Spatial and Ergonomic Label Allocation**:
    - Single-character home-row priority (`asdfghjkl`, `qwertyuiop`), falling back to two-character codes (`AA`, `AS`, etc.) only upon overflow.
    - Spatial allocation mapping: Targets on the left half of the screen map to left-hand keys (`ASDF`), right half to right-hand keys (`JKL;`), or 3x3 grid quadrants.
    - Allocation algorithms reside in Rust Core; label character sets and strategies (`home-row`, `spatial`, `compact`) are configurable via Lua policies.
  - **Single Batched GPU Annotation Layer**:
    - Beacon labels do not spawn individual Panels or OS overlays. They render as an ephemeral `BeaconAnnotationLayer` within `WorkspaceScene`, submitted in a single pass to the GPU alongside selection and IME underline layers.
  - **Core Mechanism vs Lua Plugin Policy Split**:
    - Rust Core (`TargetEngine` / `AnnotationEngine`) owns: `TargetRegistry`, semantic target snapshots, `LabelAllocator`, `AnnotationLayer`, transient input capture, and Command dispatch bridge.
    - Beacon Lua Plugin (`bitty-terminal/beacon`) is a thin policy and UX layer: key language bindings (`Alt+Space f/x/z/m/i`), which-key integration, scopes, filters, theme badges, and provider composition.
  - **Security and Capability Boundaries**:
    - Beacon acts strictly as a mediator. Registering a target does not confer elevated capabilities upon Beacon. Action dispatch executes under the target owner's capability boundaries.
    - Beacon never inspects private plugin state (e.g. LLM prompts, secrets, or memory); it observes only public target metadata (`id`, `label`, `anchor`, `actions`).
  - **Six Architectural Primitives & State Machine**:
    - Formally defines six concepts: `BeaconTarget`, `BeaconProvider`, `BeaconScope`, `BeaconAction`, `LabelAllocator`, and `BeaconSession`.
    - Session lifecycle: `Idle` -> `Collecting` -> `Active` (valid prefix -> `Narrowed` -> `Dispatch`) with clean transitions to `Cancel` on Esc, timeout, or target invalidation.
  - **Decoupling from Semantic Terminal RFC**:
    - Beacon is extracted from `semantic-terminal-rfc.md` (where it was previously buried as P7). Semantic Terminal becomes merely one provider (`CommandBlockProvider`).
    - Beacon is promoted to a standalone workspace-wide targeting framework specified under `bitty-plugins-docs`.
- Destination: proposed owner-pending — Beacon Targeting Framework specification (`beacon-targeting-framework.md`), TargetProvider API, Action-first/Target-first interaction grammar, Lua configuration, and which-key integration to the plugin ecosystem documentation owner (`bitty-plugins-docs`); Core Target/Annotation Engine in Rust, `TargetRef` generation validation, `BeaconAnnotationLayer` in WorkspaceScene compositor, Command Registry dispatch bridge, and CommandBlockProvider to the terminal platform documentation owner (`bitty-terminal-docs`); removing Beacon P7 from Semantic Terminal RFC and defining the keyboard-mouse targeting duality to cross-cutting governance (`bitty-docs`).
