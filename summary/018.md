# 018 — bitty-ai Standalone Architecture and Code Intelligence Runtime

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-14 01:45
- One-liner: Position bitty-ai as a standalone intelligence runtime reusing mature protocols and dependencies while owning context, permissions, events, and code intelligence.
- Background / Problem:
  - bitty-ai must stand apart from the terminal for reuse by panels, headless mode, and third-party clients, but currently exists only as scaffolding.
  - Rebuilding AI infrastructure from scratch risks protocol, security, and storage pitfalls, so mature libraries need selection.
  - Terminal-AI boundaries need a clear split, with answers for code reading and writing, batch calls, LSP use, and edit transactions.
- Key conclusions / Decisions:
  - Hold the general principle that protocols, providers, models, tools, and UI stay replaceable, while events, context semantics, capability policy, authorization, and sessions belong to Bitty.
  - Backfill AI canonical documentation first and acknowledge the existing version and toolchain baseline in decision records; keep only input-output-free domain types in the core contract layer.
  - Form a strict directed-acyclic dependency shape, with model, context, and tools in parallel and runtime, storage, and protocols above; do not split out a workspace yet.
  - Prefer a multi-protocol generation library for model transport behind an internal adapter; reference portable agent contracts without adopting an external runtime directly; use the official SDK for MCP with tool abstractions above MCP.
  - Center permissions on capabilities and effects, resolving effects before deciding tool calls; route all native, MCP, and remote execution through one permission engine without separating sandbox from tool bus.
  - Run the runtime as an input-output-free state machine plus external drivers, supporting replay, pause, resume, branching, and inspection; persist sessions as event streams with standard observability.
  - Model context as structured entries with budgets, deduplication, redaction, and compression, estimating tokens per provider; start memory on a relational store plus full-text search without vector stores.
  - Track stable client protocol versions behind an adapter layer, keep independent operation without the terminal, make cancellation tokens tree-shaped, retry only idempotent reads, prevent key leakage into logs, and use system credential storage.
  - Build first only the vertical slice from input, context assembly, streaming model, tool permissioned execution, to event persistence and replay; hold a strict dependency security baseline.
  - Center code capability on project inspection, semantic reading, relation graphs, transactional editing, and diagnostic checks; reuse existing libraries for single-file symbols and return high-density results for multi-file reads.
  - Split search into text, symbol, structure, and semantic modes; edit with cross-file transactions plus version guards against stale writes, followed by a compact pipeline of syntax, format, diagnostics, checks, and focused tests.
  - Let users install their own language servers, starting evaluation from existing async clients; layer language capability into syntax, semantics, diagnostics, formatting, and builds; handle independent parallel work with batch tools and dependent local composition with pipeline tools.
  - Put the intelligence kernel in Rust and the intelligence user space in Lua; keep only committable intent and policy in the project config directory, runtime state elsewhere, with explicit authorization on first trust.
  - Separate skills, tools, and MCP: skills are know-how, tools are capabilities, MCP is a cross-process protocol; use native tools for the local core, Lua for composition, and MCP for external ecosystems.
