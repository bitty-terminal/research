# 055 — Wheel as Event-Sourced Agent Workspace

- Status: Captured — conclusions not yet captured in any `*-docs` repo; destinations proposed below (owner-pending)
- Date: 2026-09-18 (archive receipt; the original discussion contains no explicit date)
- One-liner: Wheel as an Event-Sourced Agent Workspace: agents act only in headless panels, an immutable event log records facts, context compiles from facts into a programmable versioned graph, and agents collaborate over a communication graph with Git-like operations.
- Background / Problem:
  - The owner asks how Wheel should manage context: each agent works in a headless panel, agents can visit each other's panels, the flat main-agent-plus-subagents shape cannot express peers commanding peers or asking follow-up questions, and raw log volume dominates model context while the model's own output tokens stay small.
  - The owner proposes structured per-panel storage with Git-style operations (merge, fork, issue, rebase) plus per-tool-call reason annotations, and asks how to design it. The record answers by defining Wheel as an Event-Sourced Agent Workspace: panels supply execution space, agents supply behavior, the event log records facts, context is a compiled view of facts, and an agent graph handles collaboration.
- Key conclusions / Decisions:
  - Split six objects: Agent (thinking actor, mobile across panels), Panel (execution environment, may sit agentless), Event (immutable fact until GC), Context (recompilable LLM view), Task (goal and state, may span agents), Artifact (content-addressed outputs). Founding inequalities: Agent is not Panel, Panel is not Context, Context is not History, Task is not Agent.
  - Agents work only in headless panels: Headed panels are human-owned (agent read/observe), Headless panels are agent-owned (read/write/execute), shared headless panels gate on lease/capability, detached panels keep history only. Touching user work means forking an execution snapshot (cwd, worktree, environment, recent commands, outputs, context refs) — never typing into the user's panel.
  - Panel history becomes an immutable Event Log (task.created, agent.attached, tool.started/progress/finished, artifact.created, decision.recorded, context.shared, agent.message, checkpoint.created) instead of a chat log. Each tool run records input, reason, status, duration, and a structured summary plus blob references, so raw output stays out of normal model context.
  - The per-call `reason` is durable rationale — a commit message stating what the action exists to verify, the expected outcome, and links — not a thinking dump; internal thinking stays ephemeral and out of long-term history.
  - Tool calls detach from terminal input: agents call a Wheel tool runtime under policy, capability, and resource control instead of sending keystrokes to a PTY; keystroke injection stays a user-interaction API.
  - Multi-tool invocation uses Batch plus DAG (sequential, parallel, dependency, conditional, retry, timeout, cancel) rather than a bare array, with each node carrying status, duration, reason, result, resources, and dependencies — which also suits progress UI.
  - Running tasks expose only status, elapsed time, and parsed progress; full logs load on demand via inspect (tail, errors-only, ranges). UI collapse (whether the user expands logs) and context materialization (whether logs enter LLM context) are separate concepts that must never be coupled.
  - Output pipeline runs Raw Output → Blob Store → Structured Parser → Result Summary → Context Compiler → LLM, shrinking tens of kilobytes of logs to tens of tokens of findings; stable hashed context blocks keep prompt caching friendly.
  - Context is a Manifest (system, project, task, pinned knowledge, decisions, recent events, imported contexts, artifact refs, open questions) with parent lineage, organized as a selectable tree; the model prompt is only a token-budgeted materialized view compiled from that graph.
  - Git maps onto the context graph (repository→workspace, worktree→headless panel, branch→context lineage, commit→checkpoint, tree→context manifest, blob→outputs/artifacts, HEAD→current context, fork/merge/rebase/cherry-pick/squash/diff/stash/tag/reflog/GC analogues) — applied to versionable context, never by rewriting the immutable event log, so squash and checkpoint compression keep provenance and stay expandable.
  - Fork spawns parallel agents inheriting context without re-seeding background; the agent team is a cyclic communication graph of uniform Agents with dynamic roles (leader/worker/reviewer are per-task roles, never agent classes), kept distinct from the Task dependency graph, which should stay a DAG to avoid deadlocks.
  - IPC follows the actor model as typed agent mailboxes (request/thread/task/content plus context base and refs), so recipients receive the relevant context graph rather than a bare sentence; context sharing uses lazy ContextBundles (summary first, expandable decisions/checkpoints/artifacts); merges split into Knowledge, Task, and Workspace kinds; context diff compares decisions, artifacts, files, facts, questions, and task state for the dashboard.
  - Storage is hybrid: SQLite as the index and metadata database (queryable events, tasks, messages, relations, full-text search) plus a content-addressed object store (hash-addressed, compressed) for outputs, patches, and snapshots, with JSON/JSONL reserved for export, debug, and interchange. Context GC assigns Hot/Warm/Cold lifetimes so that model context and persistent history diverge by design.
  - Tasks become Issue-like durable objects (status, owner, collaborators, dependencies, context, artifacts, progress, blockers) claimable by any replacement agent; the user dashboard becomes a company-console view (ask, inspect, pause, cancel, fork, message, handoff, diff, merge — no subagents); first-priority primitives are checkpoint, fork, share, diff, squash, and merge under the principle that history is immutable, context is programmable, panels are workspaces, and agents are actors.
