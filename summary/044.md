# 044 — Execution Host and Supervisor Boundary

- Status: Partial — bitty-owned mechanisms captured (draft capture in bitty-docs, PR bitty-docs#321 open — not merged); bitty-ai-owned semantics not captured (owner-pending in bitty-ai-docs)
- Date: 2026-09-17 00:25
- One-liner: Do not build a stronger `pty_spawn`; make Job/Execution a first-class object under an Execution Supervisor independent of Agent, Panel, and Conversation — bitty owns process mechanisms and enforcement, bitty-ai owns task semantics and policy.
- Background / Problem:
  - Agent harnesses keep background work session-scoped: OpenCode `pty_spawn` (PTY session plus exit notification and ring buffer), Codex exec sessions (process JSON-RPC, but model-side `write_stdin` polling), Claude Code (background shell tasks plus Monitor plus agent supervisor), Cursor (Agent/Run plus event stream, resume cursor, subscriptions), and pueue (daemon-managed queue that understands no agents, capabilities, panels, or handoff).
  - Bitty needed answers for: jobs surviving panel close, agent panel switch, or conversation compaction; what happens when the user kills the agent; long task lifetimes versus ordinary timeouts; network disconnects, OOM, and crash semantics; multi-agent visibility; and output that must not flood model context.
  - The existing direction (`Agent -> ExecutionContext <- Panel`, identity separation, mailbox, lease, generation fencing, handoff, critical messages) had not yet defined how long-running process/job management sits beneath `ExecutionContext`.
- Key conclusions / Decisions:
  - Abstract one level up: the first-class object is Job/Execution under an Execution Supervisor; `pty_spawn` becomes one backend, PTY is optional (pipe process is the default), and waiting is the runtime's job, never the LLM's (`exec` returns a handle plus automatic subscription instead of model polling).
  - Fix the four-object ontology — Task (semantic work), Execution/Job (real OS process tree), Agent (decision maker), Panel (human projection) — with jobs not belonging to panels: origins are provenance, and completion routes to the owning agent's mailbox, not to the origin panel.
  - Fix the boundary: bitty = Execution Host (OS process, PTY, capture, process tree, signals, timeout clocks, cancellation execution, output capture, capability enforcement); bitty-ai = Agent Runtime (Task model, ownership, binding, claims, subscriptions, handoff, mailbox, progress notes, retry and timeout policy selection); the shared contract is a typed execution protocol with generic verbs, never agent ontology.
  - Host job model: spawn-time lifetime (`Agent`/`Task`/`Workspace`/`Detached`), kind (`Command`/`Interactive`/`Service`/`Watch`), stdin closed by default with explicit interactive PTY opt-in, `argv`-first execution instead of `bash -c`, separated `hard_timeout`/`idle_timeout`/`retention_ttl`, retry default none, a structured outcome enum (`OomKilled` only when actually determined), owned-process-tree kill, and a typed cancel protocol (modes `Graceful`/`Immediate`/`GracefulThenKill`, outcomes including `StaleGeneration`) that the host executes while bitty-ai chooses policy.
  - Capability-scoped operations (`observe`, `read_output`, `write_input`, `signal`, `cancel`, `attach`, `transfer`) are enforced by the host per principal, so an AI-layer bug cannot kill an arbitrary process; `WaitingInput` is a first-class state inside the sensitive-input boundary.
  - Two generations: assignment generation (bitty-ai ownership) is not execution generation (host handle); stale execution handles are rejected by the host itself.
  - Two-layer result contract: bitty produces the authoritative `ExecutionResult` (typed outcome, timestamps, stdout/stderr and artifact references, resource usage, truncation); bitty-ai produces the semantic `JobResult` (summary, diagnostics, task effect, progress note). Artifacts are stored and referenced by the host mechanism and interpreted by bitty-ai.
  - Output handling: bounded ring buffer plus optional persisted logs plus file-held artifacts; only bounded tails and references enter model context, with explicit tail/filter reads; SQLite holds metadata and an output index, never raw stdout.
  - Event delivery: observation events (stdout, progress, heartbeat) may be coalesced, dropped oldest-first, or kept UI-only and must never wake the model; critical events (completed, failed, needs_input, permission_required, timeout, ownership_changed, cancelled) are delivered reliably at-least-once with stable ids and dedupe; accepted/delivered/acknowledged stay distinct; IPC disconnects retain events and resume by sequence.
  - Three disconnect classes stay separate: LLM-provider outage (never touches jobs), a job's own network failure (record exit code, signal, stderr, timeout — do not invent `network_error`), and Bitty IPC disconnect (execution continues, events replay).
  - Persistence is staged and stays out of v0.1: Phase 1 in-memory supervisor with event-driven completion and no restart survival; Phase 2 persistent metadata/events/logs plus reconciliation and resume cursors; Phase 3 a detached supervisor daemon (multi-day jobs, handoff/adoption, scheduling) composing with the ADR-0008 headless deferral.
  - Repository placement: bitty gets an AI-agnostic execution subsystem (no `AgentId`/`TaskId`/LLM symbols; generic principals, ids, targets, capabilities, opaque metadata) and bitty-ai the semantic wrapper — "every Job may reference an Execution, but an Execution is not inherently an AI Job" — joined by generic `execution.*` IPC verbs (spawn, get, cancel, signal, read, subscribe, attach) that Terminal Core can own without agent ontology.
  - Borrow design, not backends: pueue (supervisor states, queue, groups, dependencies, pause/resume, logs, environment snapshots), Cursor (event stream, resume cursor, subscription wake-up), OpenCode PTY (read/write/list/kill, ring buffer, exit notification), Claude Code (background task, Monitor, `/tasks` UI), Codex (process event protocol).
  - Multi-agent visibility: owner plus subscribers with per-operation grants; Panel projection, attach/tail interactions, and a control console are illustrative UI direction; needs-input surfacing and output folding compose with existing terminal presentation records. The record proposes a dedicated `execution-supervisor` RFC/spec and a canonical boundary table instead of scattering the design.
- Destination: bitty-owned mechanisms captured as a draft page in bitty-docs (`docs/development/execution-host-boundary.md`, DIR-026 register row, PR bitty-docs#321 — open, not merged); the bitty-ai-owned semantics (Task model, `JobBinding`, claims, mailbox, `JobResult`, retry policy, orchestration) are NOT captured and stay owner-pending in bitty-ai-docs.
- Open items: v0.1 boundary versus the Phase 2 trigger; OOM determination without cgroups plus Windows/macOS process-tree backends; output and artifact retention defaults; execution subsystem crate shape and reconciliation of the generic execution IPC verbs with the accepted agent surface; terminal-side job-visibility and needs-input contracts; bitty-ai side uncaptured (owner-pending); OQ-061, OQ-057, OQ-059, and OQ-065 remain the contract owners; capture PR bitty-docs#321 is open and not merged.
