# 031 — Hard Gaps Blocking AI Integration on the Bitty Side

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-15 01:12
- One-liner: Clarifies which unfinished Bitty items would hard-block real AI integration after parallel development.
- Background / Problem:
  - Scope is limited to hard blockers that prevent connecting to Bitty even after parallel work finishes, not general missing features.
  - Base protocols, scopes, and authorization primitives already look fairly complete and are easily mistaken as ready.
  - The terminal panel already holds substantial early AI logic, creating a misplacement risk.
- Key conclusions / Decisions:
  - Only two P1 hard blockers remain: missing terminal snapshot host service and missing generic tool-distribution host service.
  - Authorization and consent must form a unified host-enforced gateway, built together with distribution rather than retrofitted later.
  - Execution requires a generic execution context plus structured results with unknown-state reconciliation semantics; blind retries are forbidden.
  - Bridge client SDK and rich-fragment transport are P2 and do not block runtime core development.
  - The terminal runtime stops accumulating model, memory, and other AI-specific logic, keeping only generic panel, execution, communication, and snapshot capabilities.
  - Parallel split: the AI side stabilizes against mock hosts, the Bitty side fills in host capability gateways, and both meet at the bridge layer.
  - Bitty priority order: snapshots, distribution plus authorization, execution backends, client SDK, rich-text intake, cleanup of legacy AI panel code.
- Destination: bitty-ai-docs, bitty-terminal-docs
- Open items: None
