# 020 — Pixel Badge Mascot and Image Scaling Model

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-14 17:56
- One-liner: Unify visual language with a pixel mascot, prefer modern graphics protocols, and isolate scaling per panel.
- Background / Problem:
  - Confusing numeric sizes turned out to be retro web badges, requiring clarification of practice and cultural differences.
  - Character-art mascots occupy many rows with low density and need a more recognizable small-size visual solution.
  - Image protocols, font sizes, terminal zoom, and desktop-pet behavior need clear relationships.
- Key conclusions / Decisions:
  - Treat retro badges as fixed small images plus outbound links expressing identity rather than machine state; propose an official badge set with a copy-page for sites.
  - Draw the mascot as small raster pixels rather than character art; use sprite sheets plus animation configuration internally and animated images only for external display; build three layers of command-line, desktop-pet, and plugin interfaces.
  - Constrain canvas, color count, strokes, lighting, and frame rate through skills to keep character consistency, change only a few pixels per frame for temporal coherence, and pin a canonical reference image with an asset directory.
  - Separate image pixels, terminal cells, and screen pixels; treat font size as a print size converted through display scaling and font metrics into cell size, where the same nominal size in different fonts can yield different cell geometry.
  - Prefer modern image protocols for terminal graphics with fallback to legacy protocols; the former separates image from placement and supports transparency, layering, sub-cell offsets, clipping, animation, and deletion.
  - Let plugin graphics call the renderer directly instead of looping through terminal escape sequences; external application output uses terminal graphics protocols while internal plugins use graphics and sprite interfaces.
  - Host desktop pets in floating or overlay panels in window pixel space, independent of terminal font-size scaling; distinguish global UI scaling, terminal scaling, and content scaling as three layers.
  - Restrict quick zoom to the focused panel and interpret it per panel type, changing font size for terminals, content scale for documents, and integer multiples for pixel pets; inherit configuration across global, workspace, and panel levels.
  - Build four coordinate spaces — image, cell, panel, window — into rendering, multiplying by display scale for final physical pixels.
- Destination: bitty-terminal-docs, bitty-plugins-docs
