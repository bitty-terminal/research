# 039 — Panel, Activity, and the Native UI Boundary

- Status: Captured (plugin direction in bitty-plugins-docs; AI direction distilled in bitty-ai-docs; terminal direction carried by the accepted Panel Runtime RFC in bitty-terminal-docs)
- Date: 2026-09-16 12:14
- One-liner: Panel is a workspace-managed application container; the activity stack keeps sessions alive while terminals stay a separate resource.
- Background / Problem:
  - The relationship between Panel, Activity, View, and Document was blurred: whether a terminal is a view, an activity, or a panel decided ownership of PTY lifecycle and session survival.
  - Presentation shapes (tiled, floating, overlay, fullscreen, scratchpad, pinned, popover) were being modeled as panel _types_, which multiplied the type system instead of expressing a runtime property.
  - The native UI surface needed a boundary between host-rendered widgets and plugin-driven state: whether Lua builds widget trees directly or describes declarative content for the host.
  - Capabilities and visual state (lifecycle, focus, visibility, interaction, attention) had no explicit separation for application services.
- Key conclusions / Decisions:
  - `PanelId != ViewId != TerminalId`; a panel is a generic, workspace-managed application container that generalizes view content.
  - `PanelRuntime` owns the panel lifecycle (create, mount, suspend, resume, dispose); panel content kinds are Terminal, Rich, Browser, Helper, and Canvas.
  - Presentation modes are runtime properties attached to a panel, not distinct panel types.
  - Panel is not Activity: an activity stack push/pop keeps the session alive, and `TerminalRegistry` owns terminal (PTY) lifecycle; Document, View, and Panel stay distinct concepts.
  - Rust provides primitives; the Lua application table holds state and policy, with the hot path staying in Rust.
  - The Native Widget Layer progresses from a v1 declarative slot UI (`Text`, `Row`, `Column`, `List`) toward a retained widget tree; it is retained/declarative, never immediate-mode.
  - Application services are exposed through an explicit surface with deny-by-default capabilities.
  - Visual state separates lifecycle, focus, visibility, interaction, and attention; v1 keeps bounded animation limits.
  - The final object model nests Window > Workspace > Panel > Presentation/Activity, backed by the UI Runtime, Application Runtime, and Lua Runtime.
- Destination: bitty-terminal-docs (accepted Panel Runtime RFC, 2026-09-14; draft Panel Extensibility Vision), bitty-plugins-docs
- Open items: The accepted Panel Runtime RFC leaves provider and ecosystem details to `RFC-OQ-1`..`RFC-OQ-9`; the panel-provider contract remains open.
