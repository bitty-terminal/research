# 025 — Prefix-Cache-Aware Context Organization

- Status: Captured (conclusions recorded in *-docs)
- Date: 2026-09-14 23:48
- One-liner: Stable content first, appends last, hit rate first.
- Background / Problem:
  - Prefix caching depends on the longest common prefix; dynamic content up front invalidates everything.
  - Nondeterministic tool and skill ordering and serialization break hits despite identical semantics.
  - Frequent small edits in mid-history look token-cheap but invalidate all later cache.
- Key conclusions / Decisions:
  - Order context from stable to dynamic: core prompts, tool schemas, skills, and project snapshots first, session history and current turn last.
  - Keep system prompts static; push dynamic runtime state like time, paths, branches, and budgets later or fetch on demand.
  - Determinize tool and skill serialization with fixed ordering, field order, whitespace, and newlines under a canonical encoding.
  - Version core skill and tool registries as session snapshots, incrementing only on explicit change to avoid per-turn reshuffling.
  - Prefer addressable references for dynamic state instead of embedding; read panel state on demand likewise.
  - Treat history as append-only and immutable by default; compression forms explicit epoch boundaries, abandoning old cache and rebuilding a new stable prefix.
  - Prefer compressing later segments and avoid rewriting early history; project context uses snapshot plus deltas, changing version only on explicit refresh.
  - Make context blocks content-addressed so multiple agents share stable prefixes; scope cache keys by model and tokenizer.
  - Keep session affinity in self-hosted routing so one session lands on the same worker when possible.
  - Introduce a context planner unifying ordering, normalization, budgeting, and cache affinity, with cache-friendliness shown in the usage panel.
  - Establish invariants: append by default, stable first, deterministic serialization, dynamic by reference, versioned changes, compression as structural operation, locality-aware scheduling.
