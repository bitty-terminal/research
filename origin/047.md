# 047 — 调用方归因（OpenRouter Apps 榜机制 + TurnRequest 身份字段提案）

## 第一部分：原始讨论（owner 侧分析，原样记录）

先看清截图里的统计项，再查 OpenRouter 是怎么识别和汇总这些 App 调用的。是的，截图里 Apps 这一栏不是 OpenRouter 去"扫描"各个产品，而是这些产品在调用 API 时主动报了自己的身份，OpenRouter 再按模型和 token 量汇总出来。

你看到的这段说明也很直白：

Public apps that send the most traffic to this model.

也就是：公开声明身份、并且打到这个模型上的流量最多的应用。

它是怎么认出来"谁在调用"的

每次请求打到 OpenRouter 时，客户端可以带这些 HTTP 头：

| Header                              | 作用                                                              |
| ----------------------------------- | ----------------------------------------------------------------- |
| HTTP-Referer                        | 必填。用应用的 URL 当唯一 ID，比如 https://claude.com/claude-code |
| X-OpenRouter-Title 或旧的 X-Title   | 显示名，如 Claude Code、Cline                                     |
| X-OpenRouter-Categories             | 分类，如 cli-agent、ide-extension                                 |
| X-OpenRouter-App-Visibility: hidden | 新建应用时设为隐藏，不进公开榜                                    |

没有 HTTP-Referer，这次调用就不会出现在模型页的 Apps 排行里，只会算进"未归属/私有流量"。

所以 Claude Code、Cline、Hermes Agent 能上榜，是因为它们的客户端默认就会带上自己的 Referer 和 Title。很多开源 Agent / IDE 插件现在都会这么做。

一个请求大致长这样：

POST https://openrouter.ai/api/v1/chat/completions
Authorization: Bearer sk-or-...
HTTP-Referer: https://github.com/cline/cline
X-Title: Cline
Content-Type: application/json

{
"model": "openrouter/hunter-alpha",
"messages": [...]
}

OpenRouter 收到后会记下：

哪个 model
哪个 app（由 Referer 归并）
这次消耗了多少 prompt + completion tokens
时间（按 UTC 日汇总）

数字是怎么算出来的

对某个模型页（你截图里的这个模型）来说，流程是：

只统计经过 OpenRouter 的流量，不含 Anthropic / OpenAI 官方直连。
按请求上的 HTTP-Referer 把流量归到某个 App。
同一 App 的多个别名/相近 URL 会合并到一个正式条目。
Token = prompt tokens + completion tokens。
Token 数来自上游供应商自己的分词器，不同厂牌之间只能当量级看，不能精比。
数据是实时累计的，不是一天结算一次；页面上的 Sep 16 / Sep 17 柱状图就是按 UTC 自然日切开。
隐藏应用、用户标成 private 的请求，不会进这个公开榜。 所以这不是该模型的全球总用量，只是"愿意公开身份、走 OpenRouter 的那部分"。

你截图里的 62.6B tokens，意思就是：在统计窗口内，标注为 omp 的公开应用，通过 OpenRouter 打到这个模型上，累计大约 626 亿 tokens。

和前面说的 Agent / Harness 怎么对上

截图里的 Hermes Agent、Claude Code、Cline、ZCode，本质上都是 Harness / Agent 产品。
它们内部用 LLM 做决策，但对外调用 OpenRouter 时会带上自己的 App 身份，于是模型页就能看出：

这个模型主要被哪些 Agent 在用
更像编程助手场景，还是别的场景

这也是为什么页面写：这是观察真实生产负载、判断模型适合什么场景的一个信号。

几个容易误解的点

不是 OpenRouter 入侵了这些 App。** 是 App 自己在请求头里报名。
不是该模型的全部用量。** 直连官方 API、没带头、设成 hidden/private 的都不会出现。
上榜的是 App，不是某个用户的 API Key。** 很多用户各自拿自己的 Key，通过同一个 Cline / Claude Code 去调，都会汇到同一个 App 名下。
Token 高 ≠ 用户多，更 ≠ 模型更好。** Agent 场景上下文会反复回放，token 很容易被放大。
你自己写个小工具，只要每次请求带上 HTTP-Referer 和标题，用的人多了也会出现在这个列表里；不想公开就加 X-OpenRouter-App-Visibility: hidden。

一句话：
OpenRouter 在网关层给每笔请求打上 App 标签，再按「模型 × 应用」把公开流量的 token 加总。 你看到的 Apps 排行，就是这个聚合结果。 这个也需要加上之后的设计，因为不然这样的话，调用方不知道是在哪里使用的

## 第二部分：Commander 代码核查 + 设计提案（bitty-ai 只读核查）

核查结论（`bitty-ai` 仓库，只读）：

- `TurnRequest`（`crates/bitty-ai-runtime/src/provider.rs:411-430`）字段只有 `model / messages / context_refs / tools / budget_bytes / timeout_ms / now_ms / sampling`——**没有调用方/app 身份字段**。
- 唯一真正发 HTTP 的是 `LocalProvider::http_round_trip`（`crates/bitty-ai-slice/src/local_provider.rs:611-683`）：请求头只有 `Host / Content-Type / Content-Length / Connection` + 可选 `Authorization`（`:652-663`）——**没有 Referer / Title / 任何调用方标识**。
- 计费侧只有内部成本单位，不是归因：`agent.rs:542-559` 的 cost fuse 经 `round_usage()`（`:976-987`，provider 上报 `ProviderUsage`，无上报则按字节估算）做熔断；`selection.rs:747-756` 的 `estimate_cost` 做路由估算。两者都不回答"这笔 token 是哪个 App 花的"。
- 典籍最接近的是 `provider-plugin-boundary.md:130-132` 的 `Router` 类型（网关作为一个 provider 条目、有自己的 descriptor/capabilities/accounting）——但没有调用方身份声明与透传规则。

提案（设计结论，未实现）：

> **在 `TurnRequest` 上加一个可选的 caller-attribution 字段（app id + 可选 title/category），`LocalProvider`（以及将来的 OpenRouter/HTTP adapter）在发请求时把它翻译成网关要的头（`HTTP-Referer / X-Title` 之类），缺省不填则明确记为 unattributed——让"用量归属"成为请求契约的一部分，而不是网关侧的猜测。**

必须守住的边界（均为典籍现成原则）：

1. **身份 ≠ 凭证**：`provider-plugin-boundary.md:194` secret invariant 同样适用——Referer/Title 进请求头，不进 prompt，更不进 context；进 typed surface 前先 bounded+scrubbed（`bridge.rs` bound_reason precedent）。
2. **None 语义明确**：参考 `sampling: None` 的"undeclared flows through untouched"（`provider.rs:427-429`）——缺省 = 本地/私有调用，不伪造、不默认填，必须能和"声明了身份"区分开，否则聚合数据就脏了。
3. **只做声明透传，不做用量结算**：分词、计价是网关/upstream 的事；Core 只保证"声明了什么、透传了什么、可审计"。身份字段不进缓存键、不参与路由（`cache_key.rs` 已立先例：sampling 参与 PartialEq 但不进 cache key）。
4. **按 adapter 落地**：`LocalEndpoint`（loopback）本来就不需要 Referer；真正的 `HttpApi / Router` adapter（`provider-plugin-boundary.md:115-132` transport taxonomy）落地时再接线。现在只进 `TurnRequest` 契约，不为想象中的网关提前写代码（046 记录"Generalize from two real implementations"同样适用）。

实现时机：等以后真接到 OpenRouter/HTTP adapter 时再提 AI-XXXX 实现任务；本次只归档设计结论。

然后就是这些 Agent 是需要 LLM 配置的，那么这个 LLM 配置我应该也是专门做成一个 Lua 插件比较好吧，其实就是支持各个平台的 API，比如 OpenAI, Anthropic, Gemini 的官方 API，然后还有 AWS Bedrock, Azure Foundry, Google Vertex AI, OpenRouter, OpenCode Zen/Go 等等别的提供商的 API 以及 Coding Plan 订阅，然后还需要可以使用订阅，比如 Claude 的订阅、ChatGPT 订阅、Google One 订阅等等，或者说其实就是支持 Claude Code, Codex, Antigravity, Kiro 等等这些的订阅，然后把这些订阅用在 Wheel 中使用，然后支持调用模型、调整模型思考挡位、管理不同的模型等等、或者说就是一个很好的管理 LLM 的插件，而且支持很好的同步最新的模型。
这个部分可以参考 omniroute, oh-my-pi 这些做的很好的仓库，omniroute 就是可以在本地一键管理各个模型、然后 oh-my-pi 是我见过的 Harness 工具中在 LLM 管理做的最全的，比 OpenCode 的 /connect 功能还多。

## 是的，而且我会把它进一步定义成一个独立的 **LLM/Model Infrastructure 插件**

你的方向基本正确：

> **Wheel 管 Agent，不管 Provider。**
>
> **LLM 插件管 Provider / Auth / Model / Thinking / Routing / Catalog，不管 Agent。**

这样 Wheel 就不需要知道 OpenAI、Anthropic、Bedrock、Vertex AI、OpenRouter、Codex subscription 到底怎么认证和调用。


健康很多。


Wheel 不需要知道两个 `"high"` 在 wire protocol 上完全不是一回事。

# 5. 订阅应该作为一种 `Auth Strategy`

这里特别值得设计好。

不要：

```text
Provider
├── api provider
├── subscription provider
```

而应该：

```text
Provider
    ↓
Auth Strategy
    ├── api_key
    ├── oauth
    ├── subscription_oauth
    ├── aws_credentials
    ├── google_adc
    ├── bearer_token
    └── none
```

例如当前已经存在一些官方允许的 subscription → coding agent 使用方式。

Claude Code 官方也支持 Claude Pro/Max 账户登录，同时支持 Anthropic Console、Bedrock 和 Vertex AI。([Claude Platform Docs][4])

Pi/oh-my-pi 这类工具则进一步实现了多种 OAuth/subscription provider 登录与 token refresh。([GitHub][5])

所以可以：

```text
provider: codex
auth: chatgpt-oauth
```

或者：

```text
provider: claude
auth: claude-subscription
```

## 但这里有一个原则非常重要

**只支持 provider 官方允许或稳定公开的 authentication flow。**

不要把：

```text
读取浏览器 Cookie
偷取其他 CLI credential
模拟网页请求
逆向 private endpoint
```

作为核心设计。

尤其 subscription backend 很容易变化。

Google 就是很好的例子：到 2026 年，Google 已经停止让 Google AI Pro/Ultra consumer tier 继续通过原来的 Gemini Code Assist / Gemini CLI consumer login 工作，并迁移向 Antigravity 产品线。([Google for Developers][6])

所以：

> subscription adapter 必须是 **可替换插件适配层**，而不能成为 Wheel 的基础假设。

# 8. 再进一步：支持 `Model Profile`

这个我认为对 Wheel 会特别有用。


```text
@fast
@cheap
@smart
@deep
@vision
```

```lua
profiles = {

        thinking = "low",
    },

    deep = {
        model = "provider/model-b",
        thinking = "high",
        fallback = {
            "provider/model-c",
        },
    }

```

Wheel：

```lua
agent "scout" {
    model = "@fast"
}

agent "coder" {
    model = "@coding"
}

agent "reviewer" {
    model = "@deep"
}
```

这样以后用户换 provider：

```text
Claude → OpenAI
```

根本不用修改 Agent。

只修改：

```text
@deep
```

即可。

这个设计非常值得 Wheel 借鉴。

我最终会推荐这样的架构：

```text
Bitty Core
│
├── Plugin Runtime
├── IPC
├── Secure Secret Store
├── Permission / Capability
└── generic streaming primitives
          │
          ▼

│
```

这里我尤其建议 **Secure Secret Store 属于 Bitty Core，而不是 Lua 插件自己保存密钥**。

```text

```

## Lua 插件负责 Control Plane，底层 API 可以逐步下沉

还有一点需要留余地。

最开始完全可以：

```text
Lua
├── provider definitions
├── model catalog
├── model selection
├── auth orchestration
└── HTTP request
```

但以后 provider 越来越复杂之后，可以逐渐形成：

```text
Lua
    Control Plane
        ↓
Provider ABI
        ↓
Rust/native implementation
```

特别是：

* SSE streaming
* OAuth callback
* HTTP/2
* retry
* proxy
* TLS
* credential refresh
* large streaming JSON
* high concurrency

这些未必适合永远全部堆在 Lua。

因此关键不是“所有东西必须 Lua 实现”，而是：

> **它作为一个独立 Plugin/Product Boundary 存在。**

Lua 可以是它的主要 extension/configuration layer。

---

# 最后 Wheel 会因此变得非常干净

你甚至可以让 Wheel 的整个模型概念压缩成：

```rust
trait ModelService {
    fn models() -> Vec<Model>;
    fn resolve(selector: &str) -> Model;
    fn stream(request: Request) -> Stream<Event>;
}
```

然后 Wheel 真正专注于：

```text
Agent
Task
Job
Panel
Workspace
Worktree
Context
Tool
Permission
Subagent
Commander
Result
```

这正好也符合我们前面收缩 Wheel scope 的思路：**Wheel 是 Coding Agent Harness，不是万能 AI 基础设施。**

而独立的 LLM 插件则可以慢慢发展成 Bitty 生态里的共享 **Model Infrastructure**。以后无论是 Wheel、Personal Agent、Office Agent，甚至一个普通的“终端里选模型问一句”的插件，都可以直接复用它。

我认为这个拆分甚至应该在 Wheel MVP 之前就确定，因为一旦 Wheel 直接开始写 `OpenAIProvider / AnthropicProvider / ClaudeOAuth`，后面再拔出来会非常痛苦。
