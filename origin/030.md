我看了现在的 `bitty-ai-docs`、`bitty-ai` 实现以及 `bitty` 里的 `bitty-agent` / `bitty-ipc`。我的判断是：

> **当前 `bitty-ai-runtime` 保持 `std-only` 是对的，不应该为了“避免重复造轮子”立刻塞一堆 crates。真正应该引入第三方 crates 的，是后续 Provider、MCP、Code Intelligence、Persistence 等边界层。**

你现在的 v0.1 profile 本来就明确规定：单一 `bitty-ai-runtime`、`FakeProvider`、无网络 Provider、无远程 endpoint、只做 single-agent + L0/L1 context，并要求 **“No network access in v0.1 code paths”**。 当前实际 `Cargo.toml` 也正是 `No dependencies: std only. No network providers, no TLS, no async runtime.`。

所以我会把依赖规划成这样：

| 能力                             | 推荐 crates                          | 放在哪里                                         | 现在引入？         |
| ------------------------------ | ---------------------------------- | -------------------------------------------- | ------------- |
| deterministic Agent Runtime    | **无，std**                          | `bitty-ai-runtime`                           | **是，保持现状**    |
| JSON / wire types              | `serde`, `serde_json`              | Provider / IPC adapter / Tool Bus            | 后续            |
| Error boilerplate              | `thiserror`                        | 各 adapter/runtime crate                      | 可后续           |
| Async runtime                  | `tokio`                            | Provider / MCP / LSP                         | **不要进纯 Core** |
| cancellation / async utilities | `tokio-util`                       | Provider / MCP / LSP                         | 后续            |
| Async stream abstraction       | `futures-core`, `futures-util`     | Provider streaming                           | 后续            |
| HTTP Provider                  | `reqwest`                          | `bitty-ai-model-provider` 或 provider adapter | **需要网络时再加**   |
| MCP                            | **`rmcp`**                         | Tool Bus / MCP adapter                       | 后续强烈推荐        |
| Tool JSON Schema               | `schemars`, `jsonschema`           | Tool registry / Tool Bus                     | 后续强烈推荐        |
| Logging / spans                | `tracing`                          | runtime adapter 层                            | 后续推荐          |
| workspace 文件遍历                 | **`ignore`**                       | Context / code tools                         | 推荐            |
| AST / symbols                  | **`tree-sitter`** + grammar crates | Code Intelligence                            | 推荐，但注意 MSRV   |
| LSP client/broker              | `async-lsp` + `lsp-types`          | Code Intelligence                            | 后续 spike      |
| fingerprint/cache key          | `blake3`                           | Evidence / code intelligence                 | 后续推荐          |
| diff                           | `similar`                          | Diff/context/review primitive                | 后续可用          |
| SQLite                         | `rusqlite` 优先评估                    | Persistence                                  | **现在不要选**     |
| 临时文件测试                         | `tempfile`                         | `dev-dependencies`                           | 可以            |

## 1. `bitty-ai-runtime` 不应该依赖 Tokio / Reqwest

这个边界我觉得非常重要。

你现在的 runtime：

```text
bitty-ai-runtime
├── agent.rs
├── context.rs
├── provider.rs
├── session.rs
├── stream.rs
└── tool.rs
```

已经基本就是一个 **Agent Kernel / State Machine**，而不是 I/O framework。当前实现也确实是这么组织的。

因此最好保持：

```text
bitty-ai-runtime
        │
        │ traits / domain types
        ▼
┌───────────────────────┐
│ Provider Adapter      │── reqwest / tokio
│ MCP Adapter           │── rmcp / tokio
│ Code Intelligence     │── tree-sitter / LSP
│ Persistence           │── rusqlite
│ Bitty Bridge          │── IPC protocol
└───────────────────────┘
```

也就是说，**依赖倒置**：

```rust
pub trait ModelProvider {
    // ...
}
```

runtime 知道 `ModelProvider`，但不知道：

```text
HTTP
OpenAI
Anthropic
Gemini
Ollama
reqwest
tokio
TLS
```

这个设计还正好对应你之前说的：

> `bitty-ai provider` 的网络依赖应该独立。

是的，而且我现在看完代码和 docs 后会更明确地支持这个决定。

---

# 2. Provider：`tokio + reqwest`，但隔离出去

等开始做真正 Provider 时，不要自己实现：

```text
TCP
HTTP
HTTP/2
TLS
chunked body
SSE
proxy
connection pooling
timeout
redirect
```

这些完全没有必要自己做。

直接：

```text
Provider trait
    │
    ├── FakeProvider
    ├── OllamaProvider
    ├── OpenAICompatibleProvider
    ├── AnthropicProvider
    └── GeminiProvider
              │
              ▼
        reqwest + tokio
```

当前 `reqwest 0.13.5` 的 MSRV 正好是 Rust `1.85`，与你现在 `bitty-ai` 的 `rust-version = "1.85"` 对得上。它支持 Rustls，并且如果你希望严格控制 TLS backend，可以关闭 default features 后显式配置。([Docs.rs][1])

我甚至不建议一开始每个 Provider 都单独 crate。可以先：

```text
crates/
├── bitty-ai-runtime/
└── bitty-ai-provider/
    ├── openai_compatible.rs
    ├── anthropic.rs
    ├── gemini.rs
    └── ollama.rs
```

成熟以后发现 Provider 生命周期、release cadence、features 差别真的很大，再拆：

```text
bitty-ai-provider-openai
bitty-ai-provider-anthropic
...
```

避免过早 crate explosion。

# 3. MCP：不要自己写，优先 `rmcp`

这个是最典型的“不要重复造轮子”。

你现在 `bitty-ipc` 已经有一个 bounded `McpClientStub`，负责 Bitty 自己的安全边界和测试 seam。

但以后 bitty-ai 真正成为 MCP Client 时，没有必要再自己完整实现：

```text
initialize
capability negotiation
tools/list
tools/call
resources
prompts
notifications
tasks
subscriptions
Streamable HTTP
stdio transport
JSON-RPC correlation
protocol version negotiation
```

现在已经有官方 Rust SDK **`rmcp`**，而且截至 2026-09，它已经支持稳定 MCP `2026-07-28`，底层基于 Tokio，同时提供 client/server、transport 和 schema integration。([GitHub][2])

所以未来应该是：

```text
bitty-ai ToolBus
       │
       ├── NativeToolAdapter
       │
       └── McpToolAdapter
                │
                ▼
               rmcp
```

但这里有一个与你当前工程非常相关的问题：

**`rmcp 3.x` 的 MSRV 已经是 Rust 1.88，而 bitty-ai 当前是 1.85。** ([GitHub][3])

所以现在不要急着写：

```toml
rmcp = "3"
```

你需要先决定：

```text
A. Bitty 整体 MSRV 1.85
   → pin 一个兼容版本

B. 未来 Code Intelligence / MCP 阶段
   → 全项目 MSRV 升到 >= 1.88

C. MCP adapter 独立 binary/crate
   → adapter 可使用更高 MSRV
```

我更倾向 **B 或 C**，而不是为了 MSRV 长期锁死旧 MCP SDK。

# 4. Tool Bus：`schemars + jsonschema` 很值得

你现在 Tool 本质上已经开始有：

```text
ToolSpec
ToolCall
ToolResult
arguments
schema
authorization
execution
```

而真正 Provider tool calling / MCP 接进来之后，JSON Schema 会越来越核心。

这里强烈不建议自己手搓：

```rust
if args["path"].is_string() ...
```

应该是：

```rust
#[derive(Serialize, Deserialize, JsonSchema)]
struct ReadArgs {
    path: PathBuf,
    offset: Option<usize>,
    limit: Option<usize>,
}
```

然后：

```text
Rust type
   │
   ├── serde     → serialization
   └── schemars  → JSON Schema
                      │
                      ▼
                   provider
```

`schemars` 当前直接支持 derive `JsonSchema`。([Docs.rs][4])

如果 Tool Bus 还需要验证 **模型返回的任意 JSON arguments**，再加：

```text
jsonschema
```

形成：

```text
Model generated JSON
        ↓
JSON Schema validation
        ↓
typed deserialize
        ↓
authorization
        ↓
dispatch
```

顺序最好不要反：

```text
❌ JSON → deserialize → tool
```

而是：

```text
JSON
 ↓
size bound
 ↓
schema
 ↓
typed value
 ↓
permission/effect classification
 ↓
dispatch
```

这和你 docs 里 Tool Bus 强调的 validation + authorization 边界是完全一致的。

# 5. Code Intelligence：`ignore + tree-sitter + LSP`

这里是最明显不应该自己造轮子的部分。

你的文档现在已经明确把：

```text
symbols
AST read
ast_query
LSP
progressive code reading
```

当成 bitty-ai 基础能力，而不是 `/review` 这种 workflow。

## 文件扫描：直接 `ignore`

不要自己实现：

```text
递归目录
.gitignore
.ignore
hidden file
glob
symlink
workspace exclusions
```

ripgrep 生态里的 `ignore` crate 正是干这个的，目前 `0.4.33`，直接提供尊重 `.gitignore` / glob / file type 的递归 walker。([Docs.rs][5])

例如未来：

```text
workspace.scan()
     ↓
ignore::WalkBuilder
     ↓
candidate files
     ↓
language detection
     ↓
Tree-sitter / LSP
```

这个依赖价值非常高。

# 6. Tree-sitter 非常适合 Bitty，但现在有 MSRV 问题

你之前设想的：

```text
read file
   ↓
不直接塞完整源码
   ↓
outline
symbols
struct
trait
impl
function
class
method
   ↓
agent 再 drill-down
```

Tree-sitter 正适合这一层。

但当前最新 `tree-sitter 0.27.0` 有个非常重要的问题：

> 它声明的 `rust-version = "1.90"`。([Docs.rs][6])

而：

```text
bitty       MSRV 1.85
bitty-ai    MSRV 1.85
```

所以现在不能直接用 latest。

这里建议不要因为 Tree-sitter 单独立刻把整个项目升 1.90，而是在真正落地 `bitty-ai-code-intelligence` 时做一次 MSRV decision：

```text
Rust 1.85
 ├── runtime
 ├── provider (reqwest 可以)
 └── ...

Rust >= 1.90
 └── 最新 tree-sitter
```

如果届时 Bitty 本身已经自然升级到 1.90，就完全没有问题。

# 7. LSP 千万不要自己完整实现

你 `code-intelligence.md` 里面要求的 LSP Broker，其实比“发 JSON-RPC”复杂得多：

```text
initialize
initialized
didOpen
didChange
didClose
document version
request correlation
cancellation
diagnostics
workspace folders
server restart
shutdown
exit
overlay
server generation
```

文档自己也已经把这些职责列得很完整。

所以未来应该评估：

```text
async-lsp
lsp-types
```

至少 **绝对不要自己写 LSP types + JSON-RPC framing + lifecycle state machine 全套**。

Bitty 真正需要自己写的是：

```text
                    bitty-ai
                       │
              Semantic Code API
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
   Tree-sitter      LSP Broker       Cache
       │               │
 syntax truth      semantic truth    evidence
```

你的创新点应该在 **broker / authorization / sharing / snapshot / progressive disclosure**，而不是重新实现 LSP protocol。

# 9. `bitty-agent` / `bitty-ipc` 要复用“协议”，但不要硬耦合

这里我发现一个现在就值得注意的问题。

`bitty-agent` 已经定义了一个：

```rust
AgentId
```

而且它的语义是：

```text
owner.name
```

是 generic host-neutral protocol identity。

但现在 `bitty-ai-runtime/session.rs` 里面又有：

```rust
pub struct AgentId(pub u64);
pub struct RunId(pub u64);
pub struct SessionId(pub u64);
pub struct ExecutionId(pub u64);
```

这不一定是“重复实现”，因为两个 `AgentId` 的含义其实不同：

```text
bitty-agent::AgentId
= protocol principal / external agent identity

bitty-ai-runtime::AgentId
= runtime-local logical agent handle
```

但是 **名字碰撞以后会非常难受**。

我建议趁现在 API 还没稳定，考虑显式命名成：

```rust
AgentPrincipalId     // protocol identity

AgentInstanceId      // runtime agent
RunId
SessionId
ExecutionId
```

或者：

```rust
ProtocolAgentId
RuntimeAgentId
```

这样 bridge 才会非常清楚：

```text
ProtocolAgentId
      │
      │ authorization / mapping
      ▼
RuntimeAgentId
      │
      ├── RunId
      ├── SessionId
      └── ExecutionId
```

这比以后让两个 crate 都导出 `AgentId` 好很多。

# 10. 我建议的最终依赖边界

我觉得 Bitty AI 最终最健康的形态大概是：

```text
bitty-ai-runtime
    std only / 极少依赖
    │
    ├── AgentLoop
    ├── Session
    ├── Context contracts
    ├── Tool contracts
    ├── Provider trait
    └── cancellation semantics

bitty-ai-provider
    ├── serde
    ├── serde_json
    ├── tokio
    ├── reqwest
    ├── futures-util
    └── tracing

bitty-ai-tool-bus
    ├── serde
    ├── schemars
    ├── jsonschema
    └── tracing

bitty-ai-mcp
    └── rmcp
        └── tokio / serde / schemars / ...

bitty-ai-code
    ├── ignore
    ├── tree-sitter
    ├── language grammars
    ├── async-lsp
    ├── lsp-types
    └── blake3

bitty-ai-store          # 如果未来真的需要
    └── rusqlite
```

注意，这不是说**现在立刻拆成 6 个 crate**。你自己的 v0.1 profile 已经明确说了 “No five-crate split yet”，当前单 `bitty-ai-runtime` 正是为了先稳定接口。

应该是：

```text
现在
bitty-ai-runtime
        ↓
接口稳定
        ↓
出现真正外部依赖
        ↓
沿 dependency boundary 拆 crate
```

而不是：

```text
先设计 10 个 crate
        ↓
然后发现根本没有必要
```

## 最关键的三个决定

如果让我现在直接给 bitty-ai 定原则，我会定成：

> **`bitty-ai-runtime` 尽量永久保持无网络依赖，最好甚至长期保持接近 std-only。**

> **HTTP / MCP / LSP / DB 都是 adapters，不进入 Agent Kernel。**

> **“不要造轮子”主要应用在协议、解析器、HTTP/TLS、JSON Schema、LSP、文件遍历这些 commodity infrastructure；Agent 生命周期、Context projection、Tool authorization、Panel/ExecutionContext 集成、evidence semantics 才是 Bitty 应该自己设计的东西。**

这样 bitty-ai 不会变成一个 `Cargo.toml` 里 150 个 transitive dependencies 的“大模型 SDK 拼装器”，同时又不会为了追求零依赖，跑去自己实现 HTTP、MCP、Tree-sitter、LSP 这些完全没必要自己实现的东西。

另外，**现在最值得先处理的反而不是“加哪个 crate”，而是 `bitty-agent::AgentId` 与 `bitty-ai-runtime::AgentId` 的 identity naming / mapping boundary**。这个越早定清楚，后面接 IPC、MCP、multi-agent 会越省事。
