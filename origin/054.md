到了现在这个架构阶段，**Plugin 管理应该统一**。但我不建议直接得出“Bitty = 用 Lux 管所有 Plugin”这个结论。

更合适的是：

> **Bitty 自己拥有 Plugin Package Manager；Lux 负责 Lua package/dependency 这一层。**

也就是说，统一的是**用户入口和 Plugin 生命周期**，但内部仍然保留两张不同的依赖图。

## 1. 实际上存在两种完全不同的“包”

现在 Bitty/Wheel 会同时面对：

```text
Bitty Plugin
│
├── wheel
├── bitty-ui
├── wheel-models
├── wheel-dashboard
├── wheel-tools-rust
└── third-party plugins

Lua Package
│
├── json library
├── utility library
├── parser
├── data structure
└── framework internal dependency
```

它们不能完全混为一谈。

一个 Bitty Plugin 有：

```text
生命周期
enable / disable
permissions
Service / Capability
IPC
Panel
UI
配置
版本兼容
Plugin dependencies
project overrides
```

而普通 Lua package 更多只是：

```text
source code
module resolution
SemVer
dependency graph
lockfile
```

所以我建议：

```text
                  bitty plugin
                       │
              ┌────────┴────────┐
              ▼                 ▼
      Bitty Plugin Graph    Lua Package Graph
              │                 │
       Bitty Manager        Lux / resolver
              │                 │
              └────────┬────────┘
                       ▼
                Piccolo Loader
```

用户只需要看到：

```bash
bitty plugin add wheel
bitty plugin add bitty-ui
bitty plugin update
bitty plugin remove ...
bitty plugin list
```

不需要知道下面是 Lux 还是别的 resolver。

---

# 2. Lux 很适合作为参考，甚至作为 backend

Lux 目前已经有不少你正好需要的能力：

* `lux.toml`
* proper lockfile + integrity checks
* Git dependencies
* local dependencies
* workspace
* offline vendor
* LuaRocks compatibility
* SemVer
* 多版本 dependency resolution

并且很有意思的是，Lux 自己已经使用 **Piccolo 来 sandbox 执行 Rockspec / manifest**。

所以 Lux 和 Bitty 的技术方向其实并不冲突。

但现在不适合：

```text
Bitty Plugin System
        =
Lux Package Manager
```

因为 Lux 是 **Lua package manager**，不是 application plugin manager。

而且 Lux README 当前仍明确说明它还没有 `1.0`，embedding API 也是 WIP。

因此我不会现在就把：

```rust
lux-lib
```

变成 Bitty Core 的关键 ABI 依赖。

---

# 3. Piccolo 反而说明 Bitty 应该自己控制 module loader

这是一个很重要的地方。

Piccolo 并不是标准 PUC Lua runtime。它目前明确：

* `package` stdlib 尚不完整
* `io` / `os` 等部分不完整
* 不实现 Lua C API
* 不打算支持 `package.loadlib`
* 不追求加载传统 Lua C library

这其实正符合 Bitty 的 sandbox/plugin 思路。

所以我反而建议 **不要想办法模拟完整 LuaRocks runtime**。

直接让 Bitty 在 Rust 中实现自己的：

```text
ModuleResolver
```

然后给 Piccolo 注入：

```lua
require(...)
```

---

## 4. Bitty 可以有自己的 Resolver Chain

例如：

```text
require("foo")
       │
       ▼
┌────────────────────────┐
│ Bitty Module Resolver  │
├────────────────────────┤
│ 1. plugin local        │
│ 2. plugin dependencies │
│ 3. framework packages  │
│ 4. Bitty stdlib        │
│ 5. vendored Lua libs   │
└────────────────────────┘
```

例如：

```lua
local ui = require("bitty.ui")
local tool = require("wheel.tool")
local json = require("json")
```

Rust Core 实际上负责：

```text
name
 ↓
resolve
 ↓
source
 ↓
Piccolo compile
 ↓
module cache
 ↓
Lua value
```

于是完全不需要：

```text
package.path
package.cpath
.so
.dll
Lua C API
```

甚至这些东西最好明确禁止。

---

# 5. 这样 Bitty Plugin 可以是自包含 package

我非常推荐最终做自己的 Plugin artifact。

例如暂时叫：

```text
.bpkg
```

或者任何以后确定的格式。

内部：

```text
wheel-ui.bpkg
│
├── bitty-plugin.toml
├── lua/
│   ├── init.lua
│   ├── ui.lua
│   └── components/
│
├── vendor/
│   ├── xxx/
│   └── yyy/
│
├── assets/
│   ├── icons/
│   └── themes/
│
└── LICENSE
```

安装的时候：

```bash
bitty plugin add wheel-ui
```

下载的是一个**已经解析好 Lua dependencies 的 artifact**。

Bitty runtime 不需要现场跑：

```text
Lux
LuaRocks
Git
compiler
```

直接加载即可。

这对：

* reproducibility
* startup speed
* security
* offline
* sandbox
* version consistency

都更好。

---

# 6. Lux 最适合放到“开发/打包阶段”

例如 Plugin 开发者：

```text
wheel-ui/
├── bitty-plugin.toml
├── lux.toml
├── lux.lock
└── lua/
```

开发阶段：

```bash
lux add some-library
```

然后：

```bash
bitty plugin build
```

Bitty SDK 可以调用 Lux 或读取其 dependency tree：

```text
lux resolve
     ↓
vendor pure Lua dependencies
     ↓
bitty plugin pack
     ↓
wheel-ui.bpkg
```

用户最终安装：

```bash
bitty plugin add wheel-ui
```

**不需要安装 Lux。**

这类似：

```text
Cargo → build Rust program → user 不需要 Cargo

Lux → build Bitty Plugin → user 不需要 Lux
```

我认为这是 Lux 最适合 Bitty 的定位。

---

# 7. 而且只允许一个非常明确的 Lua dependency subset

因为 Piccolo 和标准 Lua runtime 不完全相同。

可以定义：

```text
Bitty Lua Package Profile
```

比如：

```text
✅ pure Lua
✅ no C extension
✅ sandbox compatible
✅ no arbitrary os.execute
✅ no package.loadlib
✅ no native .so/.dll
✅ compatible Lua language level
```

于是一个 Lux package：

```text
pure Lua
```

可以直接 vendor。

如果一个 LuaRocks package 依赖：

```text
libsqlite3.so
libcurl.so
native C module
```

Bitty Plugin Manager 就拒绝：

```text
unsupported native Lua dependency
```

如果真的需要 SQLite：

```text
Lua Plugin
    ↓
bitty.storage / sqlite service
    ↓
Rust implementation
```

而不是：

```text
Lua
 ↓
C module
 ↓
sqlite
```

这样 sandbox 会干净得多。

---

# 8. Plugin Manifest 应该由 Bitty 自己定义

例如：

```toml
manifest_version = 1

[plugin]
name = "wheel-ui"
version = "0.4.0"
entry = "lua/init.lua"

[compat]
bitty = ">=0.5"
wheel = ">=0.3"

[provides]
services = [
    "wheel.ui@1"
]

[requires]
services = [
    "wheel.agent@1",
    "bitty.ui@1"
]

[dependencies.plugins]
bitty-ui = "^1.2"

[permissions]
panel = true
filesystem = "project"
network = false
process = false
```

这里完全不要让 Lux 管：

```text
permissions
services
capabilities
Panel
IPC
Wheel compatibility
```

这些属于 Bitty。

---

# 9. Lua dependency 则继续由 Lux 表示

例如：

```toml
# lux.toml

[package]
name = "wheel-ui"

[dependencies]
some-parser = "^2.0"
some-util = "^1.4"
```

然后构建：

```text
bitty-plugin.toml
        │
        │ Bitty-specific
        ▼

lux.toml
        │
        │ Lua dependency
        ▼

lux.lock
```

不建议强行把二者合成一个超大 manifest。

因为它们属于不同 abstraction level。

---

# 10. 但 CLI 可以完全统一

这是最关键的 UX。

用户不用知道这些内部区别：

```bash
bitty plugin add wheel
bitty plugin add wheel-models
bitty plugin add wheel-ui

bitty plugin update
bitty plugin sync
bitty plugin doctor
bitty plugin list

bitty plugin enable foo
bitty plugin disable foo

bitty plugin info foo
bitty plugin permissions foo
```

内部：

```text
bitty plugin add
        │
        ├── resolve plugin
        ├── resolve plugin dependencies
        ├── verify compatibility
        ├── verify hash/signature
        ├── unpack artifact
        ├── register capabilities
        └── configure Piccolo loader
```

所以：

> **Package manager 是需要的，但应该是 Bitty Plugin Manager，而不是直接暴露 Lux。**

---

# 11. 还可以形成两级 lock

我反而不建议只有一个 giant lockfile。

可以是：

```text
Bitty level
───────────
plugin.lock

wheel-ui 0.4.0
bitty-ui 1.3.2
wheel-models 0.8.1
```

Plugin 自己构建时：

```text
Lua level
─────────
lux.lock

foo 1.2.4
bar 2.7.1
```

发布 artifact 后：

```text
wheel-ui@0.4.0
    ↓
已经包含固定版本的 Lua dependencies
```

用户机器就只需要第一层。

这会非常干净。

---

# 12. `.wheel/` 不应该直接拥有安装权

这里还有一个安全边界非常重要。

例如项目：

```text
.wheel/
└── plugins.lua
```

可以声明：

```lua
return {
    requires = {
        "wheel-tools-rust",
        "wheel-git",
    }
}
```

但打开一个 Git repository 时，Bitty **不能因为看到这个文件就自动下载并执行 Plugin**。

应该变成：

```text
Project requests:
  wheel-tools-rust
  wheel-git

Install / enable these plugins?
```

用户 trust 以后：

```text
project requirements
        ↓
installed plugin set
        ↓
permission policy
        ↓
execution
```

这和 `.env`、shell script 等安全问题类似。

否则：

```bash
git clone malicious-repo
cd malicious-repo
```

就可能间接执行第三方 Lua Plugin，这肯定不行。

---

# 13. 最终可以变成三层

我认为现在整个生态可以正式抽象成：

```text
               Bitty Package System
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
 Plugin Manager    Lua Resolver    Service Registry
       │               │               │
 install/update      require()      runtime wiring
 enable/disable      modules        Lua ↔ Lua
 permissions         vendor         Lua ↔ Rust
 versions            cache          IPC
       │               │               │
       └───────────────┼───────────────┘
                       ▼
                    Piccolo
```

其中：

**Plugin Manager**

```text
Bitty 自己实现
```

**Lua Resolver**

```text
Bitty/Piccolo 自己控制 runtime
Lux 可以负责 development/build dependency resolution
```

**Service Registry**

```text
负责 Plugin 之间调用
```

三者不要混成一个东西。

---

## 我会采用的方案

如果现在就开始设计，我会定成：

```text
Bitty Rust Core
│
├── Plugin Manager
│   ├── install
│   ├── update
│   ├── enable
│   ├── disable
│   ├── permissions
│   ├── dependency graph
│   └── lock
│
├── Piccolo Module Resolver
│   ├── require()
│   ├── module cache
│   ├── sandbox
│   └── vendored pure-Lua packages
│
└── Service Registry / IPC
```

外部开发生态：

```text
Lux
 │
 ├── lux.toml
 ├── lux.lock
 ├── resolve
 └── vendor
      │
      ▼
bitty plugin pack
      │
      ▼
.bpkg
```

这样以后即使 Lux：

* API 大改
* 被别的 package manager 替代
* Bitty 自己实现了更好的 resolver

**Bitty Plugin ABI 都不会受到影响。**

而且这也保持了你之前 Bitty 的方向：Core 不应该为了 Plugin 下载/解析而被迫绑定一大堆网络依赖；安装源完全可以继续优先建立在系统 Git / release artifact 之上。Lux 可以作为构建工具，而不是整个终端运行时的一部分。

我觉得最终最漂亮的一句话就是：

> **Bitty 管 Plugin，Lux 管 Lua dependency，Piccolo 执行 Lua，Service Registry 连接 Plugin。**

而你之前规划的 `bitty-plugins` 仓库/网站，正好可以再往前一步变成这个体系里的 **Plugin Registry / Index**，而不仅仅是一个展示插件的静态网站。
