你可以研究下现在的 AI Coding Agent 中哪些东西最会影响任务的完成质量、准确度这些方面呢？是过长的上下文吗？
我对这个上下文的理解是，系统提示词限制的有问题，比如有的 Harness 在内置提示词写的太死板，比如必须要要求使用现有的 MCP, Skills 等等，这样的话会导致 Agent 做一件小事情会调用很多次工作，这个部分我遇到最典型的就是 Codex 了，同样的任务在 Codex 中总是先检查现有的 MCP 和 Skills，并不是靠 LLM 本身的能力，就导致一件小题大做了。
然后就是过多分散注意力的上下文，虽然说现在的 LLM 都是 1M 的上下文，但是其实大多数时候在 Agent 中是用不到那么多的，很多 Harness 会设置上下文达到一个阈值进行压缩或者主动压缩，但是 LLM 的本质就是这样应该让上下文装有更有用、更与任务相关的内容，这样对于完成任务来说才能更加高效和准确吧。
也就是说很多时候，没必要的日志、冗余的输出、过长的 MCP 描述这些应该不需要吧，而且对于阅读代码和很多文档也不应该是全部一次性输入，一个代码文件可能有几千行甚至上万行，如果一次性输入一整个代码文件就会占用很多的上下文，要让一个 Agent 了解一个大型项目的话如果一个一个文件读的话就算是 1M 上下文都不够用的。
当然还有工具、MCP 之类的描述，我是见到过的，在 OpenCode 中是有很多工具，Agent 在调用工具的时候会调用的时候因为参数选择而失败的，比如 pty\_spawn[] 这种的，如果里面的各个参数输入不对的话，那么就会调用失败，这种失败就会影响做事情的效率了，很多 MCP 也是这样，我见过的 Agent 调用 MCP 的时候，十次里面大概是有两三次是失败的，尤其是在首次调用的时候。
Harness 部分设计和 Agent 表现能力应该是两个方面的吧，比如一个 Harness 设计的很好，但是内置提示词写的不好，所以会导致 Agent 使用这些 Harness 做事情的时候效率不高，当然也跟 LLM 本身有关，但是我觉得从今年开始各个 LLM 在 Agentic 上面其实表现的都是很好了，LLM 的能力一般都是够的，只是 Harness 和内置提示词或者一些部分设计的问题，我觉得可以设计的更好，比如在上下文中应该尽量保证是跟任务相关的部分，减少过多冗余和没有用的信息。
我记得在 Anthropic 刚出 MCP 的时候，大量的 MCP 出现了，这个其实还好，因为大家都知道一个 MCP 就是内置很多工具，然后 Agent 直接调用这些就可以做事情。但是在 Agent Skills 出现之后有个变化很大，就是一开始大家都知道 Skill 这个是一个非常有用的东西，但是呢这个就是一个包含了 SKILL.md 的文件夹，很多非计算机专业觉得这个 skill（中文为技能），就会觉得这个就像是一个能力扩展，我把这个 skill 加入到项目配置目录（如 .agents/, .claude/ ）或者全局配置目录后就不管了，因为很多人其实只知道这些：

- Skill 在 Agent 显示出来的其实就是 SKILL.md 中那个 Description 的内容，很多时候只是占用很小部分的 Token
- 一个 Skill 就是一个文件夹，方便配置、管理、传输，不像 MCP 配置还得自己手动编辑文件
- 配置了 Skill 很多任务会减少犯错

等等
但是他们不知道这些：

- Skill 只是显示给 Agent 看的是 Description，但是里面的内容可能非常大，我看很多的 SKILL.md 都是在 200 行以上的，而且很多 Skill 是带有 examples, prompts, references, scripts, workflows 等等目录的；而且做的不好的 Skill 可能这个 Description 都占用很多 Token，给描述的很多，什么时候得用，有什么好处等等，巴不得 Agent 调用这个
- Skill 里面可能有 scripts 目录，如果 Agent 不看这个里面的脚本而直接运行的话可能会很危险，比如会有投毒风险，这种案例已经出现了非常多了
- 很多 Skill 其实重复且没有必要，很多用户安装了大量的跟前端设计的 Skill，因为现在跟前端相关的 skill 非常多，跟设计有关的、跟前端设计规范有关的、跟安全相关的等等，然后用户就会安装很多，因为大多数时候用户安装的时候自己是不会看里面的内容的，他只知道这个 Skill 能做什么，有什么效果，但是不会关注这个 Skill 带有哪些信息量，是否跟别的 Skill 内容重叠等等。
- 在软件工程中是有依赖地狱的，但是我觉得现在已经有 Skill 地狱了，因为 Skill 太多，Agent 也不知道到底要调用哪些，因为如果是很多 Skill 的 Description 都写的差不多，重合度很高，那么 Agent 就不知道到底得调用哪个，对于 LLM 的角度来看就是把全部都调用试试，然后再挑更好的或者自己总计，这样就占用大量上下文了。

现在就是这种情况，在最开始 Skill 出现的时候大家都觉得好，其实 Skill 的出现就是正确的，只是不好的点在用户制作出 Skill 后是否有考虑很多东西，对很多制作者来说只要 Skill 达到了他的目的和效果那么就是好的 Skill，但是没有考虑完整的 Skill Token 占用，里面放的脚本是否安全等等问题。
所以就出现了最开始有很多整理 Skills 的仓库和网站，到了后面都成垃圾场了，如果用户真的想要自己找到合适的 Skill 都不是很好找。
而且这个投毒现象也非常严重，这个问题就因为 Skill 是很好传输和配置的，一个有毒的 skill 被打包成一个压缩包，或者跟着很多 skills 一起打包，比如“前端必备 Skills 合集”这种的，用户都不关心里面有哪些 skill，只知道这样很方便。而且现在 skill 是可以被售卖的，这里就不指出是哪些网站了，因为不止是网站，也可能作为商品出现在购物平台上售卖呢。这其实就是欺骗很多非计算机专业的受众，因为很多人都不知道 Markdown，不知道改配置，他们只需要花钱办事其实就可以了，但是作为专业人员来看这些事应该会不一样。

对于 Agent 来说，不仅是工作区里面的文件占用的 Context 会影响，我觉得很多时候影响注意力的是 Harness 和用户的配置，尤其是这个 Skill 地狱现象。

因为我现在就是 AI Coding 的重度用户了，是从最开始的 Cursor/Winsurf/GitHub Copilot/Kiro，到 Claude Code, Codex, OpenCode 到 Pi Agent, OpenClaw, Hermes Agent 都是用过的。我现在的开发，我都是只用很少的 Skill，比如全局的配置如 \~/.config/opencode, \~/.claude 这种的目录我的 Skill 很少，也就两三个，然后对于具体的项目就会在 Workspace 的根目录创建 .agents 目录，然后放一些相关的会用到的 skills，比如我会用 use-carryctx 这种的 skill。

这是因为 LLM 是知识库丰富的，他本身就有很多能力的，他知道写代码需要注意什么，遇到各种情况会怎么解决，他也会自己写脚本调用，他不知道的是项目的本身、项目的规则、新工具的使用，Skill 和 MCP 这种的只是 Agent 需要的时候才该用，而不是小题大做。

## 结论

你的判断基本抓住了现在 AI Coding Agent 最关键的问题，但我会把它进一步概括成一句：

> **Agent 的质量取决于 Model × Harness × Context × Tools × Verification，而不是 Context Window 的标称长度。**

尤其当模型已经进入当前这一代、基础 coding / reasoning 能力足够强之后，**同一个模型换一个 Harness，表现完全可能像换了一个模型**。SWE-agent 很早就专门提出了 ACI（Agent-Computer Interface）这个概念：文件怎么看、搜索结果怎么呈现、编辑工具怎么设计、错误怎么反馈，都会显著改变 Agent 表现。([数字对象标识符][1])

所以“是不是过长上下文最影响质量”，答案是：

**过长上下文本身不是第一根因；低信噪比上下文才是。**

# 我会怎么理解 Coding Agent 的质量公式

可以近似写成：

$$
Q \approx M \times C \times A \times V \times H
$$

其中：

| 因素                 | 含义                                                        | 常见失败            |
| ------------------ | --------------------------------------------------------- | --------------- |
| \(M\) Model        | 基础 reasoning / coding / tool-use 能力                       | 根本不会做、推理错误      |
| \(C\) Context      | 当前真正可利用的信息                                                | 漏约束、注意错信息、忘记目标  |
| \(A\) ACI / Tools  | Agent 与计算机交互接口                                            | 参数错误、选错工具、读文件低效 |
| \(V\) Verification | tests / compiler / browser / logs 等反馈                     | “代码看起来对，但实际上错”  |
| \(H\) Harness      | system prompt、loop、compaction、skills、memory、orchestration | 小题大做、死循环、过度探索   |

这里是**乘法而不是加法**比较贴切。

例如模型再强：

* 没有 test → 很容易自信地产生错误实现；
* 工具很难用 → 一直调用失败；
* Context 塞满垃圾 → 找不到真正约束；
* System Prompt 写死 → 明明自己知道怎么做，却被 Harness 强迫绕一大圈。

Anthropic Claude Code 团队甚至把 **Verification 称为最重要的一条实践**：让 Agent 能自己运行 tests、type checker、browser、runtime，再根据真实结果迭代。([Claude帮助中心][2])

OpenAI 自己 2026 年关于 Codex Harness 的总结也非常类似：他们发现早期瓶颈并不是“Codex 不够聪明”，而是环境、工具、结构和反馈闭环不足。([OpenAI][3])

# 1. 1M Context ≠ 1M Attention

这是最容易产生误解的地方。

模型声称支持：

```text
128K
200K
1M
2M
```

说的是：

> **最大可以接受多少输入。**

而不是：

> **这些 Token 都能够以完全相同的可靠度参与推理。**

早期的 *Lost in the Middle* 就发现，信息放在长上下文不同位置会造成明显性能差异。([MIT Direct][4])

后来 Chroma 2025 年的 *Context Rot* 又测试了 GPT-4.1、Claude 4、Gemini 2.5、Qwen3 等 18 个模型，观察到随着 Context 增长，即使简单任务也会越来越不稳定。([Chroma][5])

所以可以区分两个概念：

```text
Context Capacity
        ↓
“我最多装多少？”

Context Utility
        ↓
“这里面到底多少东西真的有用？”
```

真正应该优化的是第二个。

我甚至更倾向于设计一个指标：

$$
\text{Context Efficiency}
=
\frac{\text{Task-relevant information}}
{\text{Total active tokens}}
$$

例如：

```text
200K Context
其中真正相关：15K
```

往往不如：

```text
40K Context
其中真正相关：30K
```

后者不仅便宜、快，而且 Agent 通常更容易保持目标一致。

Anthropic 现在对 Context Engineering 的总结几乎就是这个方向：**寻找能够最大化任务成功率的最小 high-signal token set**。([Anthropic][6])

# 2. Context 最大的问题不是“大”，而是“污染”

你举的东西全部属于典型 Context Pollution：

```text
重复日志
完整 cargo build 输出
完整 npm install 输出
已经解决的 error stack
几千行无关代码
旧 diff
已经失败且确定放弃的方案
几十个 MCP Tool schema
几十个 Skill description
过度详细的 AGENTS.md
重复的 project instructions
Subagent 全量 transcript
```

这些东西都有一个共同问题：

> **它们曾经有用，但不意味着下一轮 inference 还需要它们。**

例如：

```text
cargo test
```

Agent 真正可能只需要：

```text
127 passed
2 failed

failures:
parser::tests::nested_expr
lexer::tests::unicode_escape
```

而不是 3000 行 stdout。

Anthropic 的 Context Engineering 文档就明确把 **tool result clearing** 当成最安全的一类 context optimization：历史深处的工具输出通常没必要永久保留，因为必要时可以重新调用。([Anthropic][6])

所以你之前 Bitty / Wheel 里提出的：

```text
cargo test
cargo build
cargo clippy
```

自动压缩成结构化结果，其实非常有价值。

不是为了省钱而省 Token。

而是：

> **让 Agent 的 working memory 保持干净。**

# 3. 代码阅读尤其不应该 `cat 10000 lines`

你说“大项目一个一个文件全部读取，1M 都不够”，完全正确。

真正合理的是：

```text
repository
    ↓
结构
    ↓
symbols
    ↓
references
    ↓
局部源码
    ↓
必要时继续展开
```

而不是：

```text
repository
    ↓
cat file1
cat file2
cat file3
cat file4
...
```

SWE-agent 做过非常有意思的 ACI 实验。他们发现 file viewer **每次只展示约 100 行**效果反而很好；repo search 也刻意只给简洁匹配结果，因为把每个匹配附近的大量文本都塞进去反而会让模型更混乱。([GitHub][7])

Aider 也长期使用 repo map：

```text
src/parser.rs
  struct Parser
  fn parse_expr(...)
  fn parse_statement(...)

src/lexer.rs
  struct Lexer
  fn next_token(...)
```

先让 Agent 建立项目 topology，再深入相关位置。([GitHub][8])

这其实正好吻合你以前给 Wheel / ctxctl 设计的 AST 阅读思路：

```text
Level 0  Repo tree
Level 1  Symbol index
Level 2  Signature / docs
Level 3  Relevant function
Level 4  Local surrounding code
Level 5  Whole file (rare)
```

这是比单纯扩大 Context Window 更值得做的东西。

# 4. 你提到的 Tool 参数失败，其实是非常大的 Harness 问题

例如：

```text
pty_spawn(...)
```

如果 schema 有：

```text
cwd
env
stdin
timeout
shell
interactive
capture
pty_size
...
```

然后每个：

* optional semantics 不清楚；
* default 不明确；
* enum 太多；
* 参数互相依赖；
* description 模糊；

LLM 就很容易：

```text
call
→ schema error
→ retry
→ different schema error
→ read tool docs
→ retry
```

这不是 LLM 不会 shell。

而是 **Agent API 设计得不好**。

Anthropic 专门写过一篇 *Writing effective tools for AI agents*，结论之一就是：

> tool description、参数命名、schema clarity 本身就可以显著影响 Agent success rate。

甚至只是改进 tool descriptions，就能明显降低错误。([Anthropic][9])

OpenAI Agents SDK 也直接推荐 strict JSON schema，因为它能提高正确参数生成概率。([OpenAI][10])

所以 Agent Tool 应该更接近：

```rust
pty_spawn {
    command: String,
    cwd?: Path
}
```

而不是一个万能：

```text
pty_spawn(
    command,
    args,
    cwd,
    shell,
    mode,
    stdin,
    stdout,
    stderr,
    interactive,
    timeout,
    env,
    size,
    ...
)
```

除非这些确实需要。

**Tool API 应该为 Agent 设计，而不应该只是把内部 API 原封不动暴露给 LLM。**

这就是 ACI 的意义。

# 5. MCP 数量确实会直接影响 Tool Selection

这里已经有非常具体的数据了。

Anthropic 的 Tool Search 文档指出，一个典型：

```text
GitHub
Slack
Sentry
Grafana
Splunk
```

组合，tool definitions 就可能吃掉约 **55K tokens**。

而且他们观察到：

> 超过大约 30–50 个 available tools 后，tool-selection accuracy 开始明显下降。

所以后来才做：

```text
Tool Catalog
      ↓
Tool Search
      ↓
3~5 relevant tools
      ↓
Active Context
```

而不是：

```text
200 MCP tools
      ↓
全部注入 System Prompt
```

([Claude Platform][11])

他们的内部 MCP eval 里，引入 Tool Search 后还观察到了明显的准确率提升。([Anthropic][12])

所以 MCP 正确的架构其实不应该是：

```text
Connect MCP
= expose everything
```

而应该是：

```text
MCP Registry
     ↓
capability discovery
     ↓
relevance ranking
     ↓
temporary activation
```

# 6. Skill 的 Progressive Disclosure 是正确设计，但并没有消灭 Skill Hell

这里我非常同意你的区分。

Agent Skill 本身其实设计得非常漂亮：

```text
Level 1
name + description
always loaded

Level 2
SKILL.md
triggered when relevant

Level 3
references / examples / scripts
loaded on demand
```

Anthropic 官方就是这样定义的。([Anthropic][13])

所以 Skill 本身没有问题。

问题是生态。

例如你安装：

```text
frontend-design
frontend-best-practices
ui-design
ui-ux
modern-web-design
react-best-practices
web-accessibility
design-system
beautiful-ui
frontend-security
```

然后 Description 都类似：

```text
Use this skill when designing or implementing frontend interfaces...
```

此时发生的是：

### Discovery collision

Agent 不知道应该选：

```text
A?
B?
C?
A+B?
B+C?
all?
```

### Instruction duplication

三个 Skill 都告诉你：

```text
use semantic HTML
avoid unnecessary JS
use responsive design
consider accessibility
...
```

同一信息重复进入 Context。

### Instruction conflict

A：

```text
prefer Tailwind
```

B：

```text
avoid utility CSS
```

C：

```text
use existing project conventions
```

### Trigger amplification

Skill A 加载以后提到某个概念，又诱发 Skill B。

然后：

```text
Skill A
→ references
→ Skill B
→ examples
→ Skill C
→ scripts
```

从几十 Token description 最后膨胀成几十 K。

所以：

> **Progressive Disclosure 解决的是“Skill 内容不用全部常驻”；没有自动解决“Skill discovery space 太大且高度重叠”。**

我觉得你说的 **Skill Hell** 可以正式定义成：

$$
\text{Skill Hell}
=
\text{Discovery Collision}
+
\text{Semantic Duplication}
+
\text{Instruction Conflict}
+
\text{Context Amplification}
+
\text{Supply-chain Risk}
$$

这和 Dependency Hell 非常类似。

只不过 Dependency Hell 冲突的是：

```text
version
ABI
dependency graph
```

Skill Hell 冲突的是：

```text
semantics
instructions
trigger conditions
authority
trust
```

# 7. 而 Skill Supply Chain 现在确实已经是真实安全问题

你说的 scripts 风险不是理论问题。

Anthropic 官方文档就提醒：

> 第三方 Skill 可以通过 instructions 和 executable code 诱导 Claude 调用工具或执行与 Skill 声称目的不一致的操作。

([Claude Platform][14])

2026 年 Snyk 的 ToxicSkills 研究扫描了 **3,984 个公开 Skills**：

* 534 个（13.4%）存在至少一个 critical-level issue；
* 1,467 个（36.82%）存在至少一种安全问题；
* 研究人员确认了 76 个恶意 payload，包括 credential theft、backdoor、data exfiltration。

([Snyk][15])

这里需要注意：这些数字针对他们扫描的特定公开 Skill corpus，**不能推导成“整个 Skill 生态 13.4% 都有恶意代码”**。但已经足以证明 supply-chain attack surface 是真实存在的。

MCP 也有类似问题。

Invariant Labs 2025 年展示了 **Tool Poisoning Attack**：恶意 MCP 可以把隐藏指令塞进 Tool description，而这些内容 Agent 能看到、用户 UI 未必能完整看到，从而诱导 Agent 访问敏感数据。([Invariant Labs][16])

因此：

```text
Skill
MCP
Plugin
Hook
```

未来都应该被理解为：

> **代码依赖 + instruction dependency**

而不只是“配置”。

# 8. System Prompt 过度规定行为，同样会让强模型变差

你说 Codex 那种：

```text
先检查 Skill
先检查 MCP
先调用工具
...
```

如果 Harness 把它写成强制 policy，那么确实会产生一种现象：

```text
“模型本来已经知道答案”
          ↓
Harness 要求先 discover
          ↓
search skills
          ↓
inspect MCP
          ↓
read docs
          ↓
execute
```

于是：

```text
简单任务 → Agent workflow
```

变成：

```text
简单任务 → enterprise workflow orchestration
```

这就是典型的 **over-scaffolding**。

好的 System Prompt 不应该描述：

```text
你每次应该怎么想
你每次第一步是什么
第二步是什么
第三步是什么
```

而更应该描述：

```text
Capabilities
Constraints
Safety boundaries
Decision principles
Environment invariants
```

把 tactic 留给模型。

有意思的是，OpenAI 自己现在公开的 Harness Engineering 总结也已经走向这一方向。

他们尝试过一个非常大的 `AGENTS.md`，后来认为失败，原因包括：

* context 被挤占；
* guidance 太多以后等同于没有 guidance；
* stale rules；
* Agent 很难判断什么才重要。

后来改成：

```text
AGENTS.md ≈ 100 lines
       ↓
Table of Contents
       ↓
structured docs/
       ↓
progressive disclosure
```

([OpenAI][3])

所以甚至 Codex 自己的工程团队最后也得出了：

> **Give the agent a map, not a 1,000-page instruction manual.**

这与你这里的判断实际上高度一致。

---

# 9. Harness 不应该告诉 Agent “必须使用能力”，而应该让能力“可发现”

这是一个很重要的设计哲学区别。

坏设计：

```text
You MUST inspect available skills before every task.
You MUST consider MCP tools.
You MUST use specialized tools whenever available.
```

这样会导致：

```text
Tool usage = obligation
```

我会更倾向：

```text
Native reasoning
      │
      ├── enough → directly solve
      │
      └── insufficient
              ↓
        capability discovery
              ↓
        Skill / Tool / MCP
```

也就是：

```text
Need-driven capability discovery
```

而不是：

```text
Capability-driven behavior
```

Skill 应该解决的是：

> “我不知道这个项目特殊的做法。”

不是：

> “如果没有 Skill，我不会写 React。”

MCP 应该解决：

> “我需要访问 GitHub/Jira/database。”

而不是：

> “既然有 GitHub MCP，我做任何 git 工作都必须先走 GitHub MCP。”

这也是为什么你全局只保留两三个 Skill、项目需要时才放 `.agents/`，其实是很健康的模式：**global layer 极薄，project layer 提供 domain-specific delta**。

---

# 10. Compaction 也不能只是“到 80% 就 summarize”

你也提到了很多 Harness 的：

```text
context > 80%
→ compact
```

这个机制是需要的，但很粗糙。

因为真正的问题不是：

```text
Token count
```

而是：

```text
information lifecycle
```

应该把 Context 内容分为：

```text
Ephemeral
tool stdout
temporary search result
compiler noise

Recomputable
file content
git status
directory tree

Important state
changed files
current goal
unresolved errors
decisions

Durable invariants
project architecture
user constraints
API contracts
```

然后分别处理：

```text
Ephemeral
→ drop

Recomputable
→ drop + pointer

Important state
→ structured memory

Durable invariants
→ persistent project knowledge
```

而不是所有东西：

```text
LLM summary
    ↓
LLM summary
    ↓
LLM summary
```

因为 repeated summarization 本身会有 information loss。

Anthropic 也明确指出 compaction 是 lossy 的，关键在于选择保留什么；他们推荐同时采用：

* compaction；
* structured note-taking；
* tool result clearing；
* 必要时 subagents。

([Anthropic][6])

---

# 11. Subagent 也遵循同样原则：不是越多越强

这一点和 Skill Hell 很像。

如果 Agent 看到复杂任务就：

```text
spawn 10 agents
```

不一定更好。

因为每个 Agent 都有：

```text
Context cost
Tool cost
Coordination cost
Result merge cost
Conflict risk
```

真正适合 Subagent 的是：

```text
独立 research
独立 code review
不同 hypothesis
不同 subsystem
并行 test
```

而不是：

```text
“帮我看看这个 20 行函数”
→ spawn 5 agents
```

所以在 Wheel 里我反而会把：

```text
spawn_agent
```

理解成 expensive primitive，而不是普通工具。

调用之前应该隐含一个判断：

$$
ExpectedParallelGain >
CoordinationCost
$$

这和你之前考虑的 Agent resource discipline——不要无意义地创建大量 Subagents、争抢 Panel / CPU / RAM / GPU——本质上是同一个问题。

# 我认为现在 Coding Agent 最值得优化的顺序

如果固定在“模型已经比较强”的前提下，我大致会这样看：

1. **Verification loop**
   Agent 是否真的能够知道“我做对了吗”。

2. **Context relevance / signal-to-noise**
   不是 Context 多大，而是里面有多少真正相关的信息。

3. **ACI / Tool ergonomics**
   搜索、读取、编辑、执行、Tool Schema 是否真正适合 LLM。

4. **Harness policy / System Prompt**
   是否提供原则，而不是把模型绑死在固定 workflow 上。

5. **Repository legibility / project knowledge**
   是否容易探索 architecture、symbols、docs、tests、logs。

6. **State / Memory / Compaction**
   是否保存决策和任务状态，而不是保存整个 transcript。

7. **Skill / MCP discovery quality**
   是否按需加载、去重、ranking、解决冲突。

8. **Orchestration**
   Planner、Subagent、Reviewer 是否真的在复杂任务才启用。

9. **Security / permissions / provenance**
   Skill、MCP、scripts、external content 是否可信。

10. **Model capability ceiling**
    到真正困难的 reasoning、新领域、复杂 architecture 时，模型差异仍然会重新成为主要因素。

这里不是严格的 benchmark 排名，因为不同任务会变化；但如果是设计一个 Coding Harness，我会按这个优先级投入工程资源。

# 最终其实可以浓缩成一种 Harness 哲学

我觉得 Wheel 如果以后真的要做成一个很强的 Coding Harness，最值得坚持的不是：

```text
给 Agent 尽可能多的能力
```

而是：

```text
给 Agent 尽可能少、但当前足够的东西
```

也就是：

```text
small core prompt
small active toolset
small active skillset
small high-signal context
rich discoverable environment
strong deterministic verification
durable structured state
```

可以画成：

```text
                ┌───────────────┐
                │ User Intent   │
                └───────┬───────┘
                        ↓
               ┌────────────────┐
               │ Minimal Core   │
               │ Prompt         │
               └───────┬────────┘
                       ↓
              ┌──────────────────┐
              │ Agent Reasoning  │
              └──────┬───────────┘
                     │ need?
        ┌────────────┼──────────────┐
        ↓            ↓              ↓
      Code        Skill          MCP/Tool
      Search      Discovery      Discovery
        │            │              │
        └────────────┼──────────────┘
                     ↓
              Relevant Context
                     ↓
                  Action
                     ↓
              Verification
                     ↓
           pass ───────── fail
            ↓                │
          Done ←─────────────┘
```

这里最重要的其实是中间那句：

> **Need?**

不是因为系统拥有一个 Skill、MCP、Subagent、Browser、LSP，就应该使用它。

而是 Agent 判断：

> **当前这一步是否真的缺少这种能力。**

我认为这反而是 2026 年 Harness 设计越来越明显的方向：**从 Prompt Engineering → Context Engineering → Harness Engineering，而 Harness Engineering 的目标不是控制一个愚蠢模型，而是避免妨碍一个已经很聪明的模型。** OpenAI、Anthropic 目前公开出来的 Harness / Context Engineering 经验，都已经明显朝这个方向收敛。([OpenAI][3])

# 我会把 Wheel 的核心目标改成：**让模型始终处在“最容易做对事情”的环境里**

如果 Bitty AI / Wheel 想真正做到比 Claude Code、Codex、OpenCode 这一类 Harness 更强，重点不应该是堆更多 Agent、Tools、Skills、MCP，而应该是：

> **模型负责 intelligence，Wheel 负责把正确的信息、正确的能力、正确的反馈，在正确的时候提供给模型。**

OpenAI 最近总结 Harness Engineering 时也明确提到，他们遇到的早期瓶颈往往不是 Codex “不会写”，而是环境、工具、repository knowledge 和 feedback loop 不够清晰。([OpenAI][1]) Anthropic 对 Context Engineering 的定义也很接近：目标是为每一次 inference 构造“能够最大化任务成功率的最小高信号 Context”。([Anthropic][2])

所以我认为 Wheel 最核心的技术，不应该叫 Prompt Engine，而应该是：

```text
Wheel
├── Context Compiler
├── Agent Runtime
├── Capability Runtime
├── Verification Runtime
├── State / Memory Runtime
├── Resource Scheduler
└── Evaluation Runtime
```

其中 **Context Compiler + Verification Runtime** 应该是最值得下功夫的两个部分。

# 一、首先把 Bitty Core 和 Wheel 分得非常清楚

这是整个架构最重要的边界。

我建议：

```text
┌──────────────────────────────────────────────┐
│                  Wheel                       │
│                                              │
│  Agent Loop       Context Compiler           │
│  Planner          Capability Resolver        │
│  Model Router     Verification               │
│  Memory           Multi-Agent Scheduler      │
│  Skills/MCP       Policy                     │
└───────────────────┬──────────────────────────┘
                    │ stable API
┌───────────────────▼──────────────────────────┐
│                Bitty Core                    │
│                                              │
│ Workspace / Panel / PTY / Process            │
│ Filesystem / Environment / IPC               │
│ Rendering / Input / Events                   │
│ Resource information                         │
│ Permissions / Sandbox primitives             │
└──────────────────────────────────────────────┘
```

Bitty Core 不应该知道：

> “这是 Claude 还是 GPT。”

也不应该知道：

> “这是 Planner Agent 还是 Reviewer Agent。”

Core 只负责提供**确定性的计算机能力**。

而 Wheel 把这些能力组合成 Agent Harness。

这样以后即使 Wheel 整套 Agent architecture 被推翻重写，Bitty Core 都不受影响。

这也非常符合你之前给 Bitty 定下来的“极小 Core + Lua plugin ecosystem”的方向。

# 二、Wheel 最重要的模块应该是 `Context Compiler`

我甚至认为这个名字非常适合。

现在很多 Harness 的工作方式其实还是：

```text
system prompt
+ conversation
+ tool results
+ file contents
+ skill content
+ MCP schemas
+ more tool results
+ more conversation
...
```

本质就是：

```text
append()
append()
append()
append()
```

直到：

```text
context > threshold
→ compact()
```

我认为 Wheel 不应该这么设计。

应该把 Context 当成一个**每轮重新编译出来的 View**。

也就是：

```text
                     ┌── System Policy
                     ├── User Intent
                     ├── Task State
                     ├── Project Rules
                     ├── Relevant Code
                     ├── Relevant Docs
Context Compiler ◄───┼── Relevant Skills
                     ├── Active Tools
                     ├── Current Diff
                     ├── Relevant Errors
                     ├── Decisions
                     └── Recent Actions
                           │
                           ▼
                    Active Context
                           │
                           ▼
                          LLM
```

模型永远不需要直接看到 Wheel 所知道的全部信息。

这是两个完全不同的概念：

```text
Wheel Knowledge
≠
LLM Active Context
```

Wheel 本地可能知道：

```text
Repository: 800 MB
Panel history: 3 GB
Session history: 200 MB
MCP schemas: 150 KB
Skills: 80 个
LSP index: millions of symbols
Git history: years
```

但当前一次 inference 可能只有：

```text
Core Prompt        4K
Task               2K
Task State         2K
Relevant Code     18K
Relevant Docs      3K
Tool Definitions   4K
Recent Results     4K
Reserve            ...
```

这才是真正好的 Harness。

Anthropic 现在也非常明确地推荐 just-in-time retrieval 和 progressive disclosure，而不是提前把所有潜在相关内容塞进去。([Anthropic][2])

# 三、Context 应该有生命周期，而不是只有“在 / 不在”

可以在 Wheel 内部给信息做这样的状态模型：

```text
                    ┌──────────────┐
                    │   Source     │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │   Indexed    │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │  Candidate   │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │   Active     │
                    └──────┬───────┘
                           ↓
              ┌────────────┴───────────┐
              ↓                        ↓
         Retained                  Evicted
              │                        │
              ↓                        ↓
       Structured State          Re-fetchable
```

例如：

```text
cargo test 原始 3000 行
```

可能只存在于：

```text
Panel Event Store
```

模型 Active Context 里只有：

```text
cargo test failed

2 failures:
- parser::nested_expression
- lexer::unicode_escape

Relevant diagnostics:
...
```

如果模型说：

> 给我看 `parser::nested_expression` 的完整 backtrace。

Wheel 再去拿。

这比：

```text
“先全塞进去，说不定之后有用”
```

合理得多。

# 四、Bitty 本身会给 Wheel 一个其他 Harness 很难复制的优势

因为 Bitty 是 Terminal Emulator 本身。

Claude Code / Codex / OpenCode 通常只能：

```text
LLM
 ↓
shell tool
 ↓
spawn subprocess
 ↓
capture stdout
```

而 Wheel 可以做到：

```text
LLM
 ↓
Wheel
 ↓
Bitty Runtime
 ├── Panel
 ├── PTY
 ├── Process
 ├── Environment
 ├── CWD
 ├── Workspace
 ├── command lifecycle
 └── structured events
```

例如不需要让 Agent 执行：

```bash
pwd
```

Wheel 本来就知道。

不需要：

```bash
ps aux | grep cargo
```

Bitty 本来就知道哪个 Process 属于哪个 Panel。

不需要：

```bash
echo $FOO
```

如果你之后把 Panel Environment 做成结构化状态，Wheel 可以直接读取。

甚至：

```text
Agent:
这个 cargo test 还在执行吗？
```

不需要调用 shell。

Wheel 可以直接得到：

```text
process_id: 18293
panel: headless:7
state: running
elapsed: 42s
cpu: 680%
memory: 2.1GB
```

这会极大减少：

```text
LLM → shell → parse text → infer state
```

这种脆弱链路。

# 五、代码阅读应该变成一个真正的 `Code Intelligence Layer`

这是我认为 Wheel 可以明显做得比很多现有 Harness 更好的地方。

不要把核心文件工具设计成：

```text
read_file(path)
```

然后让 Agent：

```text
read 10000 lines
```

应该做成分层认知：

```text
Repo
 ↓
Tree
 ↓
Module Map
 ↓
Symbol Map
 ↓
References / Callers / Implementations
 ↓
Relevant Region
 ↓
Exact Source
```

例如 Agent 问：

> `Panel` 生命周期在哪里处理？

Wheel 可以先返回：

```text
Symbol matches

bitty-core/src/panel/mod.rs
  struct Panel
  impl Panel
    new()
    close()
    attach()
    detach()

bitty-core/src/workspace.rs
  Workspace::create_panel()
  Workspace::remove_panel()

bitty-core/src/runtime/panel_manager.rs
  PanelManager::spawn()
  PanelManager::terminate()
```

Agent 再选择：

```text
inspect_symbol("PanelManager::terminate")
```

然后才得到 80 行代码。

SWE-agent 的 ACI 实验甚至发现，专门的文件 viewer 每次只展示约 100 行，以及 repository search 尽量只返回简洁匹配，比大量返回附近上下文更容易让模型正确工作。([GitHub][3])

所以 Wheel 可以组合：

```text
Tree-sitter
LSP
ripgrep
git
filesystem metadata
```

得到一个非常优秀的：

```text
Code Intelligence API
```

你之前 ctxctl 那种 AST 快速阅读思路在这里就非常合适。

# 六、Tools 不应该等价于底层 API

这个特别重要。

Bitty Core 可能有：

```rust
spawn_process(options: SpawnOptions)
```

其中：

```text
stdin
stdout
stderr
cwd
env
pty
rows
cols
shell
detach
timeout
...
```

但绝对不要原封不动暴露成 Agent Tool。

Agent 看到的应该可能只是：

```text
run(command)
run(command, cwd)
```

而 Wheel 自己决定：

```text
PTY?
timeout?
capture?
panel?
shell?
```

只有高级操作才暴露：

```text
run_interactive()
```

Anthropic 对 Agent Tool 的研究也得出了类似结论：工具应该针对 Agent 的认知方式重新设计，而不是简单把传统 API endpoint 一个个包装成工具；工具重叠和模糊 schema 会显著增加调用错误。([Anthropic][4])

因此 Wheel Tool API 应该遵守一个原则：

> **Expose intent, hide plumbing.**

比如：

```text
坏：

process_spawn()
pty_spawn()
pty_write()
pty_resize()
pty_read()
process_wait()
process_kill()
```

对于很多 Agent 场景，更好的可能是：

```text
run()
run_interactive()
inspect_process()
stop_process()
```

底层复杂性由 Wheel 处理。

# 七、不要让所有 Tools / MCP / Skills 常驻 Context

我会给 Wheel 做一个统一概念：

```text
Capability
```

Capability 可以来自：

```text
Native Tool
Skill
MCP
Plugin
Provider
External Agent
```

Wheel 内部维护：

```text
Capability Registry
```

但模型看到的是：

```text
Active Capability Set
```

例如整个 Bitty 安装可能拥有：

```text
312 tools
84 skills
17 MCP servers
```

但用户说：

> 修一下这个 Rust parser bug。

当前模型可能只有：

```text
code.search
code.inspect
code.edit
process.run
git.diff
test.run

use-carryctx
```

就够了。

如果 Agent 后来发现：

> 需要查询 GitHub Issue。

才：

```text
discover("github issue")
```

然后临时暴露：

```text
github.issue.get
github.issue.comments
```

Anthropic 当前对 Context Engineering 的建议也是：避免 bloated tool sets，并尽量让工具具有清晰且互不重叠的职责。([Anthropic][2])

# 八、Skill 应该做一个 Resolver，而不是“有 Description 就完事”

这一点我认为 Wheel 完全可以做成非常有特色的功能。

比如安装：

```text
frontend-design
ui-design
frontend-best-practices
beautiful-ui
react-ui
```

Wheel 在 registry 阶段就可以计算：

```text
Semantic overlap
Trigger overlap
Instruction overlap
Trust
Token footprint
Script presence
Source
Version
```

得到：

```text
frontend-design
overlap:
  ui-design                 0.87
  beautiful-ui              0.81
  react-ui                  0.54
```

然后不是五个 Skill 一起扔给模型。

而是在真正需要前端设计的时候：

```text
Skill Resolver
      ↓
task semantics
      ↓
candidate skills
      ↓
deduplicate
      ↓
rank
      ↓
activate 1~2
```

甚至可以警告：

```text
⚠ frontend-design and ui-design have highly overlapping triggers.
```

这就是针对你前面提到的 **Skill Hell** 的直接工程解决方案。

# 九、Skill 和 MCP 还必须有 Trust Model

我建议 Capability metadata 里直接设计：

```rust
struct CapabilityMeta {
    id: CapabilityId,
    source: Source,
    trust: TrustLevel,
    permissions: PermissionSet,
    token_cost: TokenEstimate,
    side_effects: SideEffects,
    network: bool,
    executable: bool,
}
```

然后：

```text
Built-in
    ↓
Trusted

Official plugin
    ↓
Trusted / signed

User local
    ↓
User trusted

Third-party
    ↓
Untrusted

Downloaded Skill bundle
    ↓
Untrusted
```

尤其 Skill：

```text
SKILL.md
scripts/
references/
examples/
```

这些必须分开看。

比如：

```text
Read SKILL.md        allowed
Read references      allowed
Execute scripts      requires policy
Network              requires permission
Read ~/.ssh          denied
Read .env            denied/default prompt
```

这样 Skill 就不会拥有一个隐含的：

```text
“因为用户安装了，所以里面任何东西都可信”
```

权限。

---

# 十、Agent System Prompt 要非常小，而且不能规定具体 Workflow

Wheel Core Prompt 我认为可以控制到相当紧凑。

它应该告诉模型的主要只是：

```text
You are operating inside Bitty.

Environment:
- workspaces contain panels
- panels may be headed or headless
- tools provide structured access to code/processes
- additional capabilities may be discovered when needed

Principles:
- solve the user's task directly
- retrieve context only when needed
- prefer verification over assumption
- avoid unnecessary tool calls
- preserve existing project conventions
- minimize destructive actions
```

而不要写：

```text
Step 1: always inspect skills
Step 2: always search MCP
Step 3: inspect repository
Step 4: formulate plan
Step 5: ...
```

Anthropic 也专门指出 System Prompt 最合适的“高度”处于两个极端中间：既不能是大量 brittle if/else workflow，也不能模糊到毫无约束。([Anthropic][2])

我认为真正好的 Wheel Core Prompt 甚至应该随着模型越来越强而**越来越小**。

---

# 十一、`Verification Runtime` 应该是一等公民

这是另一个决定 Wheel 质量的核心。

现在很多 Agent 是：

```text
write code
↓
run test
↓
maybe done
```

Wheel 应该明确建立：

```text
Action
 ↓
Expected Outcome
 ↓
Verification
 ↓
Evidence
 ↓
State Transition
```

例如修改 Rust：

```text
edit
 ↓
rustfmt
 ↓
syntax / rust-analyzer diagnostics
 ↓
targeted test
 ↓
broader test
 ↓
git diff inspection
```

修改 Web：

```text
edit
 ↓
typecheck
 ↓
lint
 ↓
test
 ↓
browser/runtime verification
```

而且 Verification 应该是**Harness 能力**，不是 System Prompt 里一句：

```text
Remember to run tests.
```

最好由 project adapter 推断：

```text
Cargo.toml
→ RustProjectVerifier

package.json
→ NodeProjectVerifier

pyproject.toml
→ PythonProjectVerifier
```

这样 Agent 不需要自己每次重新发现：

```text
这个项目怎么 lint？
怎么 test？
怎么 typecheck？
```

---

# 十二、将 Agent 的“想法”和任务状态彻底分离

不要把：

```text
conversation transcript
```

当作：

```text
task state
```

Wheel 应该有明确的 structured state：

```yaml
goal: fix unicode lexer bug

status: implementing

files:
  inspected:
    - src/lexer.rs
    - tests/lexer.rs
  modified:
    - src/lexer.rs

decisions:
  - preserve current lexer state machine
  - handle unicode escape during string parsing

open_questions:
  - invalid surrogate behavior

verification:
  targeted_tests: passed
  full_tests: pending
```

这才是 Agent 真正应该跨 Context 保存的东西。

Conversation：

```text
可丢弃
```

State：

```text
不可丢弃
```

---

# 十三、因此 `/compact` 可以变成一个更高级的机制

Wheel 不应该只是：

```text
conversation → LLM summary
```

而应该：

```text
                 Conversation
                     │
        ┌────────────┼─────────────┐
        ↓            ↓             ↓
    Decisions     Evidence     Ephemeral
        │            │             │
        ↓            ↓             X
 Task State       Artifacts       drop
        │
        ↓
fresh context
```

甚至大部分情况下：

**不需要等到 Context 快满才做。**

每完成一个阶段：

```text
exploration
implementation
verification
```

都可以进行 lifecycle cleanup。

这叫：

```text
continuous context hygiene
```

我觉得比传统 `/compact` 更重要。

---

# 十四、Panel 和 Agent 生命周期一定不要绑定

这一点你之前已经考虑得非常对。

Wheel 应该是：

```text
Agent
  │
  ├── attach Panel A
  │
  ├── spawn headless Panel B
  │
  ├── release B
  │
  └── attach Panel C
```

而 Panel：

```text
Panel
  │
  ├── Agent A
  ├── User
  └── Agent B
```

应该可以跨生命周期复用。

所以：

```text
Agent != Process
Agent != Panel
Agent != Workspace
```

它们是独立实体：

```text
Task
Agent
Workspace
Panel
Process
Session
```

只建立关联。

这对于以后 multi-agent 非常重要。

# 十五、Subagent 不应该是“模型想开多少就开多少”

Wheel 应该有真正的 Scheduler。

例如：

```text
Agent requests:
spawn researcher
```

Wheel Scheduler 判断：

```text
current task complexity
active agents
CPU
RAM
GPU
rate limits
provider cost
workspace conflicts
```

最后：

```text
allow
queue
reuse
deny
```

Subagent 最理想的返回也不是整段 transcript：

```text
Agent B transcript: 80K
↓
Agent A context
```

而应该是：

```yaml
result:
  conclusion: ...
  evidence:
    - ...
  files:
    - ...
  confidence: ...
  unresolved:
    - ...
```

详细 transcript 留在存储里，需要时再查看。

---

# 十六、Model Provider 也不要进入 Agent architecture

Wheel 应该定义统一：

```text
Model Capability
```

而不是：

```text
ClaudeAgent
GPTAgent
GeminiAgent
```

例如：

```rust
ModelProfile {
    context_window,
    reasoning_levels,
    tool_calling,
    structured_output,
    vision,
    caching,
    pricing,
    latency,
}
```

然后 Agent 只是：

```text
Agent
  model = ModelRef
```

这样你之前说的 OpenAI / Anthropic / Gemini / Bedrock / Vertex / OpenRouter / subscription-backed providers，都只属于 **LLM Provider Plugin**。

Agent Runtime 不关心。

这会让 Wheel 的 architecture 非常干净。

# 十七、Wheel 必须从第一天就建立 Eval

这是我尤其建议你做的。

Anthropic 做 Agent Tools 的建议其实非常工程化：不仅测最终成功率，还应该记录 tool errors、tool-call count、runtime、token consumption 等，再据此改 schema 和 descriptions。([Anthropic][4])

Wheel 可以长期保存：

| Metric                 | 用途                       |
| ---------------------- | ------------------------ |
| task success           | 最核心结果                    |
| unnecessary tool calls | 判断是否小题大做                 |
| tool failure rate      | ACI 是否差                  |
| context tokens / turn  | Context efficiency       |
| duplicated context     | Context pollution        |
| skill activations      | Skill Resolver 表现        |
| wrong skill activation | Skill precision          |
| MCP failures           | MCP ergonomics           |
| test retries           | implementation stability |
| context compactions    | long-horizon stability   |
| agent spawns           | orchestration cost       |
| wall time              | 效率                       |
| provider cost          | 成本                       |

以后你修改：

```text
Tool schema
Core Prompt
Skill Resolver
Context Compiler
```

不能靠：

> “感觉现在 Agent 更聪明了。”

而应该直接跑：

```text
wheel eval
```

比较：

```text
v0.4.0
vs
v0.5.0
```

这会是 Wheel 长期真正建立竞争力的地方。

## 如果让我给 Wheel 定一条最高设计原则

不是：

> **让 Agent 能调用所有东西。**

而是：

> **让 Agent 在每一步只看到完成当前决策所需要的最少高质量信息，并让任何重要行动都能获得可靠反馈。**

于是整个设计自然会导向：

```text
Small core prompt
        +

Small active context
        +

Small active capability set
        +

Rich discoverable environment
        +

Strong structured state
        +

Strong verification
        +

Deterministic Bitty substrate
```

这恰好能够避开现在很多 Harness 正在出现的问题：**Prompt 越来越长、Tools 越来越多、Skills 越来越多、MCP 越来越多、Agent 越来越多，最后模型本身反而被 Harness 淹没。**

我认为如果 Wheel 把 **Context Compiler、Capability Resolver、Code Intelligence、Verification Runtime、Structured Task State** 这五块做好，它真正的竞争力甚至不会来自“支持 GPT / Claude / Gemini 哪一个最好”，而会变成：

> **同一个模型放进 Wheel，为什么比放进普通 Harness 更容易把事情一次做对。**

这才应该是 Wheel 最核心的性能指标。
