既然这直接这么都是 Lua，那么插件之间相互调用的时候代码中得怎么调用呢？如果跨仓库的话得怎么做呢？是需要封装吗？

需要封装，而且我会强烈建议：**不要让跨仓库 Plugin 通过文件路径直接 `require()` 对方源码**。

更合适的是分成三层：

```text
Lua module import
    ↓
Plugin public API
    ↓
Service / IPC proxy
```

同一个插件仓库内部，可以正常 `require()`；跨插件、跨仓库时，只调用对方公开的 API。

## 1. 同一个插件内部：正常 `require`

比如：

```text
wheel-models/
├── init.lua
├── provider/
│   ├── openai.lua
│   └── anthropic.lua
└── registry.lua
```

内部完全可以：

```lua
local Registry = require("wheel_models.registry")
local OpenAI = require("wheel_models.provider.openai")
```

这是普通 Lua module dependency，没有问题。

---

## 2. 跨插件不要这样做

例如 `wheel-ui` 想调用 `wheel-models`。

不推荐：

```lua
local models = require("../wheel-models/models")
```

或者：

```lua
package.path = package.path .. ";/some/plugin/path/?.lua"
```

这种设计的问题很多：

* 强耦合仓库目录结构
* Plugin 移动位置就炸
* 版本管理困难
* 无法跨 process
* 无法做权限控制
* 无法 lazy load
* 无法替换实现
* 很难支持多个实现

所以 `wheel-ui` 不应该知道 `wheel-models` 的代码放在哪里。

---

# 3. Plugin 应该声明一个 public service

例如 `wheel-models`：

```lua
return {
    name = "wheel-models",
    version = "1.2.0",

    provides = {
        "wheel.models",
    },

    setup = function(ctx)
        ctx.services.register("wheel.models", {
            list = function()
                -- ...
            end,

            resolve = function(name)
                -- ...
            end,

            generate = function(req)
                -- ...
            end,
        })
    end,
}
```

这样它公开的是：

```text
wheel.models
```

而不是：

```text
github.com/bitty-terminal/wheel-models/src/models.lua
```

这其实很像动态链接中的 symbol/interface。

---

## 调用方只拿 Service

比如 `wheel-ui`：

```lua
local models = bitty.services.get("wheel.models")

local available = models:list()

local response = models:generate({
    model = "gpt-5.6",
    messages = messages,
})
```

UI 并不知道：

```text
wheel.models
```

背后到底是：

```text
wheel-models 官方插件

用户自己写的 models 插件

remote daemon

另一个 Panel

甚至 Rust implementation
```

只要符合这个接口即可。

---

# 4. 最好不要直接返回裸 Lua table

实际上再进一步，我会建议做一层 **typed-ish contract / SDK**。

例如官方定义：

```lua
-- wheel/sdk/models.lua

---@class WheelModels
---@field list fun(): WheelModel[]
---@field resolve fun(name: string): WheelModel?
---@field generate fun(req: GenerateRequest): GenerateResponse
---@field stream fun(req: GenerateRequest, callback: fun(chunk: Chunk))
```

然后插件实现：

```lua
local Models = {}

function Models:list()
    ...
end

function Models:generate(req)
    ...
end

return Models
```

调用方：

```lua
local models = wheel.service("models")
```

这样 IDE / LuaLS 也可以得到 type hint。

这非常值得做。

因为否则 Lua Plugin 多起来以后，很容易变成：

```text
某插件说返回 foo
另一个插件以为返回 bar
```

最后全靠文档猜。

---

# 5. 跨仓库靠 Manifest 声明依赖

例如：

```text
wheel-ui/
wheel-models/
wheel-dashboard/
```

分别是三个 Git repository。

`wheel-ui` 的 manifest：

```lua
return {
    name = "wheel-ui",

    requires = {
        ["wheel"] = ">=1.0",
        ["wheel.models"] = ">=1.0",
    },
}
```

或者拆成：

```lua
dependencies = {
    "wheel",
}

services = {
    required = {
        "wheel.models@1",
    },
}
```

这里我反而更喜欢 **依赖 capability/service，而不是依赖具体插件名**。

不要：

```lua
requires = {
    "wheel-models",
}
```

而是：

```lua
requires = {
    "wheel.models@1",
}
```

因为可能有：

```text
wheel-models
openrouter-models
company-model-gateway
local-ollama-models
```

都能提供：

```text
wheel.models@1
```

于是 UI 不在乎哪个实现。

# 6. 这其实应该区分「Plugin dependency」和「Service dependency」

非常重要。

例如：

```lua
plugin_dependencies = {
    "wheel >= 1.0",
}
```

表示：

> 我必须安装这个 Plugin。

而：

```lua
service_dependencies = {
    "wheel.models@1",
}
```

表示：

> 我需要某个 Plugin 提供这个能力。

后者会灵活很多。

比如：

```text
wheel-dashboard
        │
        ├── wheel.agents
        ├── wheel.models
        ├── wheel.metrics
        └── bitty.panels
```

Dashboard 根本不用知道这些能力分别来自哪个仓库。

# 7. 同进程调用和跨进程调用可以统一

这里就是你 Bitty IPC 很适合发挥作用的地方。

调用者：

```lua
local models = bitty.services.get("wheel.models")

models:generate(req)
```

如果 provider 在当前 Lua runtime：

```text
wheel-ui
   │
   ▼
Service Registry
   │
   ▼
wheel-models
```

本质可能直接：

```lua
implementation.generate(req)
```

开销很小。

如果它运行在另一个 Process / Panel：

```text
wheel-ui
   │
   ▼
Service Proxy
   │
   ▼
Bitty IPC
   │
   ▼
wheel-models
```

但对于调用者仍然可能是：

```lua
models:generate(req)
```

这就是 **location transparency**。

# 8. 不过跨 IPC 最好明确 async

这里要注意一个坑。

Lua 本地调用：

```lua
local x = service:get()
```

可能立即返回。

但是跨 IPC：

```text
process A
→ IPC
→ process B
→ IPC
→ process A
```

肯定不能假装成本地同步函数，否则很容易 block 整个 UI/event loop。

所以我建议从一开始 Service API 就 async-first。

例如：

```lua
local result = await(models.generate({
    model = "...",
}))
```

或者：

```lua
models:generate(req):await()
```

甚至：

```lua
models:generate(req)
    :then_(function(result)
        ...
    end)
```

如果 Piccolo 有 coroutine，就非常适合：

```lua
local response = coroutine.await(
    models:generate(req)
)
```

这样本地服务和 remote 服务都保持相同语义。

# 9. Streaming 更需要标准化

尤其 LLM Plugin。

不要让各个 provider 自己定义 streaming。

统一：

```lua
local stream = models:stream({
    model = "claude-sonnet",
    messages = messages,
})

for event in stream do
    if event.type == "text_delta" then
        ...
    elseif event.type == "tool_call" then
        ...
    elseif event.type == "usage" then
        ...
    end
end
```

底层可能来自：

```text
OpenAI SSE
Anthropic SSE
Gemini stream
local Ollama
remote IPC
```

全部转换成 Wheel 的标准事件：

```text
start
text_delta
reasoning_delta
tool_call_start
tool_call_delta
tool_call_end
usage
finish
error
```

这其实就是 API abstraction。

看到：

# 我更推荐形成这套层次

```text
Git Repository
      │
      ▼
Plugin Package
      │
      ├── private Lua modules
      │
      └── public capabilities
                │
                ▼
        Service Registry
                │
        ┌───────┴────────┐
        │                │
     local             remote
        │                │
 direct Lua          IPC Proxy
        │                │
        └───────┬────────┘
                ▼
            Consumer
```

对应代码层面：

```lua
-- 不推荐
require("../wheel-models/src/provider")

-- 推荐
local models = wheel.services.require("models@1")
```

然后：

```lua
local result = models.generate(req):await()
```

## 甚至可以像 Rust trait 一样理解

你可以把：

```text
wheel.models@1
```

理解成：

```rust
trait ModelService {
    async fn list(&self) -> Vec<Model>;
    async fn generate(&self, req: Request) -> Response;
    fn stream(&self, req: Request) -> Stream<Event>;
}
```

Plugin 是 implementation：

```text
wheel-models
    implements wheel.models@1
```

然后 consumer 只依赖：

```text
wheel.models@1
```

而不是具体实现。

这其实会让 Wheel 的 Lua Plugin architecture 非常像：

```text
Rust traits
+
dynamic plugin system
+
microservice Service Discovery
+
Unix composability
```

## 我建议最终定一个非常简单的用户 API

最好让 Plugin 作者只需要记这几个：

```lua
-- 注册
ctx.services.provide("wheel.models@1", impl)

-- 获取
local models = ctx.services.require("wheel.models@1")

-- 可选获取
local metrics = ctx.services.optional("wheel.metrics@1")

-- 发布事件
ctx.events.emit("wheel.agent.started", event)

-- 监听事件
ctx.events.on("wheel.agent.started", callback)
```

至于这个 service 是**另一个 Git 仓库、另一个 Lua Plugin、另一个 Panel，甚至 Rust 提供的服务**，全部由 Bitty Runtime 处理。

所以你问“跨仓库是不是需要封装”，答案实际上是：

> **跨仓库应该强制走 public contract，而不是源码依赖。**

仓库只是代码的发布边界；真正的架构边界应该是 **Service / Capability Contract**。这样你以后把 Wheel 拆成几十个插件，也不会变成几十个仓库之间互相 `require("../../xxx")` 的依赖地狱。

之后是不是会出现 UI 部分出现框架级别的 Lua 插件呢？很多部分是不是可以先做成 Rust Core -> Lua Core，然后用户再调用 Lua 的轮子再开发呢

是，而且这其实很可能会自然演化成一个 **四层插件生态**。关键不是“Rust 和 Lua 二选一”，而是把不同稳定性、性能和抽象层次的能力放到不同层。

## 我更建议的层次

```text
┌──────────────────────────────┐
│ User / Application Plugins   │
│ Wheel UI / Dashboard / Tools │
├──────────────────────────────┤
│ Framework Plugins            │
│ UI Framework / Agent SDK     │
│ Model SDK / Tool Framework   │
├──────────────────────────────┤
│ Bitty Lua SDK / Lua Runtime  │
│ stable high-level API        │
├──────────────────────────────┤
│ Bitty Rust Core              │
│ renderer / panel / IPC / PTY │
│ input / scheduler / storage  │
└──────────────────────────────┘
```

所以你说的：

> Rust Core → Lua Core → 用户调用 Lua 轮子开发

整体思路对，但我会避免把第二层直接称为一个很重的 **Lua Core**。

更准确一点可以叫：

```text
Bitty Rust Core
    ↓
Bitty Lua SDK / Standard Library
    ↓
Lua Framework Plugins
    ↓
Application Plugins
```

因为真正必须稳定、不可替代的 Core 还是 Rust。

Lua 特别适合。

# 一个非常重要的原则：不要让用户依赖 Rust Core API

比如不要让普通插件：

```lua
bitty.core.renderer.create_surface(...)
```

而应该：

```lua
ui.panel(...)
```

因为 Rust Core API 往往变化比较快，而且容易暴露内部实现。

最好：

```text
Rust internal API
      ↓
stable Lua ABI/API
      ↓
framework API
```

这样未来你哪怕把：

```text
wgpu
winit
font engine
IPC implementation
scheduler
```

全部换掉，用户插件都不需要修改。

这其实和操作系统很像：

```text
hardware
↓
kernel
↓
syscall
↓
libc
↓
framework
↓
application
```

Bitty 可以理解为：

```text
Rust Core      ≈ kernel
Lua SDK        ≈ libc / system API
Lua Framework  ≈ Qt / GTK / Tokio-like libraries
Plugin         ≈ application
```

---

## 但要避免一个问题：Lua SDK 不能无限膨胀

如果以后什么东西都加入：

```text
bitty.lua.core
```

最后它又会变成另一个 monolith。

所以我会明确：

### Lua SDK

只保留非常通用且稳定的：

```text
event
ipc
service
panel
process
filesystem
storage
timer
async
permission
logging
```

### Framework Plugin

则可以自由迭代：

```text
bitty-ui
wheel-tool
wheel-model
wheel-agent
wheel-dashboard
```

这样就算：

```text
bitty-ui v1 → v2
```

发生巨大变化，也不会要求整个 Bitty Core 跟着改。

---

## 最终我会把 Bitty 的 API 金字塔设计成这样

```text
          User Plugin
              ▲
              │
      Framework Plugin
              ▲
              │
        Public Lua SDK
              ▲
              │
        Rust Host API
              ▲
              │
          Rust Core
```

并且越往下：

```text
更稳定
更低级
更少
更难替换
```

越往上：

```text
变化更快
抽象更高
数量更多
可以自由替换
```

所以 UI Framework、Tool Framework、Model Framework 这种“**框架级 Lua 插件**”不仅可以有，我认为将来应该主动鼓励它们出现。

这样 Bitty 最终不是简单的：

> **Rust 程序 + Lua 插件**

而更像一个：

> **Rust 提供系统级 runtime，Lua 构建整个 application ecosystem。**

这和你想让 Bitty 保持小 Core、但又拥有非常大的扩展空间，是非常一致的。
