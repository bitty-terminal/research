## 总体判断

这几个仓库一起看之后，我觉得现在 Bitty 最大的问题已经不是“缺设计”，而是进入了一个新的阶段：

> **架构已经成形，但早期 docs-first / experimental implementation 留下的状态漂移、职责迁移和 truth duplication 开始显现。**

尤其是 `bitty` 本身已经远远不是一个“准备实现”的仓库：现在是 19-crate workspace，`v0.0.20`，README 已明确区分 Shipped / Early / Not yet，并且有 AUR、预编译包、真实 GPU/PTY/Plugin 等功能。

所以接下来应该从：

```text
design -> experimental implementation
```

切换为：

```text
reconcile -> extract -> harden -> verify
```

而不是继续主要扩展架构文档。

---

# 1. `bitty`：现在最值得做的是“瘦身”和边界收敛

`bitty` 当前主体结构本身我认为相当合理。

19 个 crate 已经把 VT、PTY、Platform、Config、Term State、Render、UI、Plugin Host、Runtime、IPC、Agent、Rich 等拆开了。

真正需要警惕的是 **`bitty-runtime` 正在承担过多 optional experience**。

现在 `crates/bitty-runtime/src/` 里还有：

| 模块                 | 大致定位                            |
| ------------------ | ------------------------------- |
| `ai_panel.rs`      | AI Panel                        |
| `browser_panel.rs` | Browser                         |
| `file_manager.rs`  | File Manager                    |
| `git_panel.rs`     | Git                             |
| `mail_panel.rs`    | Mail                            |
| `palette.rs`       | Palette                         |
| `statusline.rs`    | Statusline                      |
| `project.rs`       | Project                         |
| `panels_async.rs`  | Panel worker infrastructure     |
| `registry.rs`      | generic Panel/runtime primitive |
| `workspace.rs`     | Workspace                       |
| `runtime.rs`       | terminal runtime                |

其中 `ai_panel.rs` 已约 51 KB、`git_panel.rs` 约 60 KB、`mail_panel.rs` 约 62 KB、`browser_panel.rs` 约 41 KB。

但你自己的 Core boundary 文档已经明确：

> Core owns mechanisms；AI / Agent、Git、Status line、File Picker 等 optional experience 应主要由 plugin policy 拥有。

所以这里不是架构理念错了，而是 **早期 dogfooding implementation 还没完成迁移**。

我会把它理解成：

```text
过去：
bitty-runtime
├─ Panel primitive
├─ Plugin Host
├─ AI Panel implementation
├─ Git Panel implementation
├─ Browser implementation
├─ Statusline implementation
└─ ...

未来：
bitty-runtime
├─ Panel Runtime
├─ Host Services
├─ Event / Command / Capability
├─ Execution primitives
└─ Plugin bridge

bitty-plugins/*
├─ palette
├─ statusline
├─ activity
├─ git
├─ file-manager
├─ mail
└─ browser

bitty-ai
└─ AI runtime + AI experience
```

你现在其实已经开始走这条路了，因为 `activity`、`palette`、`statusline` 都已经成为独立 repository，而 `bitty-plugins` 也已经把这些作为 submodule 管理。

所以我会建议：**暂时不要再往 `bitty-runtime` 添加新的 first-party experience。**

---

# 2. `ai_panel.rs` 是现在最应该迁出的一个

这个比其它 Plugin 更重要。

因为现在的 `ai_panel.rs` 已经不仅仅是：

```text
Panel UI for AI
```

里面已经有：

```text
AgentWorkspace
AgentMemory
32 KiB Context Budget
ai.provider
ai.stream
ai.model
agent.context.terminal
agent.context.workspace
agent.memory:persist
mcp.invoke:TOOL
```

甚至包含 AI-specific validation 和 workspace/memory helpers。

这实际上已经非常接近一个“小型 AI runtime”。

而你刚刚建立 `bitty-ai` 的目的，恰好就是把：

```text
Provider
Context
Agent
Tool Bus
Session
Memory
```

从 Terminal Core 边界中独立出去。

所以最终我觉得 `bitty-runtime::ai_panel` 最多应该留下：

```text
generic Panel adapter
generic context snapshot bridge
generic rich-fragment receiver
generic consent UI hooks
```

甚至整个 AI Panel 都应该最终成为 `bitty-ai` / Lua plugin。

**不要出现两个 AI runtime：**

```text
bitty-runtime::ai_panel
        +
bitty-ai
```

这会是未来最麻烦的架构债务之一。

---

# 3. `bitty-agent` 的定位也需要重新明确一次

这个 crate 本身其实设计得很克制：

```text
AgentId
AgentMessage
AgentObservation
ToolSpec
ToolCall
ToolResult
SideQueue
AgentSession
```

而且明确没有：

```text
LLM IO
real tool execution
network
provider
compaction
```

这一点很好。

所以我不建议把 `bitty-agent` 直接删掉。

但它应该被重新定义成：

> **generic Agent protocol / bounded message vocabulary**

而不是：

> Agent runtime。

也就是说：

```text
bitty-agent
    ↓
identity
message
observation
protocol
bounded coordination types

bitty-ai
    ↓
AgentLoop
ModelProvider
Context
Tools
Session policy
Compaction
Multi-agent orchestration
```

这样它甚至可以和未来的 `bitty-bridge` / `bitty-ipc-client` 形成一套非常干净的 generic SDK。

---

# 4. 我发现了一个比较严重的代码文档漂移

`bitty-agent/src/lib.rs` 现在仍然写着：

> OQ-018 remains open
> IPC/MCP wire protocol RFC has not landed
> Agent integration RFC has not landed

但同一个仓库的 `bitty-ipc/src/lib.rs` 已经明确：

> accepted IPC-Agent RFC
> accepted 2026-08-29
> closes OQ-018

这就不是普通的 README 过期了，而是：

```text
cargo doc(bittty-agent)
        ↓
告诉开发者 OQ-018 open

cargo doc(bitty-ipc)
        ↓
告诉开发者 OQ-018 closed
```

Agent 阅读仓库的时候也会得到两个相反的结论。

`bitty-runtime/src/lib.rs` 也有类似问题：里面还把 Plugin Platform RFC 描述成 Proposed/Draft、OQ-011..014 未完成的阶段性状态。

而 terminal docs 现在已经明确很多这些 ownership 是 Accepted。

### 我觉得应该增加一个专门的 drift gate

不是手动搜，而是机器检查。

例如维护：

```toml
[decisions]
OQ-018 = "accepted"
OQ-014 = "accepted"
OQ-013 = "accepted"
```

CI 扫：

```text
*.rs
*.md
```

检测诸如：

```text
"OQ-018 remains open"
"OQ-014 unresolved"
"RFC has not landed"
```

这种和 canonical register 冲突的 statement。

你的文档体系现在已经大到 **需要 semantic drift detection** 了。

---

# 5. `bitty-ipc` 反而是目前比较干净的一个边界

这个 crate 我暂时不建议大改。

它现在非常明确地只负责：

```text
Frame
WireEnvelope
Scope
ConsentLedger
Auth
RateLimit
Transport
MCP Client Stub
DevTools dispatch
```

而且不依赖 workspace crate，不持有 PTY/GPU/window，也不执行 plugin。

这个设计非常适合作为：

```text
protocol primitive
```

而不是 Host Service 实现。

所以对于之前 `bitty-ai-slice` 暴露出来的：

```text
terminal.snapshot
tool dispatch
rich fragment ingestion
```

我反而**不建议全部塞进 `bitty-ipc`**。

更合理的是：

```text
bitty-ipc
    generic protocol / framing / auth

bitty-bridge
    host client SDK
    terminal.snapshot
    execution
    tool dispatch
    rich fragment transport
```

或者叫：

```text
bitty-host-api
bitty-client
bitty-bridge-client
```

这样以后：

```text
bitty-ai
DevTools
external CLI
MCP adapter
third-party automation
```

都可以消费同一个 generic host API。

# 6. `git_panel.rs` 暴露了一个“authority inversion”

最近的 commit 有一段很值得注意：

> Canonical record lives in `crates/bitty-runtime/src/git_panel.rs`

并在 Rust module docs 中直接记录 `[tools.git]` 的 accepted contract、allowed subcommands、bounds、verification plan。

我觉得这个长期来看不太合适。

因为你现在整体架构已经定义成：

```text
bitty-plugins-docs
    canonical Plugin contracts

bitty
    implementation + evidence
```

那么应该是：

```text
plugin-reuse RFC / tools.git spec
        ↓
canonical contract

git_panel.rs
        ↓
implementation

tests/
        ↓
evidence
```

而不是：

```text
git_panel.rs
        ↓
canonical accepted contract
```

否则以后把 `git-panel` 拆成独立 repository 时，就会碰到：

> canonical contract 怎么从 `bitty` Rust comment 迁走？

所以这次 `[tools.git]` 我建议把正式 contract 移入 `bitty-plugins-docs`，Rust docs 留：

```rust
//! Implements tools.git v1.
//! Canonical contract: ...
```

即可。

# 7. `bitty-terminal-docs` 的仓库职责已经很清楚

这一点我认为拆仓是成功的。

README 定义它拥有：

```text
architecture
specifications
configuration
interfaces
product
reference
user docs
engineering evidence
platform audits
```

而：

```text
decisions
global security
roadmap
project state
reviews
```

留给 `bitty-docs`。

这个划分我建议保持。

但现在有两个明显问题。

---

# 8. 第一类问题：拆仓完成，但文档还写着“未来再拆”

`bitty-terminal-docs/README.md` 仍然说：

> submodule wiring is a later phase

`TODO.md` 也还写：

> Later phase: wire this repository into bitty as docs submodule

`docs/README.md` 也还是：

> designed to be mounted ... in a later wiring phase

但 `bitty/.gitmodules` 已经明确：

```gitconfig
[submodule "docs"]
path = docs
url = .../bitty-terminal-docs
```

所以这个需要一次统一 cleanup。

---

# 9. 第二类问题更大：Architecture 文档里混入太多“项目状态快照”

例如 `architecture/overview.md` 现在开头还是：

```text
2026-08-29
be3bdb4
16 crates
32 OQs
~808 tests
```

`core-boundaries.md` 也是类似。

但是现在实际已经：

```text
19 crates
v0.0.20
40+ accepted decisions / later work
```

这说明一个架构文档每推进几周就会“过期”。

## 我建议把 architecture 分成两种东西

**长期契约：**

```text
architecture/overview.md
architecture/core-boundaries.md

Terminal Truth
dependency direction
hot/cold path
Core/Plugin ownership
trust boundary
```

这些不应该写：

```text
commit be3bdb4
808 tests
16 crates
```

这些应该进入：

```text
project-state.json
status report
release evidence
compatibility matrix
```

这样 architecture 页面半年以后依然有效。

---

# 10. `draft` 和 `Accepted` 也有点混乱

例如 `core-boundaries.md` 的 frontmatter 是：

```yaml
status: draft
```

但正文又说：

```text
Accepted boundary principles
Accepted Core ownership
Accepted Plugin ownership
```

这虽然解释得通——“整个文档还有 candidate section”——但对机器和用户都不友好。

我更推荐拆成：

```text
architecture/core-boundaries.md
    status: accepted

architecture/future-boundaries.md
    status: draft
```

或者：

```text
Accepted architecture
Candidate evolution
```

分两个文档。

不要让一个 document-level status 和 section-level status 相互打架。

# 11. User Docs 的 gate 现在也值得重新考虑

这是我觉得 `bitty-terminal-docs` 比较重要的一点。

`bitty` README 已经明确告诉用户：

```text
paru -S bitty-bin
paru -S bitty
GitHub Releases
bitty init
bitty doctor
```

而且明确说这些是 shipped。

但 `bitty-docs` / terminal docs 的策略仍然大量保留：

> installation/getting-started 等要等 Verified 后再写。

例如总 TODO 里仍然写着只有 Verified 才添加 installation/getting-started/daily-use。

我觉得这个 gate 现在过于严格。

应该区分：

```text
Shipped factual documentation
≠
Compatibility guarantee
≠
Verified security claim
```

例如完全可以写：

> Available in v0.0.20, pre-alpha, API and behavior may change.

这不代表：

> Stable / Verified / Compatible。

否则就会变成：

```text
最权威、最好用的用户文档
    ↓
反而是 bitty/README

canonical terminal docs
    ↓
因为 Verified gate 而没有实际使用说明
```

长期看不合理。

# 12. `bitty-docs` 的 aggregator 模型，我认为整体是正确的

现在三个 submodule：

```text
bitty-terminal
bitty-ai
bitty-plugins
```

分别指向三个 canonical docs repository。

而 `bitty-docs` 自己只保留：

```text
decisions
security
development
sources
findings
reviews
handoff
project
roadmap
releases
```

这种模型非常合理。

最终我认为应该稳定成：

```text
bitty-docs
    cross-project governance

bitty-terminal-docs
    Terminal product truth

bitty-plugins-docs
    Plugin platform truth

bitty-ai-docs
    AI runtime truth
```

这是一个不错的 architecture。

# 13. 但 `bitty-docs` 最大的问题是“状态事实复制太多次”

现在同一套事实至少出现在：

```text
README.md
docs/README.md
TODO.md
docs/project/project-state.json
```

比如：

```text
bea338d
19 crates
v0.0.20
40 Accepted OQs
R-004 Open
R-005/R-006/R-007 Mitigated
```

在这些页面里反复出现。

但实际上你已经有：

```text
docs/project/project-state.json
```

专门机器化保存：

```json
implementation.revision
crates
latest_release
maturity
milestones
risks
```

那我建议以后：

> **只有 `project-state.json` 是状态事实源。**

README 只显示少量摘要：

```text
Stage: Pre-alpha
Latest release: v0.0.20
Crates: 19
Snapshot: 2026-09-14
→ Full project state
```

甚至这个摘要都可以 CI generate/check。

这样 README 就不会变成一篇巨大的项目数据库镜像。

# 14. Submodule pin 现在实际上有三种“版本”

这个设计本身没错，但需要明确语义。

例如当前：

```text
bitty-terminal-docs main
    77b538d...

bitty/docs
    56f70bc...

bitty-docs/bitty-terminal
    bcb65a4...
```

三个 revision 不一样是完全正常的。

但一定要正式定义：

```text
docs repo main
    = latest canonical docs

code repo docs/
    = docs matching this implementation revision

bitty-docs submodule
    = governance-reviewed documentation snapshot
```

如果不明确，别人会问：

> 到底哪个才是“最新 Bitty 文档”？

我甚至建议提供：

```sh
just docs-status
```

输出：

```text
bitty-terminal-docs head   77b538d
bitty/docs pin             56f70bc
bitty-docs pin             bcb65a4

code mount behind:  N commits
governance mount behind: M commits
```

但**不要自动强制三者永远相等**。

pin 的意义就在于 reproducibility。

# 16. 我现在会把整个 Bitty 仓库体系定成这样

```text
                       bitty-docs
                 Governance / Security
                 Decisions / Roadmap
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
bitty-terminal-docs bitty-plugins-docs bitty-ai-docs
        │              │              │
        ▼              ▼              ▼
      bitty        bitty-plugins     bitty-ai
        │              │              │
        │         ┌────┴────┐         │
        │      activity  palette ...   │
        │                             │
        └──── generic host APIs ──────┘
```

最关键的是中间这一条：

```text
bitty
   generic terminal mechanism
        ↕
generic host / bridge API
        ↕
plugins / AI / external tools
```

**Bitty Core 不应该知道“AI Review”“Git Panel”“Mail Panel”是什么。**

它只需要知道：

```text
Panel
View
Execution
Command
Event
Capability
Snapshot
Tool dispatch
Rich fragment
Process
Filesystem
Network
```

这其实就是你现在整个架构逐渐收束出来的核心。

# 17. 我建议现在按这个优先级推进

1. **先做一次全仓 truth reconciliation**：修掉 `bitty-agent` 的 OQ-018、`bitty-runtime` 的旧 Plugin RFC 状态、terminal/plugins docs 的“future submodule”描述，以及三个 docs repo 的 TODO/README migration residue。
2. **给 CI 加 architecture/status drift gate**，至少自动检查 OQ 状态、crate 数量、submodule wiring、canonical RFC 状态，避免以后重新积累这种问题。
3. **开始 `bitty-runtime` optional experience extraction wave**。已经独立出来的 `palette/statusline/activity` 作为模板，然后继续 Git/File Manager/Mail/Browser；`ai_panel` 优先迁向 `bitty-ai`。
4. **固定 `bitty-agent` 为 generic protocol vocabulary**，不要让 Provider、Context、LLM、Compaction 再进入它；真正 Agent runtime 全部进入 `bitty-ai`。
5. **增加 generic host bridge 层**，在不污染 `bitty-ipc` 的情况下提供 `terminal.snapshot`、Tool Dispatch、Execution、Rich Fragment 等能力，供 `bitty-ai` 和 Plugins 复用。
6. **精简 `bitty-docs` 状态复制**，让 `project-state.json` 成为唯一机器事实源；README、docs map、TODO 不再复制几十个 commit/risk/state。
7. **调整文档 maturity policy**：允许“Shipped but pre-alpha”的 factual user docs，不必等整个 subsystem 达到内部 `Verified` 才写安装和日常使用文档。

---

## 最终判断

如果把前面的 `bitty-ai` 一起考虑，现在整个 Bitty 项目其实正好到一个非常好的转折点。

前一阶段你做的是：

```text
建立架构
建立规则
建立安全模型
建立文档体系
建立 Plugin / Panel / IPC / Agent 边界
```

这些已经相当充分。

下一阶段真正值得投入大量时间的是：

```text
Core 瘦身
Plugin 外迁
AI 外迁
generic host API
真实 integration
Verification
```

而不是继续增加更多顶层概念。

尤其是 **`bitty-runtime` 里那些 40–60 KB 的 first-party experience 模块**，我觉得会是接下来 Bitty 架构是否真正兑现“Core minimal + Plugin extensible”哲学的关键。现在正是把早期 experimental dogfood 逐渐变成真正 Plugin ecosystem 的时候。
