**Git 可能是 Wheel 在 Context、Compaction、Multi-Agent 三个部分最值得借鉴的系统之一**。

关键不是模仿 `git commit` 这些命令，而是借鉴 Git 背后的几个设计原则：

> **immutable objects + content addressing + DAG + cheap branches + explicit merge + refs + garbage collection**

这些东西和 Agent 的上下文问题几乎天然对应。

# 1. 不要把 Context 当“聊天记录”，而是当一棵 DAG

传统 Harness 基本是：

```text
m1 → m2 → m3 → m4 → m5 → m6
```

本质是 append-only conversation。

Wheel 可以改成：

```text
                    C1
                     │
                    C2
                   /  \
                 C3    C4
                 │      │
                 C5    C6
                   \   /
                    C7
```

这里节点不是单纯 Message，而是：

```text
Context Object
Task State
Decision
Tool Result
Code Snapshot
Checkpoint
Compaction
Agent Result
```

于是一次 Session 不再是：

```text
[Message, Message, Message, Message...]
```

而是：

```text
ContextGraph
```

这个改变非常大。

---

# 2. Context Object 可以直接借鉴 Git Object

Git：

```text
blob
tree
commit
tag
```

Wheel 完全可以设计自己的：

```text
artifact
tree
checkpoint
summary
decision
task
result
```

例如：

```rust
enum ContextObject {
    Artifact(Artifact),
    Tree(ContextTree),
    Checkpoint(Checkpoint),
    Summary(Summary),
    Decision(Decision),
    Task(TaskState),
    Result(AgentResult),
}
```

每个对象：

```text
hash = BLAKE3(serialized_content)
```

存储：

```text
~/.local/share/wheel/objects/
ab/
  cdef1234...
```

于是天然获得：

* immutable；
* deduplication；
* integrity；
* content-addressed lookup；
* cache reuse。

---

# 3. 一个文件读十次，不应该存十份

例如 Agent 多次读取：

```text
src/parser.rs
```

如果内容没变：

```text
hash(src/parser.rs) = 81af...
```

Context Store 里永远只有：

```text
artifact:81af
```

不同 Context 只是：

```text
ref → artifact:81af
```

类似 Git：

```text
多个 commit 可以指向同一个 blob
```

这对大型 Coding Session 非常重要。

否则 Harness 很容易：

```text
第一次 read 3000 tokens
第二次 read 3000
第三次 read 3000
...
```

底层重复存储、上层重复上下文。

---

# 4. `Checkpoint` 就非常像 Commit

这是最漂亮的类比之一。

Git Commit：

```text
tree
parent
author
message
```

Wheel Checkpoint：

```text
context tree
parent
task state
decisions
evidence
agent
```

例如：

```yaml
checkpoint:
  id: 8ac...
  parent: 72f...

  goal:
    fix Panel child process leak

  tree:
    context: 12f...

  modified:
    - src/panel.rs
    - src/process.rs

  decisions:
    - panel close owns child cleanup

  verification:
    targeted_tests: passed
    full_tests: pending
```

整个 Agent Session 就成为：

```text
Checkpoint A
    ↓
Checkpoint B
    ↓
Checkpoint C
```

而不是只能依赖 transcript。

---

# 5. Compaction 可以直接理解成 Git 的历史压缩 / snapshot

这比 `/compact` 这个概念清晰很多。

例如原始过程：

```text
tool call
tool result
thinking
file read
search
tool result
test
error
read
edit
test
...
```

可能有：

```text
80K tokens
```

阶段结束以后创建：

```text
Checkpoint C
```

里面只保存：

```text
Goal
Decisions
Current tree
Relevant artifacts
Open problems
Verification state
```

旧的 80K：

> **没有删除。**

只是：

```text
不再属于 active context
```

这特别像 Git：

```text
你 checkout 当前 commit
≠
历史 commit 被删除
```

所以 Wheel 的 Compaction 应该是：

> **改变 HEAD 所看到的 Context View，而不是销毁历史。**

这个设计比传统 summarize 强很多。

---

# 6. `HEAD` 这个概念也特别适合 Agent

例如：

```text
HEAD
 ↓
checkpoint:ac29
```

当前 Agent 的 Active Context 从：

```text
HEAD
```

编译。

Agent完成一个阶段：

```text
checkpoint()
```

：

```text
HEAD → new checkpoint
```

甚至可以：

```text
wheel context log
```

看到：

```text
ac293 implementation complete
82af1 identified process ownership bug
11ef3 reproduced panel leak
83cc2 task start
```

这已经很像 Git 了。

---

# 7. Context Branch 非常适合探索不同方案

例如 Agent遇到一个 bug，有三种可能：

```text
main context
     │
     ├── hypothesis/parser
     ├── hypothesis/runtime
     └── hypothesis/pty
```

三个 Subagent 分别探索。

这就是：

```text
branch
```

每一个 branch：

* 共享相同 parent context；
* 不复制全部历史；
* 只记录自己的 delta。

于是多智能体特别自然：

```text
                Task HEAD
                   │
          ┌────────┼────────┐
          ↓        ↓        ↓
       Agent A   Agent B   Agent C
          │        │        │
         C4       C5       C6
```

并不需要：

```text
把主 Agent 的 100K transcript
复制三次给三个 Subagent
```

而只是：

```text
parent = checkpoint:c3
```

---

# 8. Multi-Agent Result 就像 Merge

这个类比非常强。

例如：

```text
Agent A:
修改 parser

Agent B:
补 tests

Agent C:
调查 regression
```

最后：

```text
              Parent
             /   |   \
            A    B    C
             \   |   /
              Merge
```

但是 Wheel 的 Merge 不只是 Git 文件 Merge。

还包括：

```text
Code merge
Decision merge
Task state merge
Evidence merge
Context merge
```

可以有：

```text
Context Merge Conflict
```

例如 Agent A：

```text
Root cause = parser
```

Agent B：

```text
Root cause = PTY lifecycle
```

不能让 LLM 偷偷 summarize 成一个模糊结论。

应该明确产生：

```yaml
conflict:
  type: hypothesis

  ours:
    cause: parser

  theirs:
    cause: pty-lifecycle

  resolution:
    pending
```

这其实比现在很多 Multi-Agent 系统的“把几个 Agent 输出塞给主 Agent总结一下”严谨得多。

---

# 9. `cherry-pick` 也特别有用

假设 Research Agent 做了很多事情，其中真正有用的只有一个发现：

```text
Agent B branch

B1
B2
B3
B4 ← important
B5
```

主 Agent 不应该 Merge 整个 context。

而可以：

```text
cherry-pick B4
```

也就是只拿：

```text
Finding:
Panel child process ownership is handled by ProcessGroup.

Evidence:
src/process/group.rs#...
```

进入自己的 Context。

这是非常好的 **Subagent Context Isolation**。

---

# 10. Context 不应该共享 transcript，而应该共享 object refs

这是 Git 架构给 Wheel 最大的启发之一。

Agent A 不应该给 Agent B：

```text
这是我前面所有聊天记录……
```

而应该：

```text
parent_checkpoint = abc
artifacts = [
    code:183a,
    decision:92fc,
    task:77ad
]
```

Agent B 需要什么再展开什么。

于是共享成本变成：

```text
refs
```

而不是：

```text
复制 tokens
```

---

# 11. `rebase` 也有意义

例如 Agent B 从：

```text
Checkpoint C3
```

开始工作。

但主 Agent 已经：

```text
C3 → C4 → C5
```

此时 Agent B 的工作可能已经基于旧 Context。

可以：

```text
rebase AgentB onto C5
```

语义上不是简单 Git patch replay，而是：

1. 找出 B 从 C3 之后的 decisions/artifacts；
2. 检查哪些已经 stale；
3. 重新验证新的 C5；
4. 重放仍然有效的工作；
5. 标记 conflict。

例如：

```text
Agent B inspected Parser::foo@hashA
```

但 C5：

```text
Parser::foo@hashB
```

则：

```text
stale artifact conflict
```

这对于长期运行的 Subagent 特别重要。

# 12. `worktree` 和 Bitty 更是天然匹配

这个你应该会特别喜欢。

可以直接对应：

```text
Task
├── context branch
├── git branch/worktree
├── Agent
└── Panel
```

例如：

```text
Agent A
context: refs/tasks/42/agents/a
worktree: .wheel/worktrees/a
panel: headless:12

Agent B
context: refs/tasks/42/agents/b
worktree: .wheel/worktrees/b
panel: headless:13
```

于是：

```text
Context Isolation
Filesystem Isolation
Process Isolation
```

统一了。

Agent A/B 不会互相改同一个 working tree。

这和你之前设计的 Panel / Agent / Worktree 生命周期模型能很好结合。

# 13. `refs` 可以解决大量 Agent 状态管理问题

Git 有：

```text
refs/heads/
refs/tags/
HEAD
```

Wheel 可以有：

```text
refs/tasks/
refs/agents/
refs/checkpoints/
refs/sessions/
```

例如：

```text
refs/tasks/42/head
refs/tasks/42/agents/reviewer
refs/tasks/42/agents/implementer
refs/tasks/42/checkpoints/pre-implementation
```

甚至：

```text
refs/users/xuepoo/current
```

不用把这些状态塞 SQLite relational tables 到处 join。

底层 object store + refs 已经可以表达很多东西。

# 14. Reflog 非常适合 Agent

Agent 很容易错误操作：

```text
错误 compact
错误切换 checkpoint
错误 merge
错误更新 task
```

Wheel 可以有：

```text
context reflog
```

例如：

```text
HEAD@{0} checkpoint:82ab merge reviewer
HEAD@{1} checkpoint:91dc implementation
HEAD@{2} checkpoint:17cc exploration
```

然后：

```text
wheel context restore HEAD@{2}
```

特别适合：

> “Agent 刚刚压缩以后似乎忘掉了一个重要决定。”

可以直接回去检查。

---

# 15. Git GC 对 Context 管理同样重要

随着使用：

```text
objects/
```

一定越来越大。

但 content-addressing 后非常容易做 mark-and-sweep：

```text
Roots:
refs/*
pinned checkpoints
active sessions
saved memory

        ↓

Traverse DAG

        ↓

reachable objects
```

不可达：

```text
unreachable artifacts
old temporary logs
abandoned search branches
```

经过 grace period：

```text
GC
```

这比：

```text
session.db 无限增长到 25GB
```

要优雅很多。

你之前 OpenCode 数据库增长到几十 GB 的问题，本质上正是这里应该避免的。

# 16. Packfile 思想也值得直接借鉴

Agent 会产生大量小对象：

```text
tool result 2KB
decision 300B
diagnostic 1KB
summary 4KB
```

如果每个一个文件：

```text
几十万个 inode
```

会很难受。

所以前期可以 loose objects：

```text
objects/ab/cdef...
```

后台：

```text
wheel gc
```

打包：

```text
packs/pack-0182.wpack
```

甚至 delta compression：

```text
src/parser.rs snapshot A
src/parser.rs snapshot B
```

差异很小：

```text
store base + delta
```

这基本就是 Git packfile 的思路。

# 17. 甚至 Context Cache 也可以借鉴 Git Object Hash

之前说的：

```text
Artifact Cache
Retrieval Cache
Compaction Cache
```

都能基于 hash。

例如：

```text
File hash
 +
Parser version
 +
Compiler version

      ↓

AST object hash
```

如果一样：

```text
AST Cache Hit
```

Compaction：

```text
hash(
  input objects
  + compact prompt version
  + model
)
```

一样：

```text
直接复用
```

这样 Cache 的 invalidation 会非常干净。

# 18. 但是 Prompt Cache 与 Git Context Store 要分开

这一点一定不要混。

Git-like store解决的是：

```text
Wheel semantic context
```

Provider KV Cache：

```text
serialized prompt prefix
```

关系是：

```text
Content-addressed Context DAG
             ↓
       Context Compiler
             ↓
      Canonical Serialize
             ↓
      Provider Prompt
             ↓
      Provider KV Cache
```

所以：

```text
Context Object Hash
```

稳定，不代表：

```text
Provider Cache
```

一定命中。

但 Context DAG 会让后者更容易稳定。

# 19. Context Compiler 本身可以变成类似 Git checkout

这是我觉得最漂亮的概念。

Wheel 保存的是：

```text
Context DAG
```

然后：

```text
Context Compiler
```

做：

```text
checkout HEAD
```

但不是恢复文件系统，而是生成：

```text
Active Context View
```

比如：

```text
HEAD
 ↓
Task State
 ↓
Relevant objects
 ↓
Authority resolution
 ↓
Dedup
 ↓
Budget
 ↓
Prompt
```

因此真正关系变成：

```text
Object Store
      +
Refs
      +
Context DAG
      ↓
Context Compiler
      ↓
Active Context
```

这比：

```text
messages[]
```

先进很多。

# 20. Multi-Agent 的核心也可以直接建立成 DAG

我会避免：

```text
Manager
├── Agent
├── Agent
└── Agent
```

这种纯树模型。

因为实际 Agent 工作很容易：

```text
Agent A result
     ↘
      Agent C
     ↗
Agent B result
```

所以本身就是 DAG。

例如：

```text
                   Task C0
                  /       \
              Explore A   Explore B
                 │           │
                A1          B1
                 \          /
                  Review C
                     │
                 Implement D
                     │
                    D1
```

每个节点：

```text
parents[]
```

即可。

这使得：

```text
parallelism
merge
reuse
provenance
```

全部自然表达。

# 最值得借鉴 Git 的，其实是一条哲学

Git 没有因为 repository 历史越来越长，就：

```text
每次操作都把所有历史读一遍。
```

它保存的是：

> **完整历史 + 当前快照 + 高效引用。**

Wheel 也应该如此：

```text
Full Session History
      ≠
Active Model Context
```

而应该：

```text
Full History
    ↓
immutable object DAG

Current State
    ↓
HEAD / refs

LLM sees
    ↓
compiled working context
```

这其实正好把我们之前讨论的所有问题统一起来了：

**Context Compiler** 类似 `checkout + index`；**Checkpoint** 类似 commit；**Compaction** 类似创建更高层 snapshot，而不是删除历史；**Subagent** 类似 cheap branch；**Multi-Agent synthesis** 类似 merge；**Agent 更新到新任务状态**类似 rebase；**Context 回滚**类似 reflog/reset；**长期存储清理**类似 gc/pack；**Worktree**甚至可以直接和真正 Git worktree 联动。

如果 Wheel 真采用这个思路，我甚至会把它概括成一句内部架构原则：

> **Wheel does not maintain conversations. Wheel maintains a content-addressed task history and compiles conversations from it.**

这会比传统的 `messages[] + compact()` 模型强很多。
