Context Compiler 还得考虑上下文缓存问题，之前是讨论过怎么样上下文缓存命中率更高，而且也讨论过压缩部分。
那么可以详细说下这个 Context Compliler 可以怎么做吗？

可以。对 Wheel 来说，我认为 **Context Compiler 应该成为整个 AI 架构中最核心的模块之一**，甚至可以把它看成 Agent Runtime 与 LLM Provider 之间的一层“编译器”。

它不应该只是：

```text
messages + tools + files
        ↓
拼 Prompt
        ↓
LLM
```

而应该类似真正的 Compiler：

```text
Raw Context Sources
        ↓
Normalize
        ↓
Classify
        ↓
Resolve / Deduplicate
        ↓
Retrieve
        ↓
Compress
        ↓
Budget
        ↓
Cache Planning
        ↓
Provider-specific Lowering
        ↓
LLM Request
```

这里还要明确区分三件经常混在一起的东西：

> **Context Storage ≠ Active Context ≠ Prompt Cache**

这是设计 Wheel Context Compiler 的基础。

---

# 1. 先定义 Wheel 的三层 Context 世界

我建议直接把所有信息分成：

```text
                    Wheel Context Universe
                              │
            ┌─────────────────┼─────────────────┐
            ↓                 ↓                 ↓
       Cold Storage       Warm Context       Hot Context
       / Event Store      / Indexed          / Active
            │                 │                 │
      几乎无限              可快速取回            LLM 当前看到
```

例如：

### Cold

```text
完整 Panel History
完整 PTY stdout
完整 tool result
旧文件版本
旧 diff
Agent transcript
MCP 原始返回
完整 test logs
```

这些**永远不应该因为“可能有用”就常驻 LLM Context**。

---

### Warm

```text
AST index
LSP symbol index
repo map
历史 command summary
structured diagnostics
task checkpoints
Skill metadata
MCP capability metadata
file summaries
previous decisions
```

Agent 随时可以重新获取。

---

### Hot

真正进入这次 inference：

```text
current user intent
task goal
critical project rules
current task state
relevant code
relevant diagnostics
recent important actions
active tool schemas
```

因此：

$$
Hot \subset Warm \subset Universe
$$

Context Compiler 做的，就是不断决定：

> Universe 里的什么东西现在应该进入 Hot Set？

---

# 2. Context Compiler 不应该输出字符串，而应该输出 `Context IR`

这是我尤其推荐的设计。

类似：

```rust
struct ContextUnit {
    id: ContextId,
    kind: ContextKind,

    source: ContextSource,

    content: ContextContent,

    priority: Priority,
    relevance: f32,
    authority: Authority,
    trust: TrustLevel,

    freshness: Freshness,
    lifetime: Lifetime,

    token_estimate: usize,

    cacheability: Cacheability,
    stability: Stability,

    content_hash: Hash,
    dependencies: Vec<ContextId>,

    provenance: Provenance,
}
```

例如：

```text
ContextUnit
────────────────────────────
id          code:lexer:parse_escape
kind        SourceCode
source      src/lexer.rs
relevance   0.93
priority    High
freshness   Current
stability   UntilFileChanges
tokens      842
cacheable   Yes
hash        a82f...
```

又例如：

```text
id          command:cargo-test:1288
kind        TestResult
relevance   0.91
priority    High
lifetime    TaskPhase
tokens      176
cacheable   No
source      panel://headless/17/event/1288
```

LLM 从来不需要知道底层存了多少数据。

---

# 3. `Context IR` 最重要的是让“内容”和“排列方式”分离

这是上下文缓存非常关键的一点。

逻辑上：

```text
Core Prompt
Project Rules
Tools
Task State
Code
Diagnostics
Conversation
```

但是各 Provider 对 cache 的实现不同。

例如 Anthropic 当前 Prompt Cache 本质上基于 prefix，而且请求顺序形成：

```text
tools
→ system
→ messages
```

它还支持显式 cache breakpoints；动态 `defer_loading` Tool 可以在不修改前缀的情况下后加载。([Claude Platform][1])

OpenAI 当前也明确建议：

> stable content 放前面，dynamic content 放后面；

并提供 `prompt_cache_key` 和 cache diagnostics；当前新的 Responses API 还支持更显式的 breakpoint 控制。([OpenAI Developers][2])

Gemini 则同时存在 implicit prefix caching 和显式 CachedContent；官方同样建议把 large/common content 放前面，以提高 cache hit。([Google AI for Developers][3])

所以 Wheel 应该：

```text
Context IR
    │
    ├── OpenAIContextBackend
    ├── AnthropicContextBackend
    ├── GeminiContextBackend
    ├── BedrockContextBackend
    └── ...
```

而不是让 Agent Runtime 知道：

```text
cache_control
prompt_cache_key
cachedContent
```

这些细节。

---

# 4. 我会给 Context 分成 6 个稳定性 Zone

这是整个缓存机制最重要的设计。

```text
┌───────────────────────────────────────┐
│ Z0 Provider / Model Contract          │ very stable
├───────────────────────────────────────┤
│ Z1 Wheel Core                         │ very stable
├───────────────────────────────────────┤
│ Z2 Project Context                    │ stable
├───────────────────────────────────────┤
│ Z3 Task State                         │ semi-stable
├───────────────────────────────────────┤
│ Z4 Working Set                        │ dynamic
├───────────────────────────────────────┤
│ Z5 Current Turn                       │ extremely dynamic
└───────────────────────────────────────┘
```

## Z1 — Wheel Core

例如：

```text
Wheel Core Prompt
Core Tool definitions
Bitty environment semantics
Safety invariants
Agent operating principles
```

可能数小时甚至整个版本周期都不变。

这是**最值得缓存**的。

---

## Z2 — Project Context

例如：

```text
project instructions
.bitty/
AGENTS.md
project architecture summary
build/test conventions
important repo topology
```

只在：

```text
git checkout
project config changes
important architecture changes
```

时变化。

非常适合第二层缓存。

---

## Z3 — Task State

例如：

```yaml
goal: fix lexer unicode escape bug

constraints:
  - preserve parser API
  - no new dependencies

decisions:
  - modify lexer state machine only

modified:
  - src/lexer.rs

open:
  - surrogate pair handling
```

几十轮才发生一些变化。

---

## Z4 — Working Set

例如：

```text
src/lexer.rs::parse_escape
tests/lexer.rs::unicode_escape
cargo test diagnostics
current git diff
```

高度动态。

---

## Z5 — Current Turn

```text
用户最新消息
刚刚的 tool result
最新 error
```

基本不可缓存。

---

# 5. 然后形成一个“缓存树”

不要把 Cache 理解成一个 Boolean：

```text
cached = true/false
```

它应该是分层的。

例如：

```text
C0
│
├── Wheel Core
│
└── C1
     │
     ├── Project Context
     │
     └── C2
          │
          ├── Task Checkpoint
          │
          └── Dynamic Suffix
```

可以内部用类似 Merkle Chain：

```text
H0 = hash(WheelCore)

H1 = hash(
    H0,
    ProjectContext
)

H2 = hash(
    H1,
    TaskCheckpoint
)

H3 = hash(
    H2,
    WorkingSet
)
```

如果：

```text
WorkingSet changed
```

那么：

```text
H0 ✓
H1 ✓
H2 ✓
H3 ✗
```

如果项目规则发生变化：

```text
H0 ✓
H1 ✗
H2 ✗
H3 ✗
```

这和 prefix cache 的实际行为非常吻合。

---

# 6. Context Compiler 必须保证序列化完全稳定

这是很多 Harness 很容易忽略的地方。

Prompt Cache 通常依赖**相同或高度一致的 prefix**。

因此这种东西非常危险：

```text
Current time: 2026-09-18 00:18:31
```

放 System Prompt 开头。

下一轮：

```text
Current time: 2026-09-18 00:18:46
```

整个后面缓存可能全部失效。

同样包括：

```text
随机 UUID
request id
临时目录
动态 tool 顺序
随机 JSON key order
不同 whitespace
实时 token 数
动态状态栏
git status
当前 CPU
```

所以 Compiler 必须有：

```text
Canonical Serializer
```

例如工具永远：

```text
sort_by(tool.stable_id)
```

JSON：

```text
stable property ordering
stable whitespace
stable enum serialization
```

Sections：

```text
固定顺序
```

这不是代码洁癖。

而是直接影响：

```text
KV cache hit rate
```

Anthropic 官方甚至特别提醒，JSON key 排序不稳定都可能破坏 prompt cache。([Claude Platform][4])

---

# 7. 所有动态数据都不能混进 Stable Prefix

例如不要这样：

```text
SYSTEM

You are Wheel.

Current workspace:
/home/xuepoo/bitty

Current branch:
feature/panel

Current time:
...

Current CPU:
...

Current task:
...
```

应该：

```text
[Stable Core]

You are Wheel...
Bitty semantics...
Operating principles...
```

然后：

```text
[Project Snapshot]

project = bitty
workspace = ...
project policies = ...
```

然后：

```text
[Task State]

...
```

最后：

```text
[Runtime State]

branch = feature/panel
current panel = 7
...
```

越动态的东西越靠后。

也就是说：

$$
\text{Prompt position}
\approx
\text{inverse volatility}
$$

很稳定 → 前。

很动态 → 后。

---

# 8. 但是不要为了 Cache Hit 牺牲 Context Quality

这里要特别强调。

假设一个旧代码：

```text
src/parser.rs
```

已经完全无关。

但因为：

> “删掉会破坏 Cache！”

就一直留着。

这是错误的。

Wheel 的优化目标应该是：

$$
Utility
=
TaskQuality
-
ContextNoise
-
Latency
-
Cost
$$

Prompt Cache 只是其中一个优化项。

也就是说优先级：

```text
Correctness
    >
Context relevance
    >
Cache hit
    >
Token cost
```

绝对不能反过来：

```text
为了 95% cache hit
让模型带着大量过期信息工作
```

---

# 9. 可以设计一个 `Context Admission Score`

并不一定非要真的使用这个公式，但这种思维很有帮助：

$$
S(c)=
R(c)
\times I(c)
\times F(c)
\times A(c)
-
N(c)
-
T(c)
$$

其中：

```text
R relevance
I importance
F freshness
A authority

N noise / duplication
T token cost
```

然后另外只有一个很小的：

```text
CacheBonus
```

例如：

$$
S'(c)=S(c)+\lambda C(c)
$$

其中：

```text
λ 很小
```

也就是说缓存只用于：

> 两个 Context 单元价值差不多时，更偏好已经稳定缓存的那个。

而不是缓存决定内容。

---

# 10. Context 还需要明确的 Authority

这一点也非常重要。

假设模型同时看到：

```text
用户：
不要改 public API。

AGENTS.md：
可以修改 API。

旧 task summary：
计划修改 API。
```

到底相信谁？

Compiler 应该提前解决。

比如：

```text
Authority
────────────────
System Policy
      ↓
User Current Instruction
      ↓
Project Explicit Rules
      ↓
Task Decisions
      ↓
Retrieved Documentation
      ↓
Old Summaries
      ↓
Model-generated Notes
```

发现冲突：

```text
OldSummary
vs
CurrentUserInstruction
```

直接淘汰旧 Summary。

不要把矛盾全部扔给 LLM：

> “你自己判断一下。”

---

# 11. Code Context 一定要 Content-addressed

比如：

```text
src/lexer.rs
lines 120-180
```

不够。

因为文件修改之后：

```text
lines 120-180
```

可能已经是另一段代码。

应该保存：

```text
CodeArtifact {
    path,
    symbol,
    range,
    file_hash,
    git_revision?,
}
```

例如：

```text
path:
src/lexer.rs

symbol:
Lexer::parse_escape

file_hash:
sha256:1234...

range:
143..208
```

如果：

```text
current_hash != stored_hash
```

这个 ContextUnit 自动：

```text
STALE
```

不允许重新进入 Hot Context。

这可以解决很多 Coding Agent 特别常见的问题：

> Agent 还在依据自己三轮之前读过的旧代码推理。

---

# 12. Context Compiler 应该主动做“去重”

例如：

```text
AGENTS.md:
Use cargo fmt before committing.

Skill:
Always run cargo fmt.

Project docs:
Code must be formatted with rustfmt.

Task notes:
Remember to run cargo fmt.
```

不能四份全部进去。

应该归约成：

```text
Project invariant:
- Rust changes must pass rustfmt.
```

保留 provenance：

```text
sources:
AGENTS.md
skill://rust
docs/contributing.md
```

所以 Context IR 最好支持：

```rust
struct DerivedContext {
    value: ContextValue,
    sources: Vec<SourceRef>,
}
```

这会极大降低：

```text
semantic duplication
```

---

# 13. Tool Result 处理应该分三级

这是 Wheel 特别值得做的。

## Level 1：Deterministic Reduction

不调用 LLM。

例如：

```text
ANSI escape
progress bar
spinner
重复 log
timestamps
```

全部删除。

---

## Level 2：Structural Reduction

还是不需要 LLM。

例如 Cargo：

原始：

```text
3000 lines
```

解析成：

```yaml
command: cargo test

status: failed

summary:
  passed: 127
  failed: 2

failures:
  - parser::nested_expr
  - lexer::unicode_escape

diagnostics:
  ...
```

TypeScript：

```text
tsc output
```

变成：

```yaml
errors:
  - file: src/a.ts
    line: 18
    code: TS2322
    ...
```

Git：

```text
git diff
```

可以先获得：

```text
3 files changed
+42 -17
```

再按需取具体 hunks。

---

## Level 3：Semantic Compaction

只有真正无法结构化的内容才调用 LLM：

```text
长讨论
设计探索
大量文档
复杂研究结果
```

---

# 14. 所以 `/compact` 不应该是唯一压缩机制

Wheel 应该至少有：

```text
continuous reduction
continuous eviction
checkpoint compaction
emergency compaction
```

### Continuous reduction

每一个 tool result 进来立即处理：

```text
raw 20K
→ structured 1.2K
```

---

### Continuous eviction

旧 Context 如果已经变成：

```text
re-fetchable
```

就直接移出 Hot Set。

---

### Checkpoint compaction

阶段完成：

```text
Exploration → Implementation
```

Compiler 创建：

```text
Checkpoint #4
```

保留：

```text
目标
关键发现
关键决定
相关文件
未解决事项
```

清掉 Exploration 阶段大量中间内容。

---

### Emergency compaction

只有：

```text
context budget almost exhausted
```

才是传统意义上的：

```text
/compact
```

所以理想状态下，用户很少需要主动调用它。

---

# 15. Compaction 一定要可追溯

这是我觉得当前 Agent 普遍做得不够好的地方。

例如：

```text
[Summary]
Parser architecture uses recursive descent...
```

之后模型可能想知道：

> 这个结论哪里来的？

所以 Summary 不能只是文本。

应该：

```yaml
summary:
  Parser is recursive descent.

evidence:
  - src/parser/mod.rs@a821...
  - src/parser/expr.rs@94ba...
  - session://events/882-901

generated_at:
  checkpoint: 4
```

这意味着：

```text
summary ≠ replacement
```

而是：

```text
summary = compressed view + pointers
```

需要时可以 rehydrate：

```text
context.expand(checkpoint:4, item:"parser architecture")
```

---

# 16. 我会特别设计一种 `Context Pointer`

例如模型看到：

```text
Recent test run:
2 failures.

[artifact:test/392]
```

而不是 5K log。

模型如果觉得：

> 我要完整看。

调用：

```text
context.inspect("artifact:test/392")
```

甚至：

```text
context.inspect(
    "artifact:test/392",
    section = "lexer::unicode_escape"
)
```

这个思想非常重要：

> **把 Context 本身做成可寻址的数据结构。**

Anthropic 最近 Managed Agents 也开始明确采用类似思想：session log 保持完整、可恢复的事件历史，而真正送进模型的 Context 是 Harness 从中选择、转换后的 view。([Anthropic][5])

这与 Wheel 非常契合。

---

如果真的要实现，我建议大概这样：

```text

              │
              ▼

┌─────────────────────────┐
```

```text
Telemetry
   ↓
Context effectiveness

```

再反过来优化下一轮。

---

# 18. Token Budget 不应该等于 Model Context Window

例如：

```text
model.context_window = 1M
```

Wheel 不应该：

```text
target = 900K
```

而是应该有：

```text
soft_active_budget
hard_active_budget
emergency_limit
```

例如概念上：

```text
1M Context Model

normal task:
40K–100K

large task:
100K–250K

exceptional:
250K+

1M:
capacity, not target
```

具体数字最后应该通过 eval 调出来，而不是硬编码。

但设计原则很明确：

> **默认从小 Context 开始，根据证据逐渐扩张。**

不是：

> 先全部装进去，再考虑删什么。

---

# 19. Context Budget 还应该按类型配额

例如，不一定真的写死百分比，但可以有：

```text
Pinned
────────────────
Core instructions
User intent
Task invariants
Safety
```

永远保证。

然后：

```text
Flexible
────────────────
Code
Docs
Diagnostics
Conversation
Tools
```

竞争剩余预算。

最后：

```text
Reserve
────────────────
next tool result
model output
reasoning
```

必须留下空间。

否则 Agent 很容易出现：

```text
读文件读到 95%
↓
运行测试
↓
结果放不进去
```

这种非常糟糕的状态。

---

# 20. 我认为缓存至少有四种，不应该只考虑 Provider KV Cache

Wheel 内部可以明确区分：

## ① Provider Prompt / KV Cache

OpenAI / Anthropic / Gemini 那一层。

目标：

```text
降低 latency
降低费用
```

---

## ② Artifact Cache

例如：

```text
AST parse
repo map
symbol index
file summary
test parse
documentation parse
```

key：

```text
content hash
```

文件没变：

```text
不用重新分析
```

---

## ③ Retrieval Cache

例如：

```text
query:
"where is panel lifetime handled?"
```

在同一个 repo revision 下：

```text
result set
```

可以缓存。

key：

```text
repo_revision
query_semantics
index_version
```

---

## ④ Compaction Cache

比如：

```text
events 2000..2500
```

已经 compact 成：

```text
checkpoint 7
```

只要事件没变：

```text
不用再次总结
```

---

因此：

```text
Context Cache
```

其实是：

```text
Provider Cache
Artifact Cache
Retrieval Cache
Compaction Cache
```

四层系统。

---

# 21. Prompt Cache 最关键的是“Stable Prefix”

例如一轮请求：

```text
████████████ Wheel Core
████████████ Core Tools
████████ Project Rules
████ Task State
██ Relevant Code
█ Current Input
```

第二轮：

```text
████████████ Wheel Core       HIT
████████████ Core Tools       HIT
████████ Project Rules        HIT
████ Task State               HIT?
██ New Relevant Code          MISS
█ New Input                   MISS
```

理想情况下：

```text
cache ratio = 80%+
```

完全可能。

而不是：

```text
每轮重新拼不同 Tool 顺序
↓
prefix changed at token 800
↓
95% Prompt Cache 全失效
```

---

# 22. Tool 激活尤其会影响 Prompt Cache

这个问题很容易被忽视。

假设第一轮：

```text
Tools:
read
edit
bash
```

第二轮：

```text
Tools:
read
edit
bash
github
```

如果 Provider 把 Tools 放在 prefix 前端：

```text
整个后续 prefix
```

都可能受到影响。

Anthropic 当前专门提供了 `defer_loading`：Tool Search 找到工具之后，用 `tool_reference` 追加进 conversation，而不会破坏原来的 system-prefix cache。([Claude Platform][1])

Wheel 也应该抽象这种能力。

例如：

```rust
enum ToolLoadingStrategy {
    Static,
    DeferredNative,
    WheelDispatch,
    CacheBranch,
}
```

Provider 支持 native deferred tools：

```text
直接使用
```

不支持：

Wheel 可以保持一个很小的静态：

```text
capability.search
capability.describe
```

找到能力后再决定：

```text
是否值得切换 Tool Set / 建新 cache branch
```

---

# 23. 但不要把所有 Tool 都做成一个万能 `call()`

例如：

```text
capability.call(
    name,
    params: JSON
)
```

虽然缓存很好：

```text
永远只有一个 Tool schema
```

但是工具调用准确率可能下降。

所以还是前面的原则：

```text
Correctness > Cache
```

更合理的是：

```text
Core high-frequency Tools
→ permanently loaded

Rare Tools
→ dynamically discovered
```

例如 Coding Agent 的核心可能长期只有：

```text
code.search
code.inspect
code.edit

process.run

context.inspect

task.update
```

而：

```text
GitHub
Jira
database
browser
cloud
```

都是 deferred capability。

这样既缓存友好，也不会出现万能 JSON Tool。

# 24. Provider Cache 能力应该抽象成 Capability

可以大概：

```rust
struct CacheCapabilities {
    mode: CacheMode,

    prefix_based: bool,

    max_breakpoints: Option<u8>,

    supports_explicit_cache: bool,
    supports_implicit_cache: bool,

    supports_prewarm: bool,

    ttl: Vec<Duration>,

    invalidation_rules: InvalidationRules,
}
```

例如：

```text
OpenAI
  prefix cache
  cache key
  diagnostics
  explicit breakpoints on supported models

Anthropic
  prefix cache
  explicit breakpoints
  auto caching
  deferred tool loading

Gemini
  implicit cache
  explicit CachedContent depending API
```

Provider plugin 自己负责不断跟进。

Wheel Context Compiler 只知道：

```text
CacheCapabilities
```

而不知道具体品牌细节。

# 25. Reasoning Level / Tool Choice 也应该进入 Cache Namespace

例如：

```text
Claude Opus
thinking = high
```

切成：

```text
thinking = low
```

或者：

```text
tool_choice
```

改变。

Provider 可能因此无法继续使用相同 cache。

Anthropic 当前就明确列出 thinking configuration、tool choice 等可能影响缓存复用。([Claude Platform][4])

OpenAI 当前文档也专门提醒，在某些最新模型上修改 reasoning configuration 时要注意保持 prefix 兼容。([OpenAI Developers][6])

所以本地 namespace 应该类似：

```text
CacheNamespace {
    provider,
    model,
    protocol_version,
    reasoning_profile,
    toolset_version,
    core_prompt_version,
}
```

不要期待：

```text
Claude cache
```

可以切 Gemini 继续复用。

那不是一回事。

# 30. 最后可以把它浓缩成五个子系统

我建议以后直接拆模块：

```text
context/
├── store/
│   ├── events
│   ├── artifacts
│   └── checkpoints
│
├── index/
│   ├── code
│   ├── docs
│   └── semantic
│
├── compiler/
│   ├── retrieval
│   ├── ranking
│   ├── dedup
│   ├── reduction
│   ├── budgeting
│   └── authority
│
├── cache/
│   ├── artifact
│   ├── retrieval
│   ├── compaction
│   └── provider
│
└── backend/
    ├── openai
    ├── anthropic
    ├── gemini
    └── ...
```

其中最重要的一条数据流是：

```text
                Full Session State
                       │
                       │ never directly
                       ▼
               Context Compiler
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
       Retrieve      Reduce       Cache Plan
          │            │            │
          └────────────┼────────────┘
                       ▼
                  Context IR
                       │
                       ▼
               Provider Backend
                       │
                       ▼
                 Model Context
```

这样 Wheel 就不会随着运行时间越来越长，变成：

```text
Session 越长
→ Context 越脏
→ Cache 越差
→ Agent 越笨
```

反而应该做到：

```text
Session 越长
→ Stored knowledge 越丰富

但是

Active Context
→ 始终小而高信号

Stable Prefix
→ 始终尽量稳定

Prompt Cache
→ 始终尽量高

Task State
→ 始终清晰
```

我觉得这可以成为 Wheel 与普通 Harness 最本质的架构区别之一：**不是管理一个不断增长的 Conversation，而是在管理一个不断增长的 Session Knowledge Graph，然后每一轮“编译”出最适合当前决策的 Context View。**

这比单纯的 `/compact` 高一个层级：`compact` 只是 Context Compiler 的一个 optimization pass，而不再是 Context 快爆掉以后才用的补救措施。
