以前设计 Wheel 的时候，都是考虑其核心的功能，不过 Wheel 本身还是由 bitty-ai 组装成的，所以 Bitty 很有特色的一点是不止是本身有 Lua 插件扩展，而且 Lua 插件之间存在 Lua 插件，也就是这个 IPC 不止是 Rust 与 Lua，而且是 Lua 与 Lua 之间的。
所以我才会说把那个大模型管理部分作为独立的一个 Plugin，那么这样的话是不是这些也是作为独立的呢？

- UI
- 模型管理
- 信息看板
- 扩展工具，因为不止是 Wheel 自带的那些可以调用的工具，很多时候用户开发的工具可以作为插件，而且这种插件可以在 .wheel 或者 \~/.config/wheel 中管理，这个很像 pi-agent 这样的靠插件扩展功能了

或者更多呢？在安装的 wheel 插件后可以选择安装这些，因为 wheel 确实可以在各个 Panel 中穿梭，只是很多时候都是 Headless 的形式罢了，而且很多东西其实都是不需要默认就有的呢？

我想这么设计是因为我不像让 Wheel 本身承担太多东西，而且很多部分可以设计的更好，比如这个 UI 部分，如果嵌入到本身的话，那么自定义就每次很麻烦，但是如果是独立的话那么改起来会方便很多

对，而且我觉得这样拆比“把所有 AI Harness 功能都塞进 Wheel”更符合 Bitty 现在的整体哲学。

更准确地说，可以把 **`bitty-ai` 看成一个 distribution / 组装层，Wheel 是其中的 Harness Kernel**。Wheel 本身只负责“Agent 能运行”所需的最小机制，其余能力通过 Lua Plugin 组合进去。

## 推荐边界

我会把结构大致定成这样：

| 组件                       | 是否 Wheel Core | 作用                                                              |
| ------------------------ | ------------: | --------------------------------------------------------------- |
| Agent Runtime            |             ✅ | Agent 生命周期、状态机、tool-call loop                                   |
| Context Engine           |             ✅ | message/context 基本表示、append、fork、checkpoint                     |
| Tool Protocol            |             ✅ | 定义 Tool 是什么、参数/结果协议、调用生命周期                                      |
| Plugin/Service API       |             ✅ | Lua Plugin 注册能力、服务发现、依赖                                         |
| Event Bus                |             ✅ | Agent / Tool / Panel / Model 等事件                                |
| Capability/Permission    |             ✅ | “这个 Agent 能不能调用这个能力”                                            |
| Panel Bridge             |        ✅ 最小接口 | 获取/创建/附着 Panel，不负责 UI                                           |
| Model API                |        ✅ 只有接口 | `generate()` / stream / tool calls 等抽象                          |
| **模型管理**                 |      ❌ Plugin | OpenAI / Anthropic / Gemini / Bedrock / Vertex / subscription 等 |
| **UI**                   |      ❌ Plugin | Chat UI、inline UI、floating panel、command palette                |
| **Dashboard**            |      ❌ Plugin | Agent、Task、Token、Context、Tool、Panel、资源状态                        |
| **Tool Packs**           |      ❌ Plugin | git、browser、AST、LSP、database、container……                        |
| **Memory**               |      ❌ Plugin | 长期记忆、项目记忆、用户记忆                                                  |
| **Context Strategy**     |         ❌ 大部分 | compact、DCP、remote compact、summarization                        |
| **Multi-Agent Strategy** |         ❌ 大部分 | Commander/Subagent、planner、reviewer、swarm                       |
| **Observability**        |      ❌ Plugin | traces、metrics、token/cost、cache hit                             |
| **History/Persistence**  |      ❌ Plugin | SQLite / log store / export/import                              |
| **MCP / Skills Adapter** |      ❌ Plugin | `.agents/` ecosystem 兼容                                         |
| **Policy Pack**          |      ❌ Plugin | 项目规则、安全策略、资源限制                                                  |
| **Provider Auth**        |      ❌ Plugin | OAuth/API Key/subscription credential                           |
| **Notification**         |      ❌ Plugin | desktop/terminal/webhook 等通知                                    |

其中最重要的一条边界是：

> **Wheel Core 提供 mechanism，Plugin 提供 policy。**

例如 Wheel Core 知道什么叫 `Context`，但“不应该决定何时 compact”；知道什么叫 `Agent`，但“不应该决定什么时候创建 5 个 Subagent”；知道什么叫 `Panel`，但“不应该规定聊天 UI 长什么样”。

这会让 Wheel 非常耐用。

## UI 尤其应该拆出去

你提到的 UI，我非常赞成独立。

因为 UI 是整个 Agent Harness 中**变化频率最高、个人偏好最强**的部分之一。

Wheel 只需要暴露：

```lua
wheel.events.subscribe(...)
wheel.agent.send(...)
wheel.agent.cancel(...)
wheel.session.current()
wheel.context.inspect(...)
wheel.tool.list(...)
wheel.panel.attach(...)
```

至于 UI 怎么表现：

```text
wheel-ui-minimal
wheel-ui-chat
wheel-ui-tui
wheel-ui-floating
wheel-ui-neovim-like
wheel-ui-dashboard
```

都可以完全不同。

甚至用户可以不用任何 Wheel UI。

例如：

```text
Bitty Panel
    │
    ├── shell
    │
    └── Wheel Agent (headless)
            │
            ├── IPC
            └── wheel-ui-dashboard
```

Agent 在一个 headless Panel 里面跑，用户在另外一个 Panel 看 Dashboard。

或者：

```text
Panel A ─┐
Panel B ─┼──── wheel-ui
Panel C ─┘
              │
              ▼
        Wheel Agent Runtime
```

UI 本身根本不必和 Agent 所在 Panel 相同。

这正好发挥 Bitty IPC 的优势。

## 模型管理也非常适合独立

这个实际上甚至不应该叫简单的 `provider`。

你之前设想的已经接近一个：

```text
LLM Runtime / Model Gateway
```

它负责：

```text
OpenAI
Anthropic
Gemini
Azure
AWS Bedrock
Vertex AI
OpenRouter
OpenCode Zen / Go
Claude subscription
ChatGPT subscription
Google subscription
Codex
Claude Code
Kiro
...
```

然后 Wheel 只看统一接口：

```lua
local model = require("models").get("claude-sonnet")

model:generate {
    messages = ctx,
    tools = tools,
    reasoning = "high",
}
```

Wheel 根本不需要知道背后是：

```text
API Key
OAuth
subscription
local model
OpenRouter
Bedrock
Vertex
```

这非常重要，因为 **模型生态变化速度远高于 Agent Harness Core**。

以后出现 GPT-7、Claude 6、Gemini 5，甚至新的 authentication / reasoning API，你只升级模型插件，而不是升级 Wheel。

## Tool 更应该天然插件化

这里我甚至建议 Tool 不只是：

```lua
wheel.register_tool(...)
```

而是允许整个 Plugin 成为一个 **Tool Provider**：

```lua
return {
    name = "wheel-tools-rust",

    provides = {
        "tool:rust.cargo_check",
        "tool:rust.cargo_test",
        "tool:rust.clippy",
        "tool:rust.symbols",
    }
}
```

另外一个插件：

```lua
return {
    name = "wheel-tools-git",

    provides = {
        "tool:git.status",
        "tool:git.diff",
        "tool:git.commit",
        "tool:git.worktree",
    }
}
```

甚至：

```text
wheel-tools-lsp
wheel-tools-browser
wheel-tools-database
wheel-tools-docker
wheel-tools-kubernetes
wheel-tools-github
wheel-tools-bitty
wheel-tools-filesystem
```

这样 Wheel 默认甚至不必有很多 Tool。

Core 可能只需要保留极少数基础 capability，例如：

```text
process
filesystem
panel
ipc
```

剩下的全部基于这些能力构建。

这和 Unix 很像。

# 最关键的其实是 Lua ↔ Lua

这里我觉得需要稍微修改一个概念：

不应该把所有 Lua Plugin 之间的通信都称为 IPC。

因为如果：

```text
Plugin A
Plugin B
```

都运行在同一个 Bitty process / Lua VM 中，那么最好走：

```text
Service Registry
Event Bus
Capability API
```

而不是 serialization → IPC → deserialize。

例如：

```lua
local models = bitty.service.get("ai.models")

local response = models.generate(...)
```

这是：

```text
Lua Plugin
    ↓
Bitty Service Registry
    ↓
Lua Plugin
```

而跨 Panel / Agent / Process 的时候：

```text
Lua Plugin
    ↓
Bitty IPC
    ↓
Lua Plugin
```

所以从架构上其实是两层：

```text
         ┌───────────────┐
         │ Service Bus   │
         └───────┬───────┘
                 │
       same process / VM
                 │
       Lua ◄──────────► Lua

────────────────────────────────

         ┌───────────────┐
         │ Bitty IPC     │
         └───────┬───────┘
                 │
       process / panel
                 │
       Lua ◄──────────► Lua
```

最好再让两者的 API 尽量统一。

比如：

```lua
bitty.service.call("ai.models", "generate", args)
```

Bitty 自己判断：

```text
local service
    → direct call

remote service
    → IPC RPC
```

这样 Lua Plugin 根本不在乎另外一个 Plugin 在哪里。

这个设计会非常强。

## 最后会自然形成 Dependency Graph

例如用户安装：

```text
wheel-ui
```

它声明：

```lua
requires = {
    "wheel",
}

optional = {
    "ai.models",
    "ai.dashboard",
}
```

而：

```text
wheel-dashboard
```

可能需要：

```text
wheel
bitty.panel
bitty.events
```

模型插件：

```text
wheel-models
 ├── provider-openai
 ├── provider-anthropic
 ├── provider-gemini
 └── provider-openrouter
```

Tool 插件：

```text
wheel-tools
 ├── git
 ├── filesystem
 ├── lsp
 ├── rust
 └── browser
```

最后就像一个 package graph。

这甚至和 Cargo/Nix/Linux package dependency 很接近。

## `.wheel/` 就可以真正成为 composition layer

你之前把项目级 Wheel 原生配置定成 `.wheel/`，我觉得到了这里它的作用会更加明确：

```text
.wheel/
├── init.lua
├── plugins.lua
├── models.lua
├── tools.lua
├── agents.lua
├── policy.lua
├── context.lua
└── ui.lua
```

例如：

```lua
return {
    plugins = {
        "wheel-models",
        "wheel-tools-git",
        "wheel-tools-rust",
        "wheel-ui-minimal",
    },

    disable = {
        "wheel-tools-browser",
    }
}
```

全局：

```text
~/.config/wheel/
```

负责个人默认配置。

项目：

```text
.wheel/
```

覆盖它。

而：

```text
.agents/
```

仍然继续承担跨 Harness 的标准化生态：

```text
Skills
MCP
Agent definitions
...
```

这样 `.wheel/` 和 `.agents/` 的职责不会混乱。

## 甚至 bitty-ai 都可以变成 meta package

最后可能出现一个很漂亮的关系：

```text
Bitty
│
├── Lua Runtime
├── Plugin System
├── IPC
├── Panel
├── Rendering/UI primitives
└── PTY
      │
      ▼
bitty-ai
│
├── Wheel
├── wheel-models
├── wheel-tools
├── wheel-ui
├── wheel-dashboard
├── wheel-context
├── wheel-memory
├── wheel-multi-agent
└── wheel-observability
```

其中：

```text
bitty-ai
```

甚至不是一个“大插件”，而更接近：

> **官方 AI plugin distribution**

就像一个预设集合。

用户安装：

```bash
bitty plugin add wheel
```

可能只有最小 Harness。

而：

```bash
bitty plugin add bitty-ai
```

则得到官方推荐组合。

甚至以后：

```text
bitty-ai-minimal
bitty-ai-coding
bitty-ai-research
bitty-ai-full
```

都只是不同的 plugin composition。

---

我认为这会成为 Bitty/Wheel 相比现在 Claude Code、Codex、OpenCode 这类 Harness 很有辨识度的一点：

**不是“一个 Agent Harness 支持插件”，而是 Agent Harness 本身就是由插件组成的。**

甚至可以进一步概括成：

```text
Bitty = Runtime
Wheel = Agent Kernel
bitty-ai = Distribution
Plugin = Capability
.wheel = Composition
.agents = Ecosystem Interop
IPC / Service Bus = Glue
```

这个边界一旦定下来，后面的 **UI、LLM、Tool、Context、Memory、Multi-Agent、Dashboard、Observability** 都不需要不断把 Wheel Core 撑大，Wheel 本身可以长期保持非常小。
