# bitty-ai Review Report (AI Runtime Skeleton + Slice Stress Tests)

- Scope: `bitty-ai/crates/bitty-ai-runtime/` (11 `src/*.rs` + 3 `tests/*.rs`, 14 rs files total), `bitty-ai/crates/bitty-ai-slice/` (7 `src/*.rs` + 4 `tests/*.rs`, 11 rs files total), plus `bitty-ai/Cargo.toml`, `bitty-ai/README.md`, `bitty-ai/docs/` (`bitty-ai-docs` submodule), `bitty-ai/scripts/`, `bitty-ai/justfile`, `bitty-ai/SECURITY.md`, `bitty-ai/deny.toml`, `bitty-ai/rust-toolchain.toml`.
- Method: first read the workspace `Cargo.toml` (resolver 3, edition 2024, MSRV 1.85, `publish=false`, runtime zero-dependency claim) and the two crates' `lib.rs` module trees; for runtime read module by module `agent/session/provider/stream/tool/context/prompt/bridge/selection/reconcile`, focusing on inference and session lifecycles, streaming fragments and cancellation checkpoints, timeout and quota dual caps, and determinism rules (all calls take `now_ms`; no wall clock/threads/network/secrets); for slice read module by module `bridge/error/harness/fake_host/live_host/local_provider`, focusing on whether context-slicing policy actually lands correctly in `bitty-ai-runtime/src/context.rs::assemble` (truncation ordering, window budgets, character boundaries, externalization atomicity), and whether integration assumptions with the `bitty` main repository's `bitty-ipc` (pinned rev `2cbb1fb`) are fragile (method registry, scope, consent, DTO/validate/bound reuse, sequence semantics); cross-checked evidence by running `cargo test --workspace --locked` (all green, including 11 slice vertical tests); read-only, no source changes.

## Defect List

### P0-1 (SEC): `bitty-ai/crates/bitty-ai-runtime/src/agent.rs::Agent::run_turn` snapshots stale `AuthBase`, and `rotate_generation` downgrades can be bypassed

- Phenomenon: each `run_turn` snapshots `AuthBase { agent_instance_id, session_id, level }` once at entry, and later `precheck` and every `dispatch` reuse that snapshot without re-reading `session.level()` / `generation`. If the host or peer calls `rotate_generation()` mid-turn through a cloned `AgentSession` handle (resetting to `Inspect`), the remaining `dispatch`es in the turn are still authorized at the old higher privilege level.
- Trigger: a `Workspace`/`All` session starts a turn with multiple tool calls; after the first `dispatch`, another handle calls `rotate_generation()`; subsequent `dispatch`es should be rejected by the `Inspect` read-only gate for write tools, but actually still pass the `Inspect` check in `ToolBus::authorize_call` at the old level.
- Evidence: `agent.rs:418-423` constructs `base` once; `506-514` loops with `dispatch(executor, call, &base, ...)` without re-reading; `session.rs:364-369` `rotate_generation` resets to `Inspect` only when `Active`; `tool.rs:613-618` `Inspect` read-only gating depends on the passed-in `base.level`. `session.rs:59-61` explicitly designs sessions as shared handles that can cancel across holders, showing mid-turn mutation is an expected reachable path.
- Security impact: violates the “server-side state; client claims are ignored” comment in `session.rs` and the `AG-2` rotation-invalidation intent: a lost downgrade signal is privilege escalation (low-integrity input not converged in time).

### P0-2: `bitty-ai/crates/bitty-ai-runtime/src/agent.rs::Agent::record_execution` silently drops tool bytes on externalization failure

- Phenomenon: when large `execution.data` fails to externalize into the `ArtifactStore` (full at 64 entries or 256 KiB), the `Err(_)` is swallowed and replaced with `RecordBody::Inline(Vec::new())`; tool output bytes are silently lost, but the turn still completes as `Success`.
- Trigger: `ArtifactStore` near `MAX_ARTIFACTS` / `MAX_ARTIFACT_STORE_BYTES`, with a tool result larger than `EXTERNALIZE_THRESHOLD_BYTES` (4 KiB) appearing in the turn; `store.store` returns `ArtifactStoreFull`.
- Evidence: the `match self.artifacts.store(...) { Ok(r)=>..., Err(_)=>Inline(empty) }` at `agent.rs:612-619`; `context.rs:338-361` `store` fails closed when full, while the caller converts the failure into empty data. This violates the very promise in `context.rs:18-19` that “missing/expired/deleted resolve to typed absence, never silent substitute”.
- Impact: auditability break: downstream sees an empty result and misjudges that the tool returned empty, rather than “preservation failed”; also inconsistent with the strict posture of `ToolBus::dispatch`, which directly returns `Err` for oversized results as `ResultTooLarge`.

### P1-1: `bitty-ai/crates/bitty-ai-runtime/src/agent.rs::Agent::run_turn` accumulates `executions` across turns without bound

- Phenomenon: the `run_turn` entry resets turn state with `tool_history.clear()` and `turn_cost=0`, but `self.executions: Vec<ExecutionRecord>` is never cleared and grows without bound across turns; the `dispatched` count in `reconcile_cancel`, `UnknownEscalation.dispatched`, and later target lookups in `reconcile_unknown` all mix in historical turns.
- Trigger: reusing the same `Agent` for two or more turns (inevitable in production; all existing tests create a fresh `Agent` per turn, so this was never exposed).
- Evidence: struct definition at `agent.rs:297-307`; `426-427` clears only `tool_history`/`turn_cost`; `654-673` `reconcile_cancel` counts the full `self.executions`; `730-733` `reconcile_unknown` searches full history by `execution_id`. No `MAX_EXECUTIONS` cap.
- Impact: resource leak (an attacker can bloat memory via multi-turn tool calls) + attribution errors (cancel/upgrade reports with inflated `dispatched`).

### P1-2: `bitty-ai/crates/bitty-ai-runtime/src/agent.rs::Agent::run_turn` does not enforce session terminal states

- Phenomenon: the entry only checks `is_cancelled()`, not `SessionState::Active`. A session already moved to `Completed` via `finish(false)` or to `Failed` via `fail()` in the previous turn can still `run_turn` and produce new `dispatch`es.
- Trigger: two consecutive `run_turn` calls on the same `Agent`/`AgentSession`, where the first completes or fails normally and the second still executes.
- Evidence: entry check at `agent.rs:385-390`; `finish` in `session.rs:322-330` transitions only from `Active`; `679-686` `fail` marks `Failed`. All three existing integration test suites never reuse a terminated session, so there is no coverage.
- Impact: lifecycle violation: the “terminal” semantics of completed/failed sessions are void; retries of `Failed` sessions should take the explicit `reconcile` path, but can be implicitly re-entered.

### P1-3 (SEC): `bitty-ai/crates/bitty-ai-slice/src/harness.rs::SnapshotRequest::params_json` does no JSON escaping

- Phenomenon: `instance`/`terminal`/`zone` are directly `format!`-interpolated into `{"instance":"{}"...}` without escaping `"`, `\`, or control characters. A malicious or abnormal zone name can break the wire params structure and inject extra fields into the host parser.
- Trigger: `zone` containing `"` or `\` (e.g. a polluted terminal semantic zone name flowing back into the request); the host side parses `terminal.snapshot` parameters as JSON.
- Evidence: direct `format!` interpolation at `harness.rs:75-81`; `terminal_record` in the same file explicitly marks terminal bytes as an untrusted surface, but the request side is not equally hardened. Although this is harness test assistance, it is easily copied into product wiring.
- Security impact: a classic injection surface: untrusted strings enter a structured envelope without encoding; a lenient host parser may suffer parameter confusion.

### P1-4 (SEC): `bitty-ai/crates/bitty-ai-slice/src/local_provider.rs::find_key_string` hand-extracts JSON by taking the first `"content"` substring

- Phenomenon: without tracking object depth/arrays/escape context, it globally substring-searches for the first `"content": "..."` and treats it as the assistant body. If the server-returned `error` field or a nested object contains the same string first, error text is mis-extracted as model output.
- Trigger: a polluted or abnormal local server returning e.g. `{"error":"missing content: \"x\"","choices":[]}`; or an Ollama/OpenAI-compatible layer returning multiple `choices` where only the first is taken without validating `role`/`finish_reason`.
- Evidence: the loop `find(&quoted)` + `parse_json_string` at `local_provider.rs:906-929`; `889-904` tries `content` then `response` with no path validation. `std`-only without `serde` is a known constraint, but the comment does not acknowledge this mis-extraction risk.
- Security impact: model-output integrity: an attacker can shape “what the model said”, influencing next-turn tool-call decisions (a transport-layer amplifier for prompt injection).

### P1-5: `bitty-ai/crates/bitty-ai-runtime/src/stream.rs::emit_fragments` restarts sequence numbers per batch, conflicting with transport deduplication semantics

- Phenomenon: `Agent::emit_text` and `emit_tool_card` each call `fragment_text` + `emit_fragments` per text/card batch, numbering each batch independently as `seq 0/total N`. A normal turn produces `[0/1 Markdown, 0/1 ToolCard, 0/1 Markdown]`. But `bitty-ipc`'s `FragmentIngestService` deduplicates by `(terminal_id,generation,seq)` keys, directly rejecting duplicate `seq`.
- Trigger: mapping multiple runtime blocks straight into transport as `chunk.seq -> FragmentData.seq` (as shown by the helper in `fragment_mapping.rs`); the second block already reports duplicate.
- Evidence: per-batch `total` computation at `stream.rs:258-276`; two emission points at `agent.rs:566-602`; `vertical_slice.rs:171` asserts all three blocks are `(0,1,true)`; `fragment_mapping.rs:277-304` asserts duplicate `seq` fails closed. Each side is correct alone; combined they break.
- Impact: end-to-end streaming to screen will largely fail if directly connected; either the mapping layer must renumber (requiring a defined global-sequence authority) or the runtime must number continuously across batches. Neither side currently has this layer.

### P1-6: `bitty-ai/crates/bitty-ai-runtime/src/session.rs::IdIssuer` numbers per `Agent`, conflicting with the single-binding assumption in `bridge.rs::IdentityBridge`

- Phenomenon: each `Agent::new` builds in an `IdIssuer::default()` starting from 1, so `AgentInstanceId/RunId/SessionId/ExecutionId` are unique only within a single `Agent`. `IdentityBridge` instead maps identity to instance via a global singleton binding of `(ProtocolAgentId, AgentInstanceId)`.
- Trigger: two `Agent`s in the same process (inevitable with multiple sessions/windows), both issuing `AgentInstanceId(1)`; the bridge cannot distinguish them, and `resolve_protocol(instance)` becomes ambiguous.
- Evidence: a fresh issuer on every construction at `agent.rs:312-323`; counters from 1 at `session.rs:99-135`; a single `Option<(ProtocolAgentId, AgentInstanceId)>` + second-pair `AlreadyBound` at `bridge.rs:295-333`. The comment says v0.1 is single-agent, but gives no issuer-isolation or namespace scheme for multi-instance cases.
- Impact: scaling out confuses identities; `ConsentQuery.agent_instance` attribution becomes unreliable with it.

### P1-7: `bitty-ai/crates/bitty-ai-runtime/src/session.rs::AgentSession` is `Rc<Cell>`, hence `!Send`, incompatible with async multi-threaded host foundations

- Phenomenon: `SessionInner` implements shared mutability with `Rc` + `Cell<AgentLevel/State>`, making the whole `AgentSession` `!Send !Sync`, unable to be held across threads/across `await`.
- Trigger: embedding the runtime in the `bitty` host's Tokio/multi-threaded executor, or holding the session while tool execution needs `.await`.
- Evidence: `use std::rc::Rc` at `session.rs:63-65`; `Rc<SessionInner>` + `Cell` at `240-253`. Deterministic tests benefit from this (lock-free), but the integration side documents no `Send` alternative design.
- Impact: an architectural coupling point: either the host is forced to drive AI turns single-threaded, or the runtime must migrate to `Arc<Mutex>`/`Arc<Atomic>` and re-prove cancellation-visibility ordering.

### P1-8: `bitty-ai/crates/bitty-ai-runtime/src/context.rs::assemble` non-atomically pollutes the `ArtifactStore`

- Phenomenon: the L1 externalization loop in `assemble` writes each `store.store(bytes)` directly into the caller-passed `&mut ArtifactStore`; if a later entry triggers `ArtifactStoreFull` or a subsequent budget check returns `BudgetExceeded`, previously stored artifacts remain, and `next_id` has already advanced on the next call, leaving visible residue.
- Trigger: `store` near the 64-entry/256 KiB caps + multiple >4 KiB inline bodies in this call; or a budget so small that even the minimal record does not fit.
- Evidence: direct `store.store(bytes)?` with `?` return inside the loop at `context.rs:644-658`, with no staging/rollback; `302-361` `store` itself guarantees immutability for a single `store`, but `assemble` as a whole does not. The comment “no partial assembly returned” covers only the return value, not store side effects.
- Impact: quota exhaustion degrades from fail-closed to half-committed: a failed turn steals usable artifact quota from later turns; `externalized` counts can also desynchronize from actual store entries.

### P2-1: `bitty-ai/crates/bitty-ai-runtime/src/stream.rs::validate_chunk` `OversizedChunk` branch is unreachable

- Phenomenon: `MAX_FRAGMENT_BYTES` 64 KiB < `MAX_STREAM_CHUNK_BYTES` 256 KiB, and both branches look only at `fragment.bytes.len()`, so anything over 256 KiB always hits `OversizedFragment` first, and `OversizedChunk` is never returned.
- Trigger: any oversized block; the RC-10 over-limit case in `vertical_slice.rs:336-361` actually asserts `OversizedFragment`, proving it.
- Evidence: constants at `stream.rs:12-16`; first check `>MAX_FRAGMENT` then `>MAX_STREAM` at `146-157`. If the intent was “chunk envelopes may exceed a single fragment”, the whole encoded `chunk` length (not the same field) should be validated.
- Impact: misleading error classification: callers cannot distinguish fragment-layer from transport-layer over-limit; the mapping comment to `bitty-ipc/wire.rs::CHUNK_CEILING` is therefore also off.

### P2-2: `bitty-ai/crates/bitty-ai-runtime/src/context.rs::assemble` has several effectively dead request fields

- Phenomenon: in `ContextRequest { max_tokens, max_bytes, priority, detail }`, `priority` and `detail` have zero references inside `assemble`; the `generation` field (`ContextRecord.generation`) likewise has zero references; duplicate record `id`s are not validated.
- Trigger: a caller sets `DetailLevel::Summary` expecting summaries only, or sets `request.priority` expecting global promotion, or passes an expired `generation`, or two records share an `id` (e.g. `harness.rs::terminal_record` generates via `format!("terminal-{generation}")`, so sampling twice in the same generation collides).
- Evidence: request definition at `context.rs:244-277`; the assembly body at `581-738` uses only `effective_budget_bytes()`, with no reads of `request.priority`/`request.detail` anywhere; no `generation` comparison inside `assemble`; the dedup key is `(provider,owner,summary,body)` (`616-621`) rather than `id`, so duplicate `id`s can both be selected, making `omitted_ids/pruned_ids` ambiguous.
- Impact: contract failure: hosts may over-expose body bytes (wanting only summaries), or retain expired context; duplicate `id`s make omission reports unattributable. Truncation/windows/boundaries themselves are carefully implemented (priority clamping, whole-packet-equality dedup, character-boundary truncation all have negative tests), but these dimensions are blind spots.

### P2-3: `bitty-ai/crates/bitty-ai-runtime/src/prompt.rs::assemble` computes budgets without enforcing them, and empty intersections silently succeed

- Phenomenon: `effective_budget_ceiling_bytes` takes the minimum across layers but never compares it against `canonical_bytes.len()` (only the 96 KiB hard cap is validated); two layers with disjoint `allowed_tools` yield `Some([])` and still return `Ok`, with total rejection deferred to `check_dispatch`.
- Trigger: Core sets `budget=1000` while text is 10 KiB; or Core allows `[tool_a]` while Project allows `[tool_b]`.
- Evidence: minimum-taking at `prompt.rs:1017-1026`; `render_canonical` at `1162-1266` checks only `MAX_CANONICAL_BYTES`; intersection logic at `1000-1015`. The existing `budget_min_wins_cannot_widen` only asserts the value taken, without enforcing it.
- Impact: fail-closed is delayed until dispatch time, giving callers a false “success” impression at assembly; the empty allowed set could directly signal a configuration conflict at assembly.

### P2-4: `bitty-ai/crates/bitty-ai-runtime/src/prompt.rs::parse_skill_chunk` reuses tool-name validation for skill names, overly strict

- Phenomenon: skill-entry `name`s are validated with `validate_prompt_tool_name` (`^[a-z][a-z0-9_]*$`), so conventional hyphenated skill names (e.g. `my-skill`) are judged `InvalidToolName`.
- Trigger: a registry containing a hyphenated skill name.
- Evidence: `prompt.rs:1963-1975`; tool shapes at `tool.rs:168-182` explicitly exclude `-`/`.`. Skill and tool namespaces should be independent.
- Impact: availability rather than security: legitimate skills are rejected; renaming to work around it then diverges from documentation examples.

### P2-5: Dual tool-call caps: `bitty-ai/crates/bitty-ai-runtime/src/tool.rs::MAX_TOOL_CALLS_PER_TURN` vs `agent.rs::AgentConfig::max_tool_calls_per_turn` take the minimum without declaring it

- Phenomenon: `Agent::run_turn` first checks bursts against `config.max_tool_calls_per_turn` (`agent.rs:484-491`), then enters `ToolBus::precheck` checking the constant 8 (`tool.rs:649-653`), with another run-count check against constant 8 inside `dispatch` (`675-679`). A host setting config to 16 still cannot relax above 8.
- Trigger: any configuration with config > 8.
- Evidence: constant 8 at `tool.rs:31`; `AgentConfig::default` takes that constant (`agent.rs:94`), but custom larger values are silently clamped. The `precheck_over_limit` test covers only the constant path.
- Impact: misleading configuration semantics; security-wise it is “only tighter, never looser” (acceptable), but docs must state “effective cap = min(config, constant)” or hosts will misjudge capacity.

### P2-6: `bitty-ai/crates/bitty-ai-runtime/src/selection.rs::ProviderRegistry::select` alias fall-through + split zero-weight semantics

- Phenomenon: when an `alias` is specified, alias candidates go first, but remaining capability-satisfying non-alias entries are still appended to the chain. If all alias candidates are expired or capability-mismatched, a caller requesting the alias still gets a non-alias model; `estimate_cost` treats weight 0 as 0, while `Agent::round_usage`'s `effective_cost_weight` treats 0 as 1.
- Trigger: an alias pointing at a retired model + another same-capability model in the registry; or a model registered with weight 0 (uncalibrated).
- Evidence: unconditional appending of `entries()` after the alias loop at `selection.rs:557-590`; the `alias_still_requires_capabilities` test instead codifies that fall-through as expected; zero-weight contributes 0 at `730-738` vs 1 at `agent.rs:818-820`. Routing therefore prefers uncalibrated models (cheapest), while accounting bills them as 1 — split behavior.
- Impact: routing surprise + quota fuses tripping early; recommend returning `NoCandidate` (or explicit `StaleAlias`) on full alias miss, and unifying zero-weight semantics.

### P2-7: Consent and error reason strings reflect unbounded input

- Phenomenon: `DenyAllConsent::check` interpolates the queried `tool` verbatim into the reason (`bridge.rs:445-451`); `ensure_consented` wraps it again into `ConsentDenied`; `ProviderError::Transport/Auth/RateLimited/Unknown` `reason`s are all unbounded `String`s, and `FakeConsentLedger::grant` only shape-validates tools, without charset validation on scope contents (beyond NUL/empty/length).
- Trigger: model-output tool names (`ToolCallRequest.name`, length-unlimited before assembly) or host-returned overlong reasons containing newlines enter logs and `Display`.
- Evidence: scope checks only for empty/NUL/128 bytes at `bridge.rs:509-528`; `authorize_call` in `tool.rs:599-601` limits length only after `validate_tool_name`, but the earlier host-side consent seam has no such guarantee. `MAX_RECONCILE_REASON_BYTES` constrains only the reconcile Escalation spot.
- Impact: low-severity log-injection/memory-amplification surface; recommend truncating all outbound reasons to a bound and scrubbing newlines (the existing `bound_reason` can be reused).

### P2-8 (SEC low): `bitty-ai/crates/bitty-ai-slice/src/local_provider.rs::LocalEndpoint::validate` path and Host-header checks too loose

- Phenomenon: `path` forbids ` `, `"`, `<> overall` etc. but allows `\t`, `?`, `#`, `;`, `:`, `@`, `&`, `%` and C0 controls other than `\r\n`; the `Host` header concatenates `endpoint.host` verbatim, so `::1` without brackets forms a malformed `::1:port`; `[localhost]` passes validation but fails `socket_addr` parsing (construction succeeds, connection fails).
- Trigger: callers passing unusual `path`s or unbracketed IPv6 literals.
- Evidence: blocklist-style validation at `local_provider.rs:303-324`; Host concatenation at `590-601`; split judgment on `[localhost]` at `392-404` vs `345-369`. localhost-only + trusted callers keep actual harm low, but this is a classic allowlist gap.
- Suggestion: switch `path` to an allowlist (starting with `/`, only `A-Za-z0-9/_-.~` plus explicit `/v1/...` prefixes), rejecting `\t` and C0; normalize Host to bracketed IPv6 uniformly.

### P2-9: Reconciliation and cost-accounting timing and caliber seams

- Phenomenon: `reconcile_unknown` passes the same `now_ms` on every retry in a turn (`agent.rs:754`), computing `_next_retry_ms` into an underscore-prefixed variable that is discarded, never advancing the clock; the `round_usage` fallback estimate uses `request.total_message_bytes()` (full history) instead of per-turn deltas, so longer history trips later-turn fuses earlier.
- Trigger: reconcilers depending on timeouts (multiple queries need time to advance); long-context multi-turn conversations tripping the cost fuse.
- Evidence: the loop at `agent.rs:747-783`; the fallback branch at `800-811`. All existing `unknown_reconcile` tests use a fixed `NOW_MS`, so frozen clocks cannot surface.
- Impact: liveness (should back off and advance) and fairness (history double-counting) issues; the current deterministic design intentionally does not sleep, but should state “callers must advance `now_ms` per `delays_ms` and re-invoke” with a documented formula, otherwise hosts passing the same timestamp misuse it.

## Test Gaps

- Multi-turn reuse: no integration test for “same `Agent` runs two turns”, so P1-1 (history accumulation) and P1-2 (terminal-state re-entry) fully leak. Needed: semantics of `executions.len()` after two successful turns, `turn_cost` reset, and rejection of a second `run_turn` on a `Completed` session.
- Mid-turn downgrade: no test for “`rotate_generation`/authorization revocation in `dispatch` gaps”, so P0-1 fully leaks. Needed: `FakeToolExecutor` rotating generation on the Nth call (following the existing `with_cancel_on_call` pattern), asserting remaining calls are rejected without rolling back already-dispatched ones.
- Store-full path: missing a large-result `Agent::run_turn` test when `ArtifactStore` is full, so P0-2 fully leaks. Needed: pre-fill store to 63/64 entries then run a large-result turn, asserting the whole turn `Failed(ArtifactStoreFull)` rather than succeeding with empty data.
- Assembly atomicity: no assertion of “`store.len()/total_bytes/next_id` unchanged after failed `assemble`”, so P1-8 fully leaks. The existing `artifact_store_exhaustion_fails_closed` only asserts unchanged `len`, not `total_bytes` and pre-staged entries.
- Sequence end-to-end: `vertical_slice` and `fragment_mapping` each assert correctness alone, but no joint test of “three real turn blocks straight into a real `FragmentIngestService` via existing mapping functions”, so P1-5 fully leaks. Needed: feed the three blocks from `run_harness` into the real service with existing mapping, asserting dedup behavior (should fail now, pass after fix).
- Dual budget tracks: no test that `config.max_tool_calls_per_turn=16` is still clamped by 8; no `DetailLevel::Summary` body-suppression test; no duplicate-`id` test; no `generation` expiry test.
- Time advancement: `reconcile_unknown` uses only fixed `now_ms`, with no test re-invoking with time advanced per `delays_ms`; no CJK/large-history inflation case for the cost fallback estimate.
- Local-provider abnormal semantics: existing stubs cover 401/403/429/404 and truncation/oversize, but no case for “`error` field containing a `content` substring first causing mis-extraction”, no construction-rejection cases for malformed `path`s (`\t`/`?`/`#`), and no `[localhost]`/`::1` unbracketed Host-header assertions.
- Concurrency: no compile-time assertion test (`static_assertions` style) for the `!Send` of `AgentSession`; host multi-threaded misuse surfaces only at integration time.

## Integration Risks with the bitty Main Repository (standalone section)

- **IPC revision pinning and silent drift**: slice references `bitty-ipc` via git rev `2cbb1fb` in `Cargo.toml` (`Cargo.lock` already locks `0.0.20`), and `fake_host.rs` carries a long header comment declaring that window “only adds `host_bridge.rs`, with identical DTO/validate/bound bytes”. Once the `bitty` side changes any bound/validate/scope enum, the hand-mirrored `FakeHost` (explicit step replicas of `dispatch_tool`/`execute`/`bound_snapshot`/`truncate_to_budget`) drifts, while `LiveBittyHost` (directly calling real services) changes behavior abruptly; both surface only under shared assertions in `host_conformance.rs`. There is no automatic follow-bump mechanism — a “pin for determinism, watch drift by hand” mode. Suggestion: add rev bumps to a scheduled `bitty-ai` CI task, automatically filing an Issue pointing at the `bitty`-side change when `host_conformance` fails.
- **Dual consent models**: the runtime `bridge.rs` `ConsentLedger` is a string triple `(protocol,tool,scope)` + `FakeConsentLedger` (64 entries), while `bitty-ipc/scope.rs` `ConsentLedger` is typed `(client_id, Scope)` + `MAX_GRANTS` 64. The shared capacity 64 is pure convention with no type-level linkage; the mapping from string scopes (`workspace.read`) to `Scope::TerminalInspect` etc. enums is scattered across `IpcBridge::call` (via `required_scope_for_method`/`authorize_method`) and host implementations, with no single mapping-table contract. Any case/dot-dash style mismatch causes cross-repo rejection, and rejection surfaces are defined separately on each side (`SliceError::ConsentRequired` vs `IpcError::Denied`), requiring cross-repo log correlation to debug.
- **Streaming triple-ceiling mismatch**: runtime production 64 KiB (`MAX_FRAGMENT_BYTES`) → `bitty-ipc/wire.rs::CHUNK_CEILING` 256 KiB → `rich_fragment.rs::MAX_FRAGMENT_TEXT_BYTES` 16 KiB. The three layers have different fail-closed/truncate policies (runtime rejects, wire rejects, ingest truncates with `truncated=true`), so a full 64 KiB block straight into 16 KiB necessarily truncates and loses bytes (`fragment_mapping.rs` already proves it). The `rich.*` wire methods are still unregistered (tests explicitly assert all five candidate names are `None`), so streaming to screen has no first-class transport method and can only use test-period mapping. Products bypassing wire methods to write the ingest service directly lose the scope/consent/provider-echo trio (the `ingest_takes_no_consent` test already declares the sequel belongs to the `bitty` track).
- **Two ID sets for identity and execution attribution**: the runtime `(AgentInstanceId,RunId,SessionId,ExecutionId)` are `u64` handles (`session.rs`), while the `bitty-ipc` side uses string `client_id` + `execution_id: u64` + `target`. `LiveBittyHost` passes `client_id.clone()` through to three real services, as does `FakeHost`, but the binding rule from the runtime bridge `ProtocolAgentId(owner.name)` to `client_id` is undefined (`IdentityBridge` only manages `owner.name <-> instance`, not `client_id`). `MAX_TOOL_CLIENT_ID_BYTES` and `MAX_EXEC_CLIENT_ID_BYTES` currently agree because they share the `auth::MAX_SCOPED_ID_BYTES` source, but each side defines its own constant; if upstream forks, the single length check in `LiveBittyHost::new` is half-wrong.
- **Synchronous loopback vs real-transport semantic gap**: `slice::bridge::IpcBridge::call` relies on the synchronous queue behavior of `IpcEndpoint`'s `send_request/recv_request/send_response/recv_response/complete` for correlation (`bridge.rs:132-165`); real-deployment socket/channel backpressure, timeouts (`DEFAULT_REQUEST_TIMEOUT_MS`), and `pending_count` backpressure are never exercised. `FakeHost`'s script queue is per-instance FIFO, while the real provider is a `fn` pointer table (`live_host.rs`); both fail closed on “missing handler”, but with different error payloads (different `NotFound` wording), so upper layers matching on wording are fragile and should match only on type.
- **Process-global mutability (live store)**: `live_host.rs::live_provider_tests` shares a process-global `OnceLock<Mutex<BTreeMap>>` live snapshot table with upstream `host_bridge.rs`; tests serialize via `live_test_lock` + `t:41xx` prefixes + surrounding fences. If products reuse that global table for multi-tenancy, tenant isolation (namespaces/quotas/cleanup) must be defined, otherwise cross-terminal interference results. The current 64-entry full-rejection semantics become quota contention under highly concurrent snapshot publication.
- **Tool-name vocabulary break**: the runtime `TB-2` (`^[a-z][a-z0-9_]*$`) rejects all dotted names, while slice legacy terms `terminal.read_zone`, provider legacy `local.deterministic`, and multi-level `StableId`s (`inst-1/term-1`) have all been renamed (declared in `harness.rs:11-19` and `vertical_slice.rs:12-20`). If the `bitty` side still uses dotted terms in docs/configs, they will all be rejected at the runtime boundary (`InvalidName`/`InvalidProviderId`/`InvalidStableId`), with rejection happening after model output (`UnknownTool` → whole turn `Failed`), visible to users as whole-turn failure rather than single-call retry. Recommend an explicit “vocabulary-mapping P1” in the integration contract with a rejection-code cross-reference.
- **Unknown execution-semantics consensus**: both sides agree on `Unknown` as “never blind-retry, only `resolve` after querying” (`execution.rs:1149/1169` vs `reconcile.rs`/`agent.rs::reconcile_unknown`), but query-clock semantics are unaligned: the runtime retries pass the same `now_ms`, while host-side `ConsentLedger::is_granted` and execution-store expiry judgments depend on caller-advanced time. If the host advances but the runtime freezes, retries may be rejected host-side for expired consent while the runtime still treats them as retryable `Pending`, forming a livelock. A cross-repo contract is needed for “who advances the clock, and by how much”.
